## 0. 先に結論（この章で一番効く 10 点）

1. **商品フィードの広告は「ベータ」の 1 つのキャンペーンの種類**。キャンペーンの作成で種類を「商品フィード」にし（API は `mode: product_feed`）、キャンペーン＝フィード・目的・予算・期間・地域、広告グループ＝入札・商品の絞り込み、広告＝商品広告のテンプレート（1 グループに 1 つ）と分かれる ✅〔仕様〕H:20001268（2026-11-11 ごろ更新）、D:Ads「Product Feed Campaigns」
2. **キャンペーンの種類・目的・つないだフィードは作成後に変えられない** ✅〔仕様〕D:Ads。フィードを差し替えるならキャンペーンを作り直す
3. **地域は国単位だけ**。都道府県・郵便番号は使えない（標準のキャンペーンとの違い）✅〔仕様〕H:20001268、D:Ads「Targeting」
4. **商品データの必須は 9 項目＋地域の 2 項目**（`item_id`・`title`・`description`・`url`・`brand`・`seller_name`・`image_url`・`availability`・`price`、と `target_countries`・`store_country`）。タイトルは 150 字・説明は 5,000 字までを目安に、と公式は書く ✅〔仕様〕D:Com「Product feed schema」
5. **項目は 2 週間で期限切れ**。手動の CSV だけで運用すると 2 週間で商品が消える。ホストした URL か SFTP の自動更新を公式が勧める ✅〔公式の推奨〕H:20001268
6. **広告に使うかは `is_ads_eligible` で決まる**。広告マネージャーで作ったフィードは、明示的に false にしない限り広告の対象。開発者文書の一般の規則は「書かなければ、フィードの既定が無い限り無効」✅〔仕様〕H:20001268、D:Com（両方とも正しく、**フィードの既定しだい**。§3-7）
7. **商品の絞り込み（商品セット）に使える項目は 14、数値の比較は価格と星の評価だけ**。カスタム ラベルは `ads_metadata` の中に置く。ラベルで地域名を付けても、その地域の利用者に配信が絞られるわけではない ✅〔仕様〕D:Ads「Ad Groups」「Product Sets & Filters」
8. **方針で却下された商品は、サポートに異議を出せない**。元のカタログを直すしかない ✅〔仕様〕H:20001268
9. **ベータの間、広告マネージャーのフィードの商品は広告にだけ使われ、ふつうの会話の商品表示には出ない** ✅〔仕様〕H:20001268。広告ではない商品表示に載せる道は別（67）
10. **日本向けに商品フィードの広告を配信できるかは ❓（2026-11-24 時点）**。日本語版のヘルプに国の限定は無く、開発者文書には日本円の価格の書き方まであるが、「日本で使える」とはどこにも書いていない。商品データの標準のアップロードは「今は米国向け」と書く ✅〔仕様〕D:Com。だから日本の EC は、使えると確かめるまで標準のチャット カードで商品ページへ送る〔推測〕（§12）

## 1. Google・Meta との対比

Google 側は `../Google広告の基礎/21_ショッピング広告と商品フィード.md`、Meta 側は `../Meta広告の基礎/21_カタログと商品の広告.md` に合わせた。

| 観点 | Google（ショッピング） | Meta（カタログ） | ChatGPT（商品フィードの広告） | 運用の判断への効き方 |
|---|---|---|---|---|
| 商品データの置き場所 | Merchant Center（広告とは別の管理画面） | コマースマネージャのカタログ | **広告マネージャーの中のフィード**（「ツール > フィード」）か API の `/v1/feeds` ✅ H:20001268 | 広告用のフィードは広告アカウントの持ち物。Business Hub の買い物用のフィード（67）とは別の道 |
| 何が商品と利用者を結ぶか | 検索語句と商品データ（キーワードは無い） | 行動のシグナル・ピクセル | **会話の文脈**と商品データ。文脈ヒントも広告グループに置ける（D:Ads Ad Groups の欄。商品フィードで効くかは ❓） | 商品タイトル・説明の具体さが入口〔推測〕 |
| 無料の掲載 | 無料リスティング（同じ Merchant Center のデータ） | ショップ | 広告マネージャーのフィードの商品は**自然な商品表示に出ない**（ベータ）✅ H:20001268 | 無料の露出と広告を 1 本のフィードで兼ねられない（今は） |
| 商品の束ね方 | 商品グループ（7 階層、G21§5-1） | 商品セット（フィルタ、M21§8） | **商品セット（フィルタ）**。項目は 14、比較は `in`・`gt`・`gte`・`lt`・`lte` ✅ D:Ads | Google の「商品グループで入札を分ける」形は無い。分けたいなら広告グループを分ける |
| 地域 | 国より細かく指定できる（Google 23） | 国より細かく指定できる（Meta 23） | **国単位だけ** ✅ | 国内の地域を絞った EC の計画は立てられない |
| 広告の形 | 商品の画像・価格・店名 | 単一画像・カルーセル・コレクション | 1 枚の商品カードか複数のカルーセル。**OpenAI が自動で選ぶ** ✅ H:20001268 | 形式を選べない。画像の差し替えだけが手 |
| 更新の速さ | 最後の更新から 30 日で失効（G21§3-5） | 日時指定の取り込み（M21§5-1） | **2 週間で期限切れ**。価格・在庫・タイトルは Delta API で部分更新（アカウントごとの許可制）✅ | 期限が Google の半分。自動更新を最初から組む |
| 不承認への対処 | 商品データを直すと自動で再審査（G21§4-1） | M21 を参照 | **商品の却下はサポートで異議を出せない** ✅ H:20001268 | 元データを直す以外の道が無い |
| 日本で使えるか | 使える（配送情報は日本で必須） | カタログ広告は使える | **❓**（§12） | 計画の前提にしない |

## 2. 仕組みの全体像

### 2-1. 4 つの部品 ✅〔仕様〕H:20001268、D:Ads「Product Feeds」

| 部品 | 中身 | 置き場所 |
|---|---|---|
| フィード | 商品のカタログ（1 行＝1 商品か 1 バリエーション）。名前と国を持つ | 広告アカウント（「ツール > フィード」、API の `POST /v1/feeds`） |
| 商品フィードのキャンペーン | フィード・目的・予算・期間・地域 | キャンペーン |
| 商品セット | 広告グループが使う商品の絞り込み（フィルタ）。省けばフィード全体 | 広告グループ |
| 商品広告のテンプレート | 商品から画像・タイトル・説明・価格・リンク先を差し込む広告。1 グループに 1 つ | 広告 |

- 公式の対象の説明: 商品が多いか、頻繁に変わる小売の広告主向け ✅ H:20001268
- 公式の主張: 商品フィードから作った広告は「これまでのプログラムで最も成果の良い広告の 1 つ」✅ H:20001268（英語版・日本語版とも）。**数字・比べた相手・期間は書かれていない** ❓。判断の根拠にはしない

### 2-2. 商品データが広告になるまで（流れは公式の記述を書き手が並べ直した）

1. フィードを作る（名前・国）→ 2. 商品を取り込む（CSV／TXT、ホストした URL、SFTP）→ 3. 処理を待ち、アップロード履歴で行の受理・却下を確かめる → 4. 商品ごとに審査（承認・保留・却下）→ 5. 商品フィードのキャンペーンを作る（フィードを選ぶ）→ 6. 広告グループで商品を絞り、入札を決める → 7. テンプレートの広告を作る → 8. 審査に出して配信 → 9. 「商品」タブ（配信の実績がある商品だけ）で成果を見る ✅ H:20001268（手順 1〜7 と「商品」タブの節）、D:Ads

- 作ったキャンペーン・広告グループ・広告は、API では一時停止で作られ、確かめてから有効にする設計 ✅ D:Ads「Product Feed Campaigns」
- 有効にしても、審査・在庫・予算などの配信の条件がそろうまで配信は始まらない ✅ D:Ads

### 2-3. 2 つのフィードの道（混同しやすい）

| 道 | どこで出すか | 何に使われるか | 既定 |
|---|---|---|---|
| **広告用のフィード** | 広告マネージャーの「ツール > フィード」、Ads API の `/v1/feeds` | 商品フィードの広告。**ベータの間は広告だけ**で、ふつうの会話の商品表示には出ない ✅ H:20001268 | 広告マネージャーで作ったフィードは広告の対象が既定 ✅ H:20001268 |
| **買い物用のフィード** | Business Hub（本人確認の後）か販売者向けの窓口 | 買い物の調べもの（検索）での商品の発見 ✅ D:Com「Submit product feeds」 | 検索は既定で有効、購入手続き（checkout）は既定で無効、広告は**フィードの既定が無ければ無効** ✅ D:Com「Minimal example」 |

- 商品データの項目の決まり（schema）は同じ 1 つの仕様（D:Com の Product feed schema）を使う。広告用は「この仕様＋広告の商品フィードの手引き」✅ D:Com「Ads」節
- **運用の判断への効き方**: 「Business Hub にフィードを出したから広告にも出る」「広告マネージャーにフィードを出したから自然な商品表示にも出る」は、どちらも今は成り立たない。目的ごとに別の道で出す（67§6）

### 2-4. 提供の段階

- ヘルプは「このベータの間」と書く ✅ H:20001268。**一般提供の時期は ❓**
- 開発者文書: フィードの API を使うには「アカウントに商品フィードの API の許可」が要り、無ければ OpenAI の担当チームに連絡、と書く ✅ D:Ads「Before you start」
- 変更の記録（Changelog）に商品フィードの新機能として載るのは、2026-06-11 の「商品・国・端末の区分けのレポートと、表示ゼロの商品の行」だけ ✅ D:Ads「Changelog」。商品フィードの広告そのものの開始日は ❓
- 商品フィードのコンバージョン最適化（oCPC）は「オープン ベータ」✅ D:Ads「Conversion-Optimized Campaigns」
- ホテルのフィードは「限定ベータ」（承認されたパイロットの広告主だけ。オープン ベータではない）✅ D:Ads「Hotel property feeds」（§13）

### 2-5. 運用の判断への効き方

- 商品数が少ない（数十点）店は、商品フィードの広告を使う理由が薄い。標準のチャット カードを商品ごと・用途ごとに書いたほうが、文面を管理できる〔推測〕
- 商品数が多く価格・在庫が日々変わる店は、フィードの自動更新（2 週間の期限）を作れるかが入口〔推測〕

## 3. 商品データの仕様 ✅〔仕様〕D:Com「Product feed schema」（2026-11-24 取得）

### 3-1. 書式の決まり（全体）

| 決まり | 中身 |
|---|---|
| 1 行の単位 | 買える 1 商品か 1 バリエーションごとに 1 行 |
| 文字コード | UTF-8 |
| URL | 絶対の HTTP か HTTPS（HTTPS を推奨）。商品ページと画像は**公開されていること** |
| 識別子 | 文字列で持つ（先頭の 0 を守る） |
| CSV の引用 | カンマ・引用符・改行を含むセルは引用符で囲み、中の引用符は 2 つ重ねる。CSV・TSV のセルに入れる JSON は直列化する |
| 空の値 | 任意の項目で分からない値は省く。省略・JSON の null・空のセルは「値なし」。`null`・`unknown`・`n/a` のような埋め草の文字は使わない（`unknown` は明記された所だけ）。空は 0 や false の意味ではない |
| 真偽値 | JSON の true／false か、区切りのファイルでは小文字の `true`／`false` |
| 検証の範囲 | 書式の説明は「不正な値をすべてアップロードで弾く」保証ではない |

- 広告用の取り込みの例は UTF-8 の CSV ✅ D:Ads「Prepare the product file」。ヘルプは CSV か TXT のアップロード ✅ H:20001268。**JSONL を広告マネージャーで取り込めるかは ❓**（仕様の例は JSONL で書かれている）

### 3-2. 必須の項目（基本の 9 項目）

| 項目 | 型 | 決まり | 例（公式の例を要約） |
|---|---|---|---|
| `item_id` | 文字列 | フィードの中で 1 商品（バリエーション）ごとに一意で変えない。別の商品に使い回さない | `TRAIL-BLK-10` |
| `title` | 文字列 | 商品名。関係するならバリエーション（色・サイズ）を含める。**150 字までを目安** | |
| `description` | 文字列 | その商品の事実の説明。プレーンテキスト。**5,000 字までを目安** | |
| `url` | URL | 商品の詳細ページ。できればバリエーションを選んだ状態の URL。変えない | |
| `brand` | 文字列 | 商品ページに出ているブランド。埋め草ではなく本物の名前 | |
| `seller_name` | 文字列 | その出品の売り手の名前。OpenAI の形式では**全行に必須** | |
| `image_url` | URL | そのバリエーションを写した主の画像。JPEG・PNG などの画像への直接の URL | |
| `availability` | 文字列 | `in_stock`・`out_of_stock`・`pre_order`・`backorder`・`unknown` のどれか。**省略・空・知らない値は行ごと却下**。在庫が分からないときは `unknown` を明記 | `in_stock` |
| `price` | 金額の文字列 | 通常の価格（§3-4 の書式） | `79.99 USD` |

- 「150 字」「5,000 字」は「aim for at most（多くてもこのくらいを目指す）」という書き方で、**超えたら却下されるかは書かれていない** ❓。日本語の 1 字の数え方も ❓（日本語の扱いの記述が無い）
- 公式は、ブランド名と売り手の名前に埋め草を使わないよう書く ✅

### 3-3. 必須の項目（地域の 2 項目）

| 項目 | 決まり |
|---|---|
| `target_countries` | 届け先の国。ISO 3166-1 alpha-2 の大文字の配列。**共通の形式が今表せるのは `US`・`CA`・`MX`**。標準のアップロードはこの列にかかわらず `["US"]` を使う。省略・空は「全世界」の意味ではない |
| `store_country` | 売り手の店の国。標準のアップロードはこの列にかかわらず `US` を使う。地域ごとの価格・在庫の上書きではない |

- 本文（Geo tagging）: 「OpenAI 形式の標準のアップロードは今は米国を対象にしている。行ごとの市場の列は既定を変えない。ほかの市場は、OpenAI が連携と許可する国・通貨を確認してから使う。通貨・商品の URL・サイズの体系は届け先の市場を選ばない」✅（00§2-3・05§8-3 と同じ）
- 複数の国に対応できるかは連携ごとに確かめ、配列の順番で市場が選ばれると思わない ✅
- **運用の判断への効き方**: 日本円の価格を書いても、`target_countries` に `JP` を書いても、それだけで日本向けにはならない（§12）

### 3-4. 価格と値下げ

| 決まり | 中身 |
|---|---|
| 書式 | `金額 通貨`（例 `79.99 USD`）。主の単位の小数、半角の空白、ISO 4217 の大文字 3 字。千の区切り・指数表記は使わない。小数の桁はその通貨で許される数まで（米ドルは 2 桁）。払う額と違う数に丸めない |
| 通常の価格 | 正の数。フィードで合意した通貨。セールの始まり・終わりでフィードを更新する |
| `sale_price` | 今のセール価格。0 より大きく、`price` より**厳密に小さく**、同じ通貨。省略・空なら `price` を使う。0 以下・同じ・高い・別の通貨のセール価格は**使われない** |
| 日付 | セールの期間・期限・在庫の日付の欄は、価格や在庫の変更を予約しない。変わったら今の値をフィードで送る |

- 日本円の書き方: 仕様の本文に日本円の例は無い。**Delta API の節は「日本円は小数の単位が無いので、`amount` の 7999 は 7,999 円」と書く** ✅ D:Ads「Price and availability formats」。CSV の `price` の日本円の書き方は「`7999 JPY`」になる〔推測: 書式の決まり「小数の桁はその通貨で許される数まで」から〕
- 広告の表示は価格とセール価格を見せる形式 ✅ H:20001268

### 3-5. バリエーションと識別子

| 項目 | 決まり |
|---|---|
| `group_id` | 親の出品の ID。バリエーションのときは条件つきで必須。全バリエーションで同じ値。`item_id` と違う値にする（省略すると `item_id` を使い、グループにならない） |
| `listing_has_variations` | バリエーションの全行で `true` |
| `variant_dict` | 選んだ選択肢の対応（例 `{"color":"Black","size":"10"}`）。`listing_has_variations=true` と、`item_id` と違う `group_id` が要る。グループ内で選択肢の名前をそろえ、組み合わせは重ねない |
| `offer_id` | 売り手の出品の ID。フィードの中で一意。**価格を ID に含めない** |
| `gtin` | 8・12・13・14 桁のどれか（検査数字が正しいこと）。先頭の 0 を守り、空白・ハイフンを入れない。割り当てが無ければ省く。ISBN-10 は出さない（ISBN-13 は 13 桁の GTIN として出せる） |
| `mpn` | 製造元の型番。`brand` と一緒に出す。GTIN の代わりに作らない |

- `item_id`・`group_id`・`offer_id` は、価格・在庫・タイトル・画像が変わっても変えない ✅
- 同じ商品のバリエーションだけをまとめる（サイトで同じ商品として見せているもの）。各行が自分の価格・在庫・URL・画像を持つ ✅

### 3-6. 任意の項目（商品の属性・画像・配送・返品・レビュー）

| 区分 | 項目と決まり |
|---|---|
| 状態 | `condition`: `new`・`refurbished`・`used`。省略は `new` と扱われうるので、中古・整備品は必ず書く |
| 分類 | `product_category`: 自社の分類を `>` でつなぐ（例 `Apparel & Accessories > Shoes`） |
| 属性 | `material`・`color`・`size`・`gender`（`male`・`female`・`unisex`）・`age_group`（`newborn`・`infant`・`toddler`・`kids`・`adult`。購入の年齢制限ではない） |
| 寸法 | `dimensions`: `length`・`width`・`height` のうち 2 つ以上と `unit`（`in`・`cm`・`ft`・`m`・`mm`）。新しいフィードはこちら。別々の欄（`length` などと `dimensions_unit`）も既存のフィード向けに残る。梱包ではなく商品の寸法 |
| 重さ | `weight`（梱包を除く正味）と `item_weight_unit`（`g`・`kg`・`oz`・`lb`） |
| 画像 | `additional_image_urls`: 追加の画像の URL の配列（CSV ではカンマ区切りの 1 セル。URL の中のカンマは `%2C`）。不正な URL は省かれる。**枚数の上限は記載なし** ❓ |
| 売り手 | `seller_url`: 売り手の店のページ。マーケットプレイスでは個々の売り手のページ |
| 配送 | `shipping_price`（OpenAI の形式。`price` と同じ通貨、0 は送料無料、省略は「不明」で送料無料ではない）か、連携の設定が要る `shipping`（`国:地域:サービス:金額` の 4 つの位置）。両方を同じ送料に送らない。表示に対応しているかは連携ごとに確かめる |
| 返品 | `accepts_returns`（true／false）、`return_deadline_in_days`（正の整数の日数。返品を受けるときだけ）、`return_policy`（公開の方針の URL）。最終販売の品は `accepts_returns=false` |
| レビュー | `review_count`（0 以上の整数、店のレビューを含めない）と `star_rating`（0〜5、小数 2 桁）。件数と評価は同じ母集団。バリエーションで共有のレビューは各行に同じ値を書き、足し合わせない。レビューが無ければ評価を省く |
| 設定が要る項目 | `marketplace_seller`、`size_system`（`US`・`UK`・`EU`・`DE`・`FR`・`JP`・`CN`・`IT`・`BR`・`MEX`・`AU`。届け先の国ではなくサイズの体系）、`store_review_count`・`store_star_rating`、`accepts_exchanges`、`is_digital`。**列を足しただけでは有効にならない**。連携の設定で確かめる |

- 個々のレビューの本文・Q&A は、この仕様の対象外 ✅
- **運用の判断への効き方**: 商品広告は星（評価）を見せる形式 ✅ H:20001268。`review_count` と `star_rating` が無い商品は、星の無いカードになる〔推測〕。評価 0 は表示から省かれうる ✅ D:Com

### 3-7. 広告の項目と、検索・購入手続きの旗

| 項目 | 決まり |
|---|---|
| `is_ads_eligible` | 広告で処理する商品は `true`。`false` は明示の辞退。**省略・空はフィードの広告の既定が無い限り無効**。検索の対象（`is_eligible_search`）とは独立 |
| `ads_metadata` | 商品の絞り込み用のメタデータ（文字列の値のオブジェクト）。キーは広告の連携で設定されたものを使う。**絞り込みのキーを自分で作らない**。例 `{"custom_label_0":"summer"}` |
| `is_eligible_search` | 検索の対象。省略・空は `true`。`false` にすると検索と購入手続きの両方が無効。対象でも表示の保証ではない |
| `is_eligible_checkout` | 購入手続きの対象。検索も `true` で、連携で購入手続きが有効なときだけ効く。省略・空・false は無効 |
| `seller_privacy_policy`・`seller_tos` | 購入手続きに条件つきで必須の、売り手のプライバシーの方針と利用規約の URL |

- 広告マネージャーの既定: 「広告マネージャーで作ったフィードは、商品が明示的に広告の対象外（false）でない限り、広告の対象になる」✅ H:20001268（英語版・日本語版）
- 開発者文書の CSV の例は全行に `is_ads_eligible=true` を書く。「広告で処理したい商品は true にする」✅ D:Ads「Prepare the product file」
- **運用の判断への効き方**: 広告マネージャーで作るなら空欄でも広告の対象になる。API や他の道で作ったフィードは既定が分からないので、**広告に出したい商品には `true` を明記する**のが安全〔推測〕。出したくない商品（利幅の薄い品・規制の品）は `false` を明記する

### 3-8. 互換の別名・使われない欄

- 受け付ける別名: `id`・`sku`→`item_id`、`item_group_id`→`group_id`、`enable_search`→`is_eligible_search`、`enable_checkout`→`is_eligible_checkout`、`is_eligible_ads`→`is_ads_eligible`、`return_window`→`return_deadline_in_days`。1 つの値に 1 つの名前だけを送る ✅
- 旧式の `Custom_variant1_category`／`Custom_variant1_option`（2・3 も）は受け付けるが、`variant_dict` へ移す。`variant_dict` が優先。表し方を混ぜない ✅
- **△ 仕様の本文の中の食い違い**: 別名の優先の説明で「`return_window` が `return_deadline_in_days` に勝つ」と書く一方、表では `return_deadline_in_days` を正の名前として書く（`return_window` は別名）。他の別名は「正の名前が勝つ」なので、この 1 か所だけ向きが逆 △ D:Com「Compatibility notes」。新しいフィードでは正の名前だけを使い、両方を送らない〔推測〕
- 本文の最後は「Warning and age-restriction fields」で途切れている（取得した一括版の終わり）。警告・年齢制限の欄の決まりは ❓

### 3-9. 運用の判断への効き方

- 必須の 11 項目が全行にそろわない行は、取り込みで弾かれる（`missing_required_column`、§4-4）。とくに `availability` の空欄は行ごと却下 ✅
- タイトル（150 字の目安）は商品カードの見出しになる。テンプレートで `{{brand}}: {{product.title}}` と組むと、ブランドの分だけ長くなる〔推測〕。カードでどこまで見えるかは ❓（標準のチャット カードの切れ方は 05§3-4）
- 価格の書式の誤り（通貨の欠け、千の区切り、桁の多い小数）は `invalid_value` で行が却下される（§4-4 の例は価格）✅ D:Ads

## 4. フィードの作り方と取り込み

### 4-1. 広告マネージャーで作る ✅〔仕様〕H:20001268（英語版・日本語版、2026-11-11 ごろ更新）

1. 広告マネージャーの「ツール」タブ → 「フィード」→「フィードを作成」→ 画面の指示どおりに作る
2. フィードの行の 3 点メニューから取り込み方を選ぶ

| 取り込み方 | 公式の向き不向き |
|---|---|
| CSV か TXT のアップロード | 始めるときや、ときどき手で直すとき |
| ホストした URL | 商品カタログが安定した HTTPS の住所にあるとき |
| SFTP の接続 | サーバーどうしのアップロードを自動にする技術チーム |

3. 処理を待つ。**フィードの大きさで数分〜数時間** ✅
4. 「アップロード履歴」で処理の状況とエラーを確かめる ✅

- **項目は 2 週間で期限切れ**になるので、ホストした URL か SFTP の自動のアップロードを勧める ✅〔公式の推奨〕
- ホストした URL の取り込みの間隔（毎日・毎時など）を選べるかは、商品のフィードについては ❓。ホテルのフィードの手順は「手動の取り込みか、使える自動の更新の予定を設定」と書く（D:Ads Hotel）ので、商品のフィードにも同じ画面がある可能性〔推測〕
- アップロードの失敗の直し方（公式）: 一般的なエラーが出たら、各行の値を仕様と照らす。必須の欠け・名前の違う列・書式の違う値を探す。メッセージがホストした URL を指していても CSV の中身を確かめる（同じファイルを直接上げても失敗するならなおさら）✅ H:20001268
- ファイルの大きさ・行数の上限は **記載なし** ❓（Google・Meta には上限の数字がある）

### 4-2. フィードの件数の 4 つの数 ✅〔仕様〕H:20001268（2026-11-24 に読んだ版で確認。05 には無い記述）

- 「フィードの接続」の「アイテム」の横の説明（ツールチップ）で、**取り込み済み（Ingested）・処理済み（Processed）・未承認（Not approved）・準備完了（Ready）**の数を見られる
- これらは**個々の商品ではなく、出品のレコードの数**。数ごとに対象の母集団が違いうるので、**引き算しても足りない商品の正確な数にならない**
- 方針の承認は、配信できる状態の保証ではない
- 「未承認」は集計の数で、対象の一覧や 1 件ずつの理由は出ない（理由は API の §6-2 で取る）
- この数は「商品」タブ（配信の実績がある商品だけ、§11）と別に扱う
- **運用の判断への効き方**: 「取り込み 1,000 − 準備完了 800 ＝ 200 件が落ちた」と報告しない。足りない商品は API の審査の一覧（§6-2）か、表示ゼロの商品の行（§11-3）で 1 件ずつ確かめる〔推測〕

### 4-3. API で作る ✅〔仕様〕D:Ads「Feed Setup & Ingestion」

| 手順 | 中身 |
|---|---|
| 前提 | 広告アカウントと、フィードを管理できる Advertiser API の鍵。**アカウントに商品フィードの API の許可**。仕様に沿ったカタログ。公開の商品ページと画像。SFTP の道具 |
| 1. フィードを作る | `POST /v1/feeds` に名前と、カタログが対応する国（`countries`）。返る `feed_id` を使う |
| 2. SFTP の接続を設定 | `POST /v1/feeds/{feed_id}/sftp_access`。パスワード（`authentication_method: password`）か SSH の公開鍵（`ssh_key`）。新しいパスワードを作ると古いものは置き換わる |
| 3. ファイルを用意 | UTF-8 の CSV。1 行 1 商品（バリエーション）。識別子を変えない |
| 4. 上げる | SFTP の**一番上の階層に直接置く**（入れ子のフォルダは不可）。分けるなら全部のファイルで 1 つのカタログを表し、各商品は 1 回だけ |
| 確かめる | 処理は非同期。転送の成功は「上がった」ことだけを意味する |

- フィードの一覧で `product_count` を求めると、**取り込み済みで広告の対象の商品の数**が返る。最初の取り込みの処理中は 0 のままのことがある ✅
- SFTP の接続の一時停止・再開: `POST /v1/feeds/{feed_id}/sftp_access/pause`・`/activate`。**これはアップロードの接続の操作で、広告の配信を止めるものではない**（配信はキャンペーン・広告グループ・広告で止める）✅
- 鍵はサーバーに置く ✅（この知識ベースの方針として鍵は作らない。読み取りの道具も作らない）

### 4-4. アップロードの状態と診断 ✅〔仕様〕D:Ads「Monitoring Uploads」「Troubleshooting」

| 状態 | 何をするか |
|---|---|
| `scanning`・`received`・`processing` | 処理中。終わりの状態と数を待つ |
| `completed` | 完了。数を確かめ、出したい商品を点検する |
| `completed_with_errors` | 一部は処理されたが誤りが残る。診断と却下の行を見る |
| `skipped` | 処理されなかった。商品が変わったと思う前に、元のファイルと履歴を確かめる |
| `failed` | 失敗。診断を見て直してから上げ直す |

| 診断のコード | 確かめること |
|---|---|
| `missing_required_column` | 列を仕様と照らし、欠けた必須の列を足す |
| `invalid_value` | 報告された欄の書式と許される値（例: 価格の金額と通貨） |
| `unsupported_file_type` | 対応する形式か（手引きは CSV） |
| `invalid_sftp_directory_layout` | 一番上の階層に置き、入れ子のフォルダを消す |

- アップロードの記録の例: 受理 1,245 行・却下 3 行・広告の対象 1,245 行、診断は `price` の `invalid_value`（警告）3 行 ✅
- 完了したアップロードは、全商品が配信できることを意味しない（商品データ・在庫・審査・絞り込み・キャンペーンの条件が別にある）✅
- 1 回のアップロードの数と、フィードの今の商品の数は違いうる ✅

### 4-5. 運用の判断への効き方

- 最初の取り込みは、**全商品ではなく数十点で試し**、`completed` と審査の結果を見てから全件を流す〔推測〕
- 価格・在庫の変化が日に 1 回以上ある店は、手動の CSV では 2 週間の期限と価格のずれの両方に当たる。ホストした URL か SFTP の自動化を最初に作る〔推測〕
- 商品画像のホストが OAI-SearchBot を 403 で弾くと、フィードの処理が止まりうる ✅（68§7、`C-審査-004`）。取り込みの前に 68 の点検をする

## 5. 更新（全体の上げ直し・Delta API・置き換えの設定）

### 5-1. どの方法で直すか ✅〔仕様〕D:Ads「Updating Feeds & Delta API」

| 変わったもの | 方法 |
|---|---|
| 既存の商品のタイトル・価格・在庫 | Delta API |
| 新しい商品を足す | 更新したカタログを SFTP で上げる |
| 画像・説明など他の項目 | 更新したカタログを SFTP で上げる |
| カタログ全体を新しくする | 更新したカタログを SFTP で上げる |

### 5-2. SFTP で上げ直すときの決まり ✅

1. 既存の商品の識別子を変えない
2. 在庫切れにしたい商品も含め、**今のカタログ全体**を入れる
3. 既存のファイルを置き換え、古いファイルを消す（同じファイル名の使い回しが楽）
4. 複数のファイルなら、各商品を 1 回だけ
5. アップロード履歴と、結果の商品を確かめる

- 売れない商品の配信を止めるには、`availability` を明示的に `out_of_stock` にする。戻ったら `in_stock` と今の情報を送る ✅
- Delta API で送った変更を元のカタログにも反映しておく（次の全体の上げ直しで古い値に戻さないため）✅

### 5-3. 全体の置き換え（`is_full_refresh`）✅

- 対象のフィードでは「カタログの置き換え」を有効にできる（`PATCH /v1/feeds/{feed_id}/settings` に `{"is_full_refresh": true}`）
- 有効にすると、以後の全体のアップロードには残したい商品を全部入れる。**入っていない商品は 1 日以内に OpenAI が消す**
- Delta API の部分更新には効かない
- 止めるには false で送る。保留中の消去は止まるが、**すでに消えた商品は戻らない**。欄を省けば設定は変わらない
- **運用の判断への効き方**: 置き換えを有効にしたまま、一部の商品だけのファイルを上げると、残りが 1 日で消える。分割のファイルで運用するときはとくに注意〔推測〕

### 5-4. Delta API ✅〔仕様〕D:Ads「Delta Feeds API」

| 項目 | 中身 |
|---|---|
| できること | 既存のバリエーションの**在庫・タイトル・価格**の更新。変わった商品だけを送る |
| できないこと | フィードを作る、カタログ全体を上げる、フィードに無い商品を足す |
| 許可 | **広告アカウントごとに有効化**。`403` で `product_feed_api_disabled` か `product_feed_delta_api_disabled` が返ったら、担当チームに許可を確かめる |
| 端点 | `PATCH /feeds/{feed_id}/products`（`/v1/` 付き） |
| ID | `products[].id`＝親の商品（バリエーションをまとめていれば `group_id`、なければ `item_id`）、`products[].variants[].id`＝個々の `item_id` |
| 価格 | `{"amount": 整数, "currency": "USD"}`。**整数の小さい単位**（8999＝89.99 米ドル）。日本円は小数の単位が無いので 7999＝7,999 円 |
| 在庫 | `availability.available`（true＝`in_stock`、false＝`out_of_stock`）か `availability.status`（両方あれば status が勝つ） |
| 制約 | `products` と各 `variants` は 1 件以上。ID は空にしない。同じバリエーションを 1 回の要求で重ねない。`shop_id`・`scoped_offer_id`・`target_country` は送らない（フィードから決まる） |
| 応答 | `200` と `accepted: true`。**受け付けただけ**で、索引・広告の対象・配信の反映ではない。完了の時刻も返らない |
| 誤り | `400`（欠け・空・知らない欄）、`401`（鍵）、`403`（許可・権限）、`404`（フィードが無いかアカウントが違う） |

- 価格の書き方が 3 通りある: CSV の `79.99 USD`（主の単位）、Delta API の `{"amount": 7999}`（小さい単位の整数）、キャンペーンの予算・入札の micros（50000000＝主の単位で 50）。**商品の価格に予算の micros を使わない** ✅
- 在庫切れの商品は、変更が行き渡った後に配信の対象から外れる。在庫に戻しても配信の保証ではない（商品・キャンペーン・広告グループ・広告の条件がある）✅
- 変更を何分で反映するかは **記載なし** ❓（「非同期」「時間を見込む」とだけ書く）

### 5-5. フィードのアーカイブ ✅

- 要らないフィードは `POST /v1/feeds/{feed_id}/archive`
- **アーカイブしていないキャンペーン・広告グループにつながっている間はアーカイブできない**。一時停止では足りず、先にそれらをアーカイブする

### 5-6. 運用の判断への効き方

- セールの開始・終了は、日付の欄では予約できない（§3-4）。**始まりと終わりの時刻に Delta API か全体の上げ直しを走らせる**仕組みが要る〔推測〕
- Delta API はアカウントごとの許可制。セルフサーブのアカウントで使えるかは ❓。使えない前提で、全体の上げ直しを短い間隔で回す設計を先に作る〔推測〕

## 6. 商品の審査と不承認

### 6-1. 何が審査されるか

- 商品は 1 件ずつ審査される（`approved`・`pending`・`rejected`）✅ D:Ads「Check product review status」
- 却下の理由の例は「Policy: Alcohol」✅ D:Ads（例の応答）。商品も広告ポリシー（31・34）の対象〔推測: 理由の書き方から〕
- フィードに出す商品は「フィードの仕様」に従う必要がある ✅ H:20001268

### 6-2. API で審査を確かめる ✅〔仕様〕D:Ads

| 項目 | 中身 |
|---|---|
| 端点 | `GET /v1/feeds/{feed_id}/products` |
| 鍵 | Advertiser API の鍵か、パートナーの OAuth（`ads.admin.all.read`）。利用者の範囲のトークンなら `OpenAI-Ad-Account` ヘッダーでアカウントを送る |
| 絞り | `is_approved=false`（保留と最終の却下の両方が入る）か `is_approved=true` |
| 状態 | 審査の閲覧の権限があれば `review_status`（ID ごとに approved／pending／rejected）。null か ID が無いのは「今の状態が無い」 |
| 理由 | `include_rejection_reasons=true` で `rejection_reasons`。null は「出せる説明が無い」で、却下でも null がありうる。却下かどうかは `review_status` で判断 |
| 1 ページ | `limit` は既定 20・最小 1。審査の閲覧の権限があれば 1 ページ**最大 100 件**。理由つきで 100 を超えると `400` |
| 次のページ | `has_more` が true なら、同じ絞りで `after` に `last_id` |
| ID | `data` の ID は中身の分からない ID。**1 つの SKU に複数の索引の ID がつくことがある** |
| 時間切れ | `503` は再試行 |

- 審査の閲覧の権限が無いアカウントは、`review_status` の無い一覧だけを受け取る ✅

### 6-3. 却下された商品への対処 ✅〔仕様〕H:20001268

- 個々の商品が「却下」「ポリシー違反による却下」なら、**サポートはその商品の異議・手動の審査ができない**。広告ポリシーと広告の商品フィードの手引きを読み、元のカタログを直す
- これは、アップロード・処理のエラー、説明のつかない状態の食い違い、個々の広告・アカウントの判断とは別（それらはそれぞれの手順に従う）
- 標準の広告・アカウントの却下は、管理画面の異議（Request Review）が最短。**商品は異議の道が無い**ところが違う

### 6-4. 運用の判断への効き方

- 酒類・健康食品・医薬品の近くの商品を含むカタログは、却下が増える〔推測〕。米国外の扱いは 31§2-2・34§2（ポリシーは 2026-11-20 に v1.7。94 の 2026-11-24 の点検）。**最初から `is_ads_eligible=false` で除いておく**ほうが、却下の数で取り込みの点検が見えにくくならない〔推測〕
- 却下の理由が null の商品は、ポリシーの章（31・34）と照らして自分で原因を推す以外に手が無い ❓

## 7. キャンペーン・広告グループ・広告の作り方

### 7-1. キャンペーン ✅〔仕様〕H:20001268、D:Ads「Product Feed Campaigns」「Campaigns」

| 決めること | 中身 |
|---|---|
| 種類 | 広告マネージャーの「キャンペーンの種類」で「商品フィード」。API は `mode: product_feed` と `product_feed_id` |
| フィード | 同じ広告アカウントのフィード |
| 目的 | 表示・クリック・コンバージョン（§9） |
| 予算・期間 | 標準と同じ（02§7） |
| 地域 | **国単位の指定・除外だけ**（新しい商品フィードのキャンペーン）。指定できる地域の選択肢は他の種類と違いうるので、アカウントで使えるものを使う |
| 変えられないもの | **種類（mode）・目的・つないだフィード** |

- 開発者文書の例は米国・米ドル・1 日 50 ドル・入札の上限 2 ドルのクリックのキャンペーン。「金額は例で、アカウントの通貨と計画に合わせる」✅
- 「新しい」商品フィードのキャンペーンが国単位、と書く。**前からあるキャンペーンが国より細かく指定できるかは ❓**

### 7-2. 広告グループ ✅〔仕様〕H:20001268、D:Ads「Ad Groups」

| 決めること | 中身 |
|---|---|
| フィード | キャンペーンのフィードを受け継ぐ（広告マネージャーでは選ぶ画面がある） |
| 商品の絞り込み | 商品セット（§8）。省けばフィード全体 |
| 商品数の確認 | 画面に出る商品数で、上げた商品のうち絞り込みを通る数を確かめる |
| 入札 | **成果の最大化（Maximize results）が、対象の新しい広告グループでは既定で選ばれる**。目的に合わせ、予算の中でクリックかコンバージョンが最も多くなるよう自動で入札を調整する ✅ H:20001268。開発者文書の例は固定の入札（`fixed_bid`）✅ D:Ads |
| 文脈ヒント | API の欄（`context_hints`）は広告グループにある ✅ D:Ads。商品フィードの広告グループで効くか・画面で入れられるかは ❓ |

- 開発者文書: 「成果の最大化が使えるかはアカウントとキャンペーンの設定しだい。商品フィードのキャンペーンで選ぶ前に条件を見る」✅ D:Ads。条件の中身は ❓
- 広告グループの更新で商品セットを変えるときは、**商品セットの全体**を送る。直後の応答に商品セットが入らないことがあるので、取り直して確かめる ✅ D:Ads

### 7-3. 広告（商品広告のテンプレート）✅〔仕様〕H:20001268、D:Ads「Ads」「Product Feed Campaigns」

| 項目 | 中身 |
|---|---|
| 種類 | `creative.type: product_ad_template` |
| 数 | **1 つの広告グループに、アーカイブしていないテンプレートは 1 つまで** |
| 差し込み | `{{brand}}`（ブランド）・`{{product.title}}`（タイトル）・`{{product.body}}`（説明）・`{{product.price}}`（価格） |
| 組み方 | 本文と価格は例のとおり（`{{product.body}}`・`{{product.price}}`）。タイトルは文と組める（例 `{{brand}}: {{product.title}}`） |
| 画像・リンク先 | **選ばれた商品から入る**。画像を上げたり（`file_id`）リンク先（`target_url`）を入れたりしない |
| 画面の制約 | 広告マネージャーのテンプレートは「今は画像の欄の選択だけに対応」 |
| プレビュー | サンプルの商品のプレビューで、タイトルと説明の見え方を確かめる。**実際の形と商品数は保証しない** |

- 「画像の欄の選択だけ」が何を選ぶのか（主の画像か追加の画像か）は ❓
- テンプレートの文字数の上限は ❓（標準のチャット カードはタイトル 3〜50・本文 100、05§3）

### 7-4. 計測用のパラメータ ✅〔仕様〕D:Ads、05§8-1、04§2-6

- 商品の URL に計測用のパラメータを付けるには、アカウントの計測の設定か、キャンペーン・広告グループ・広告の `landing_page_configuration`。**商品ごとの設定は無い**（広告の設定が商品の行き先に効く）
- 優先は「フィード < アカウント < キャンペーン < 広告グループ < 広告」（04§2-6。旧方式からの移行期限は 2026-11-05 で過ぎた）
- △ ヘルプとの書き方の違いは 06§7-3（ヘルプは「広告の URL ＞ 広告 ＞ 広告グループ ＞ キャンペーン」と書き、アカウントと商品フィードに触れない）

### 7-5. 配信の前の点検（公式の項目）✅ D:Ads「Inspect before activation」、H:20001268「Step 7」

- アカウントの状態と審査
- キャンペーンのフィード・目的・予算・地域
- 広告グループの入札と、絞り込みに合う商品
- 商品のタイトル・説明・価格・画像・リンク先
- 広告の審査と配信の問題（`include[]=serving_issues`。キャンペーン・広告グループでも取れる）
- 商品数が意図した数と合うか、テンプレートのプレビューが正しいか

### 7-6. 運用の判断への効き方

- フィードを選び間違えると作り直し（変えられない）。**フィードは国ごと・用途ごとに名前で分かるようにしてから**キャンペーンを作る〔推測〕
- テンプレートが 1 つしか置けないので、「見出しの書き方を 2 通り試す」は**広告グループを 2 つに分ける**しかない。ただし同じ商品を 2 つの広告グループに入れると、どちらが選ばれるかは ❓〔推測〕

## 8. 商品フィルター（商品セット）

### 8-1. 決まり ✅〔仕様〕D:Ads「Ad Groups」「Product Sets & Filters」

| 項目 | 中身 |
|---|---|
| 置き場所 | 広告グループの `product_set`。`product_feed_id` はキャンペーンのフィードと同じ |
| 使える項目（14） | `title`・`body`・`item_id`・`offer_id`・`price`・`target_url`・`image_url`・`product_category`・`brand`・`seller_name`・`external_seller_id`・`star_rating`・`condition`・`age_group`。加えて、連携が対応していれば `ads_metadata.<キー>` |
| 演算子 | `in`・`gt`・`gte`・`lt`・`lte` |
| 数値の比較 | `gt`・`gte`・`lt`・`lte` は **`price` と `star_rating` だけ** |
| 値 | 文字列の配列（数値も `"100"`・`"4.5"` のように文字列） |
| 組み合わせ | すべての条件を**同時に満たす**商品（AND） |
| 重ね | 1 つの商品セットの中で**同じ項目を 2 回使えない** |
| 空 | `"filters": []` で絞らない |

- 演算子に「含む」「前方一致」「否定（not_in）」は無い（ホテルのフィルタにはある。§13-4）✅〔仕様〕D:Ads の表の比較から。**除外の条件は書けない**ので、除きたい商品は `ads_metadata` のラベルで「入れる側」を作る〔推測〕
- 価格の比較の値の単位は主の単位（例 `"100"` は 100 米ドル以下）✅

### 8-2. カスタム ラベル（`ads_metadata`）✅〔仕様〕H:20001268、D:Ads

- 用意された項目で分けきれないときは、フィードの `ads_metadata` に値を入れて分ける。公式の例は `bidding_tier`（入札の段）・`product_line`（商品の系列）✅ H:20001268
- キーは「連携で対応しているもの」を使い、絞り込みのキーを作らない ✅ D:Com。**どのキーが使えるか（`custom_label_0〜4` か、自由なキーか）は ❓**（ヘルプの例は自由な名前、仕様の例は `custom_label_0`）△〔推測: 広告マネージャーと API・連携で違う可能性〕
- 同じカタログから、広告グループごとに違う部分を選べる ✅
- **`custom_label_0` に `WA`（ワシントン州）を入れて絞っても、ワシントン州の利用者への配信には絞られない**。ラベルは商品を選ぶもの。利用者の地域はキャンペーンの地域で決める ✅（英語版・日本語版とも、D:Ads の Targeting にも同じ注意）

### 8-3. 保存の前に試す ✅〔仕様〕D:Ads「Preview matching products」

- `POST /v1/feeds/{feed_id}/products/query` に予定の絞り込みを送ると、合う商品と `total_count`（全体）・`matched_count`（合う数）が返る
- 汎用の `POST /feeds/{feed_id}/items/query` は商品とホテルの両方に対応。消えた・期限切れ・広告の対象外の商品を除き、審査の承認は求めない。**商品向けの `/products/query` とは結果が違いうる** ✅
- 合っても表示の保証ではない ✅
- 合う商品が 0 のとき: まず空の絞り込みで調べる。出るなら条件を 1 つずつ足して、どれが落としているかを探す。空でも 0 なら、アップロード履歴を見る ✅
- カタログの更新（価格・ブランド・分類）で、絞り込みに合う商品が変わる。変更の後に選ばれた商品を見直す ✅

### 8-4. 運用の判断への効き方

- 価格帯で広告グループを分ける（例 1 万円以下・以上）と、セール価格ではなく通常の `price` で判定される可能性 ❓。セールの期間に商品が別の広告グループへ移るかは ❓
- 評価（`star_rating`）の下限で絞れる（例 4.0 以上）。星の無い商品が `gte` の条件で落ちるかは ❓〔推測: 値の無い項目は合わないと読める〕
- Google の「商品グループの入札を末端で分ける」形は無い。入札を分けたい単位で広告グループを分ける（入札は広告グループの持ち物）✅ 04§2-3

### 9-2. 成果の最大化 ✅ H:20001268

- 対象の新しい広告グループで既定。キャンペーンの目的に応じ、予算の中でクリックかコンバージョンを最多にするよう自動で入札を調整する

## 11. レポート

### 11-1. 「商品」タブ ✅〔仕様〕H:20001268

- 報告の画面で、上げた商品・対象の商品の一覧ではない
- 有効な商品フィードのキャンペーンで**配信の実績**があり、そのデータがレポートに入った商品だけが出る
- 始まっていない・開始日が先・まだ配信していないキャンペーンでは、空か、フィードより少ない。**フィードの失敗を意味しない**
- 配信が始まってから、商品の行が最初に出るまで**最大 7 時間**。キャンペーンの指標（表示・クリック・CTR）は**約 15 分**ごと、費用は**約 7〜8 時間**遅れる
- 配信した後も期待の商品が出ないときに、サポートへ送るもの: 広告アカウントの ID、フィードの ID、キャンペーンと広告グループの名前、期間と時間帯、例の商品の ID、「商品」タブの画面写し

### 11-2. 商品別の指標（API）✅〔仕様〕D:Ads「Product Reporting」

| 指標・欄 | 中身 |
|---|---|
| 区分け | `segments[]=product` |
| 欄 | `product.feed_id`・`product.item_id`・`product.title`・`product.impressions`・`product.clicks`・`product.spend`・`product.ctr` |
| 突き合わせ | フィードの ID と商品の ID の組でカタログに戻す（タイトルは読む人のため） |
| 粒度 | 日別は可。**時間別は不可** |
| カルーセル | `product.carousel_product_card_impressions`・`product.carousel_product_card_clicks`。**カードの表示は課金の表示ではなく、カードのクリックは広告のクリックとは別** |
| 購入の額・ROAS | 商品別ではなく、コンバージョンのレポート（06）で |

### 11-3. 表示ゼロの商品の行 ✅〔仕様〕D:Ads「Insights」

- 区分けのレポートと「表示ゼロの商品の展開」が有効なアカウントでは、表示ゼロの商品の行も返せる（2026-06-11 に追加）
- ゼロの行は、取れない指標の欄が省かれる
- **運用の判断への効き方**: 「フィードにあるのに出ていない商品」を見つける唯一の公式の道。画面の「商品」タブには出ない（§11-1）。この機能がセルフサーブのアカウントで有効かは ❓

### 11-4. 保存期間

- 商品のレポートは約 30 日 ✅ S-01（06§12-3）。**月次の報告に使うなら毎月書き出して残す**〔推測〕（06 と同じ）

### 11-5. 運用の判断への効き方

- 商品別に見られるのは表示・クリック・費用・CTR まで。**商品別のコンバージョン・売上は商品のレポートに無い**（コンバージョンのレポートに `contents`〔06〕で商品の情報を送っていれば、別に突き合わせられる可能性〔推測〕）
- ads-mcp の週次の報告に商品別の表を足すなら、表示・クリック・CTR・CPC（費用÷クリック）は作れ、CV・CVR・CPA は商品別には作れない、と表に注記する〔推測〕（運用者の「指標は網羅する」の決まりに対し、欠ける理由を書く）

## 12. 地域と国の制約・日本向けに使えるか

### 12-1. 公式に書いてあること（全部）

### 12-3. 読み方

- #5 は **D:Com（買い物用のフィードの仕様）**の Geo tagging の節で、広告の手引きは「商品データはこの仕様を使う」と書く（D:Com の Ads 節、D:Ads の Before you start）。だから広告用のフィードにも #5 が当たる、と読むのが自然〔推測〕

- △ 既存の章（00§2-3、05§8-3、61§3#4）は「日本向けは ❓」で、この章も同じ結論。**食い違いは無い**

### 12-4. 確かめ方〔推測〕

1. 広告マネージャーの「ツール > フィード > フィードを作成」で、国の選択肢に日本があるかを見る（作成の手前まで。画面の操作は運用者本人が行う）
2. サポート（ads-support@openai.com、34）に「日本の広告アカウントで、日本の利用者向けに日本円の商品フィードの広告を出せるか」を聞く（費用はかからない）
3. 開発者文書の Geo tagging の節（https://developers.openai.com/commerce/specs/file-upload/products ）の「US・CA・MX」に JP が足されるかを見張る（61§5 の見張る項目）

### 12-5. 運用の判断への効き方

- **日本の EC の計画は、標準のチャット カードで商品ページへ送る形を前提にする**〔推測〕。商品フィードは確かめられてから

## 13. ホテルの物件フィード（限定ベータ）✅〔仕様〕D:Ads「Hotel property feeds (limited beta)」（2026-11-24 取得）

### 13-1. 提供の範囲

- **承認されたパイロットの広告主だけ**。オープン ベータではない。項目・検証・機能はベータの間に変わりうる
- ホテルの選択肢がアカウントに無ければ、OpenAI の担当チームに連絡
- キャンペーンは**国全体だけ**。地域の除外・細かい地域・絞り込んだプラットフォームの指定は使えない。目的はクリック、課金はクリック、**手動の CPC（固定の入札）**。自動入札と商品セットは使えない（入札の選択肢は担当チームに聞く）。開発者文書の Campaigns の参照は「米国全体」の指定を要すると書く（省けば米国）
- 日本で使えるかは ❓（例も条件も米国）

### 13-2. 作り方

| 方法 | フィードを作る | ファイルを送る |
|---|---|---|
| 広告マネージャー | 「フィード > フィードを作成」で在庫の種類に「ホテル」 | CSV／TXT のアップロード、ホストした URL（HTTP の Basic 認証可、手動の取得か自動の更新の予定）、SFTP |
| Ads API | `inventory_type`（hotel）と `schema_profile`（`hotel_property_v1`）を明示（省くとホテルのフィードにならない）。`Idempotency-Key` が必須 | SFTP（パスワードか SSH 鍵。片方に変えるともう片方は無効） |

- 更新は既存のフィードで全体の写し（スナップショット）を上げ直す。**更新のたびにフィードを作らない**。`hotel_id` を変えない
- 一覧とアップロード履歴は `inventory_type=hotel` を付ける（省くと商品の在庫が既定）

### 13-3. 項目（`hotel_property_v1`。1 行＝1 物件で、部屋・料金プラン・宿泊日ではない）

| 項目 | 必須 | 決まり |
|---|---|---|
| `hotel_id` | ○ | 大文字小文字を区別する文字列、**100 字まで**。変えない |
| `name` | ○ | 表示の名前、**150 字まで** |
| `description` | ○ | 物件の説明、**5,000 字まで** |
| `url` | ○ | 物件の LP、**2,048 字まで**。認証情報を埋め込まない |
| `brand` | | ホテル・チェーンのブランド、70 字まで（広告主の表示名とは別） |
| `status` | | `active` か `archived`（既定 active） |
| `is_ads_eligible` | | 省けばフィードの既定。旧名 `is_eligible_ads` と食い違うと行を却下 |
| `images` | ○ | JSON の配列で **1〜20 枚**。各 `url`（2,048 字まで）と `tags`（20 個まで、各 1〜64 字）。有効な画像が 1 枚も無い行は却下。最初の画像が主 |
| `location.address.city` | ○ | 100 字まで |
| `location.address.country_code` | ○ | ISO 3166-1 alpha-2。**物件の所在地で、広告を出す国ではない** |
| `location.coordinates.latitude`・`longitude` | ○ | −90〜90、−180〜180 |
| `location.address.addr1`・`region`・`postal_code` | | 200・100・32 字まで |
| `location.neighborhoods` | | JSON の配列、20 個まで・各 100 字まで |
| `base_price` | | 静的な最低価格（例 `149.00 USD`、64 字まで）。宿泊日の見積もり・空室の表示ではない。**入れることを強く勧める** |
| `star_rating` | | 1.0〜5.0、0.5 刻み（物件の星で、宿泊者の評価ではない） |
| `category` | | 200 字まで |
| `ads_metadata` | | JSON のオブジェクト、**50 個まで**。キー 80 字まで・値 200 字まで。キーは大文字小文字を区別せず一意 |
| `guest_rating[n].*` | | 宿泊者の評価を**最大 20 組**。各組に `rating_system`・`score`・`max_score`（0 より大きく 100 以下）・`number_of_reviewers` の 4 つ全部。**入れることを強く勧める** |

- 使われない列: `room_id`・`checkin_date`・`length_of_stay`・`sale_price`・`tax`・`fees`・`phone`・`applink`・`priority`・`margin_level`・`custom_label_*`・`custom_number_*`・`internal_label` など ✅
- 対象外: 部分・差分の更新、Delta API、XML、部屋・料金プラン、変動の料金、宿泊日の空室
- 10 物件の例の CSV が公開されている（https://developers.openai.com/ads/hotel-property-feed-v1-public-example.csv ）

### 13-4. ホテルの絞り込み（ホテル セット）

| 項目 | 演算子 |
|---|---|
| `country` | `in`・`not_in` |
| `region`・`city` | `in`・`not_in`（値は JSON にした地域の道筋。例 `["US","California","San Francisco"]`） |
| `category` | `in`・`not_in`・`contains`・`not_contains`・`starts_with` |
| `ads_metadata.<キー>` | 同上 |

- すべての条件が合うこと。`in` は値のどれかに合えばよい。**大文字小文字を区別しない**。値の無い項目は否定の条件に合わない。各項目は 1 回まで。`contains` などは値 1 つ
- `hotel_id` では絞れない（`ads_metadata` のラベルで束ねる）。商品の `brand`・`price` も使えない
- **絞り込みは物件を選ぶもので、配信先の利用者の地域ではない** ✅

### 13-5. 広告とプレビュー

- 広告は `product_ad_template` と `{{product.*}}` の差し込み（本文 `{{product.body}}`・価格 `{{product.price}}`）。画像とリンク先は物件から。1 グループに 1 つ
- プレビュー: `POST /v1/ads/{ad_id}/preview`（物件は指定できず、サーバーが 1 つ選ぶ）。今の・有効な・広告の対象の・**審査で承認された**物件が無いと `422`。カードは最低価格と宿泊者の評価を（あれば）出す。署名つきのリンクは**作成から 24 時間**で切れる。宿泊日の空室も配信も保証しない

### 13-6. 運用の判断への効き方

- 日本の宿泊業には今は関係が薄い（限定ベータ・米国の例だけ）〔推測〕。米国に物件を持つ・米国の旅行者を集めたい事業者だけが、担当チーム経由で検討する
- 宿泊日の料金・空室を扱えないので、「今夜空いている部屋」の訴求はできない。最低価格と評価の訴求になる

## 14. 判断の型〔推測。§2〜§13 の仕様から組んだ〕

### 14-1. 商品フィードの広告を使うかの 5 つの問い

1. **日本向けに出せると確かめたか**（§12）→ いいえなら、標準のチャット カードで商品ページへ
2. 商品は数百点以上か、価格・在庫が週に何度も変わるか → いいえなら、標準のチャット カードのほうが文面を管理しやすい
3. 2 週間の期限より短い間隔で、フィードを自動で上げ直せるか（ホストした URL か SFTP）→ いいえなら始めない
4. 全商品に必須の 11 項目がそろい、`availability` が空欄の商品が無いか
5. 商品画像のホストが OAI-SearchBot を通すか（68§7）

### 14-2. 構成の型

| 層 | 型 |
|---|---|
| フィード | 国（市場）ごとに 1 つ。名前に国と用途を入れる |
| キャンペーン | フィード × 目的 ごとに 1 つ（変えられないので）。まずクリック目的 |
| 広告グループ | 予算や入札を分けたい商品の束ごと（`ads_metadata` の `product_line` や `bidding_tier`）。テンプレートを比べたいときも広告グループを分ける |
| 広告 | テンプレート 1 つ。タイトルは `{{product.title}}` だけか `{{brand}}: {{product.title}}` |

### 14-3. この表示・出来事があったら

| 見えたもの | まず確かめる | 出典 |
|---|---|---|
| 「商品」タブが空 | 配信が始まって 7 時間たったか。キャンペーンが配信したか。**フィードの失敗とは限らない** | §11-1 |
| 取り込みが `completed_with_errors` | 診断のコードと却下の行。価格の書式・必須の欠け | §4-4 |
| `product_count` が 0 のまま | 最初の処理中か。`is_ads_eligible` が false か空（フィードの既定が無い） | §4-3、§3-7 |
| 絞り込みに合う商品が 0 | 空の絞り込みで出るか → 条件を 1 つずつ | §8-3 |
| 商品が却下 | 理由（null もある）→ 元のカタログを直す。異議は出せない | §6 |
| 2 週間後に商品が消えた | 期限切れ。自動の更新が止まっていないか | §4-1 |
| 全体の上げ直しの後に商品が消えた | 置き換えの設定（`is_full_refresh`）が有効で、ファイルに入れ忘れた | §5-3 |
| Delta API が 403 | `product_feed_delta_api_disabled` → 許可が無い。再試行しない | §5-4 |
| 配信が少ない | 地域（国単位）・オーディエンス・端末・入札・**使える商品の数**の組み合わせ | D:Ads Targeting、02§8 |

## 18. 既存の章との食い違い

- **rules.csv `C-コマース-002`**（「商品フィードは検索では既定で有効、広告では既定で無効」）: 仕様（D:Com）は「広告はフィードに広告の既定が設定されていなければ無効」、ヘルプ（H:20001268）は「広告マネージャーで作ったフィードは、明示的に false でない限り広告の対象」。**どちらの道で作ったかで既定が違う**ので、行に条件を足す必要がある（この章の C-コマース-002・029）
