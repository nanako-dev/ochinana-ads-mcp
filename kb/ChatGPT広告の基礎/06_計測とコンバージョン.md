## 0. 先に結論（この章で一番効く 10 点）

1. **送り方は 3 つ: OpenAI ピクセル（ブラウザ）、コンバージョン API（サーバー）、画像タグ（JavaScript なし）。** どれも「データソース」（ピクセル ID）に送る。サーバーだけで送る場合もピクセル ID は要る ✅〔公式〕本文（S-01 Conversion Tracking、S-45 20001604）
2. **ピクセルとコンバージョン API を両方使うなら、同じピクセル ID・同じイベント名・同じイベント ID で送る。** 重複を除く鍵はこの 3 つ（カスタム イベントはイベント名の代わりに `custom_event_name`）。**先に届いたほうを採り、後から届いたものは捨てる** ✅〔公式〕本文（S-01 Measurement Pixel・Conversions API）
3. **`oppref` が計測の要。** 広告のクリックで LP の URL の末尾に付く OpenAI のクリックの参照。ピクセルが拾ってファースト パーティ Cookie `__oppref`（書き込みから 30 日）に入れる。**コンバージョン API は自動で拾わない**ので、自分で保存して送る。**リダイレクトで落とさない** ✅〔公式〕本文（S-01、S-45 20001409）
4. **コンバージョン API は「起きてから 7 日以内」の出来事しか受け付けない**（未来は 10 分まで）。1 回に 1,000 件まで送れるが、**1 件でも不正だと全体が失敗する**。イベントの品質の点検は「起きてから 1 時間以内に届いたか」を見る ✅〔公式〕本文（S-01 Conversions API、K-01）
5. **自動詳細マッチング（AAM）は、日本以外では既定でオン、日本の広告アカウントでは広告主がオン・オフを選ぶ。** ピクセルの編集画面で設定する。日本の既定値は書かれていない ❓ ✅〔公式〕本文（S-45 20001409 の英語版・日本語版）
6. **最適化（コンバージョン目的）に使えるのは標準イベントだけ。** カスタム イベントは計測には使えるが最適化の目標にできない。目的と選んだイベントは作成後に変えられない ✅〔公式〕本文（S-01、S-37）
7. **ビュースルーは、レポートの「コンバージョン」の合計に入る（ビュースルーの期間を 1 日にしているとき。既定は 1 日）。** 0 日にすればクリックスルーだけになる。**2026-11-18 のヘルプ（23 時間前に更新）とレポートの開発者文書・変更履歴はそう書き、ピクセルとコンバージョン API の開発者文書の 2 か所だけが「含まない」と古いまま残っている** △ → 運用は「含む」で読む（§11-3）✅〔公式〕本文（S-45 20001214、S-01 Reporting・Changelog）
8. **レポートの期間（クリック 7／14／30 日、ビュー 0／1 日）を変えても、最適化・入札・課金は変わらない。** 見え方だけ。帰属は**最後の接点（ラストタッチ）**で、データドリブンのような配分は無い ✅〔公式〕本文（S-45 20001214、K-08）
9. **数字の遅れ: 表示・クリック・CTR は約 15 分、費用は約 7〜8 時間、コンバージョンは 24〜48 時間。** 今日・昨日の CPA は必ずぶれる。**審査のクローラーがトラッキング パラメータ付きで LP を訪れ、GA4 などで有料の流入に見える**が、課金されるクリックではない ✅〔公式〕本文（S-45 20001214、S-31）
10. **Ads Manager・GA4・CRM の数字は合わないのが正常。** 窓、計上日（広告に触れた日か成果の日か）、ビュースルー、モデル化、重複除外、時間帯が違う。GA4 を Ads Manager につなぐ機能（ベータ）があるが、取り込んだ数字は**サイト全体の流入の合計で、キャンペーンに帰属した成果ではない** ✅〔公式〕本文（S-45 20001604、K-02）

## 2. 道具の全体（何がどこにあるか）

### 2-1. 部品 ✅〔公式〕本文（S-01 Conversion Tracking・Conversion Setup）

| 部品 | 何をするか | 管理画面・API |
|---|---|---|
| データソース（ピクセル ID） | ウェブサイトやサーバーからイベントを受ける器。`pixel_id`（送るときに使う）と `id`（イベント設定で選ぶときに使う）の 2 つの番号を持つ | 「コンバージョン」>「データソース」。API は `POST /v1/conversions/pixels`（`client_type` は `web`） |
| コンバージョン イベントの設定 | 「どのデータソースの、どのイベントを成果として数えるか」の定義。イベントを送る機能ではない。1 設定に 1 データソース | API は `POST /v1/conversions/event_settings`。`attribution_window_days` は「30 を使う」と書かれている |
| キャンペーンへの紐づけ | 設定をキャンペーンに付けると、そのキャンペーンの成果として数える。表示・クリックのキャンペーンも、目的を変えずに成果を計測できる | `conversion_event_setting_ids`（更新は**一覧の置き換え**。残したいものも全部送る） |
| 2 つの鍵 | 管理用の「Advertiser API キー」（`api.ads.openai.com`）と、イベント送信用の「Conversions API キー」（`bzr.openai.com`）は別物 | どちらもサーバーに置く。ブラウザのコードに置かない |

- 紐づけの効き方: **目標の成果のレポートは、紐づけた時点から先にだけ効く**（過去にさかのぼらない）✅ 本文（S-01 Reporting「Goal reporting applies going forward from attachment」）。ヘルプも「設定の食い違いを直しても、過去の分は埋まらない」と書く ✅ 本文（S-45 20001214、20001604）
- 紐づけていないイベントも、API の `include: ["attributed_events"]` で「帰属したイベント」として見られる（目標ではないイベントの集計）✅ 本文（S-01 Reporting）
- ピクセルの管理と API キーの作成は、アカウントで有効になっている必要がある（API で 404 なら担当者に連絡）✅ 本文（S-01 Conversion Setup）

### 2-2. 運用の判断への効き方

- **配信を始める前に、成果の設定をキャンペーンに付ける。** 後から付けても、それまでの成果は目標として数え直されない
- **表示・クリックの目的でも成果を付けておく。** 後でコンバージョン目的の新しいキャンペーンを作るとき、どのイベントがどれだけ出ているかの土台になる〔推測〕
- **紐づけの更新は置き換え。** API や自動化の道具で 1 つ足すつもりで送ると、既存の設定が外れる

### 2-3. Google との違い

- Google はコンバージョン アクションに「メイン／サブ」の区別があり、入札に使うのはメインだけ（G06 §4）。ChatGPT には ❓ その区別の記載が無い。**最適化に使うのは、コンバージョン目的のキャンペーンで選んだ 1 つの標準イベントだけ**で、ほかの紐づけは計測用 ✅ 本文（S-01）

## 3. OpenAI ピクセル（ブラウザ）

### 3-1. 置き方 ✅〔公式〕本文（S-01 Measurement Pixel）

- 成果を測りたい**全ページの `<head>` の上のほう**に置く（早い成果を取りこぼさないため）。SDK は `https://bzrcdn.openai.com/sdk/oaiq.min.js`
- `oaiq("init", { pixelId: ... })` で初期化し、成果の時点で `oaiq("measure", イベント名, データ, 任意の設定)` を呼ぶ。`debug` を付けるとブラウザのコンソールに動きが出る
- **ピクセルは必ずブラウザで使う。ページのコードからサーバー用のコンバージョン API を直接呼ばない**（鍵が漏れる）
- 金額・数量は整数。金額は通貨の**最小単位**で送る（米ドル 89.00 は `8900`、**日本円 8,900 円は `8900`**。円は最小単位が 1 円なので、そのままの金額）✅ 本文（S-01 Conversion Tracking）
- コンテンツ セキュリティ ポリシー（CSP）があるサイトは、`script-src` に `bzrcdn.openai.com`、`connect-src` に `bzr.openai.com` と `bzrcdn.openai.com`、`img-src` に `bzr.openai.com` を足す。ピクセルのためだけに `'unsafe-inline'` を足さない
- 1 つのページで複数のピクセル ID を使える（複数の広告主・ブランド・パートナー）。`measure` は初期化済みの全ピクセルに送り、`measureSingle` は 1 つだけに送る ✅ 本文（S-01 Multiple Pixel IDs）

### 3-2. Google タグ マネージャーで入れてよいか ✅〔公式〕本文（S-45 20001214、K-03）

- **よい。** ただし正しいページで読み込み、初期化と `measure` の順番を崩さないこと。**GTM で「タグが発火した」と出ても、イベントが送られた証拠にはならない**（コンソールとネットワークで確かめる）
- 第三者の実装の道具として、Stape（GTM のウェブ用・サーバー用のテンプレート）と Datahash が公式ヘルプに載っている（どちらも提供元が保守）✅ 本文（K-03）

### 3-3. 同意 ✅〔公式〕本文（S-01、S-45 20001409・20001604）

| 項目 | 決まり |
|---|---|
| 既定 | 同意あり（`true`）。`false` にするか、保存された拒否があると送らない |
| 拒否の間 | 計測のイベントを送らない。**止めた分は、後で同意しても送り直されない** |
| Cookie | 拒否にすると `__oppref` と `__obref` の両方を消す |
| 画像タグ | 必要な同意を取ってから表示する |
| `opt_out` | 個人向けの利用（パーソナライズ）を断る印で、計測を止めるものではない。OpenAI は今、ピクセル・API のデータを個人向けに使っていない、将来使うならこの印を守る、と書く |
| 法令 | 「法律で求められる場合は、集めるデータを利用者に明確に説明し、必要な同意を得てから送る」とだけ書く。日本の法令（個別の規律）への当てはめは ❓ 公式に記載なし |

- **運用の判断への効き方**: 同意管理の仕組み（CMP）があるサイトは、`consent` を初期化の前に `false` にし、同意の後で `true` にする。同意を外して成果を増やすことは、公式ヘルプが明確に「しないで」と書いている ✅ 本文（S-45 20001604）

### 3-4. ピクセルが自動でしていること ✅〔公式〕本文（S-01）

- LP の URL から `oppref` を拾う
- `oppref` をファースト パーティ Cookie `__oppref` に入れ、後のページで使い回す
- ページのオリジンを `source_url` として付ける
- イベントに時刻を付け、近い時刻の `measure` をまとめて送る
- AAM がオンなら、サイトの顧客情報を見つけてブラウザの中で SHA-256 でハッシュ化し、イベントに添える

### 3-5. Cookie ✅〔公式〕本文（S-01）

| Cookie | 中身 | 期限 |
|---|---|---|
| `__oppref` | LP の URL の `oppref` | 書き込みから 30 日。空でない `oppref` を受けるたびに 30 日に戻る。参照するだけの訪問では延びない |
| `__obref` | このサイト用にランダムに作ったブラウザの参照 | 作成から 365 日。延長しない。無いか壊れていれば作り直す |

- Cookie の期限は、アトリビューションの窓とも、成果のデータの保存期間とも別の話。ブラウザの制限や Cookie の削除で短くなる ✅ 本文（S-01）
- **運用の判断への効き方**: クリックの窓を 30 日にしても、`__oppref` は 30 日で切れ、ブラウザの制限でもっと早く消えうる。Google の `_gcl_aw`（90 日）より短い〔推測: 長い検討の商材ほど、ピクセルだけでは取りこぼす〕

### 3-6. ピクセルのテスト ✅〔公式〕本文（S-01、S-45 20001604）

1. Ads Manager の「コンバージョン」>「データソース」で、ウェブのピクセルの「…」>「テスト」
2. ピクセルを入れたページの URL を入れて「テストを開始」→ 開いたサイトで操作する
3. 「イベントストリーム」に戻ると、そのセッションのイベントに「テスト」の印が付く

- 印が付くのは**最長 30 分**、開いたタブ・同じオリジンだけ（別のドメインやサブドメインは入らない）
- イベントが多いと一部だけ表示、遅れることもある。**テストのイベントもふつうの集計に入る**（除かれない）
- API の `GET /v1/conversions/events` は、**直近およそ 15 分の最新 50 件**を返す（試験と点検用で、帰属や報告用ではない）。ブラウザからは `pixel_sdk`、サーバーからは `server_to_server` と出る ✅ 本文（S-01）
- ログインした後のページ、購入手続きの各段階、ログイン前のページもそれぞれ試す。CSP で止められていないかをコンソールとネットワークで見る ✅ 本文（S-45 20001214）

### 3-7. 運用の判断への効き方

- **最初に確かめるのは「成果のイベントが送られているか」。** ピクセルが読み込まれても、購入・リードのイベントが呼ばれていなければ数は 0。公式ヘルプは「送られていないなら、レポートを待っても直らない」と書く ✅ 本文（S-45 20001604）
- **テストの成果は集計に入る。** 本番の口座で試すなら、試した時刻とイベント ID を台帳に書き、報告で引く〔推測〕
- **予約サイトや別ドメインの決済**（外部の予約システムなど）は、そのページにピクセルが入らないと取れない。公式は「LP で動いても他のページで動く保証にはならない」と書く ✅ 本文（S-45 20001604）

## 4. コンバージョン API（サーバー）

### 4-1. 何が良くなるか ✅〔公式〕本文（S-01 Conversions API・Conversion-Optimized Campaigns）

- ブラウザでの送信だけに頼らずに成果を測れる
- 顧客の識別子を足して照合を上げられる
- 送信と再送をサーバーで管理できる
- 公式は「コンバージョン API はピクセルだけより確実な計測の源」と書く
- 公式の推奨: **`oppref` があるイベントだけでなく、すべての成果のイベントを送る**（ビュースルーの成果を成績に入れるため）✅ 本文（S-01 Conversions API、S-45 20001409）

### 4-2. 送り方と決まり ✅〔公式〕本文（S-01 Conversions API・Conversion Tracking）

| 項目 | 決まり |
|---|---|
| 宛先 | `POST https://bzr.openai.com/v1/events?pid=<ピクセル ID>`、Conversions API キーで認証。サーバーからだけ送る |
| 鍵の作り方 | Ads Manager の「コンバージョン」タブで、ピクセル ID と Conversions API キーを作れる。API パートナーは管理用のキーで作れる |
| まとめて送る数 | 1 回に 1,000 件まで。**1 件でも失敗すると、その回の全部が失敗する** |
| 時刻 | `timestamp_ms`（ミリ秒の Unix 時刻）。**過去 7 日以内、未来は 10 分まで**。古い出来事の時刻を書き換えて通さない（ヘルプが明記）|
| イベント ID | `id`（必須）。再送するときと、ピクセルと両方で送るときは同じ値 |
| `action_source` | `web`・`mobile_app`・`offline`・`physical_store`・`phone_call`・`email`・`other`。`web` のときは `source_url` が必須 |
| `oppref` | イベントの階層に置く（`user` の中ではない）。**OpenAI から渡された文字列を変えずに送る。API は自動で拾わない** |
| 試すだけ | `"validate_only": true` で、保存せずに形だけ確かめる（イベントの点検の一覧にも出ない） |
| パートナーの印 | 広告主の代わりに送るなら、毎回 `integration_source`（1〜64 字の安定した名前）を付ける。認証には影響しない |

### 4-3. `user`（照合用の情報）✅〔公式〕本文（S-01 Conversions API）

| 項目 | 送り方 |
|---|---|
| メール（`emails_sha256`） | 前後の空白を除き小文字にして SHA-256 |
| 電話（`phone_numbers_sha256`） | 国番号を残し、空白・括弧・点・ハイフン・先頭の `+`・先頭の 0 を除いた 8〜15 桁を SHA-256 |
| 自社の顧客 ID（`external_ids_sha256`） | 前後の空白だけ除き、大文字小文字はそのまま SHA-256 |
| 名・姓（`first_names_sha256`・`last_names_sha256`） | 小文字にし、空白と ASCII の記号を除く。**ASCII 以外の文字はそのまま**（アクセントを外さない、ローマ字にしない）で SHA-256 |
| 地域・郵便番号・市・国 | ハッシュ化せず、そのままの文字列（国は 2 文字の ISO コード） |
| `obref` | ピクセルの Cookie `__obref` の値を、ハッシュ化せずにそのまま（2026-07-16 追加） |
| IP・ユーザー エージェント | 成果を起こした利用者の端末のもの。ハッシュ化しない |
| Android の広告 ID（GAID） | API だけ。**IDFA は使えない**。全部 0 の ID は無視される |

- 複数形の欄は**各 3 個まで**。超えると 400 エラー（切り詰めない）✅ 本文
- ピクセル側の `user` は `init` に入れる（リクエストの単位）。API 側の `user` は各イベントの中に入れる（イベントの単位）✅ 本文
- **運用の判断への効き方**: 日本語の氏名は、ローマ字にせず漢字・かなのまま小文字化（ASCII 部分だけ）してハッシュ化する、と読める〔推測: 公式の例は欧文だけ。同じ人の氏名を照合側がどう持っているかで一致するかが決まるので、効き目は ❓〕。電話は日本の `090-1234-5678` なら国番号 81 を付けて先頭の 0 を落とす形（`819012345678`）〔推測: 公式の規則をそのまま当てはめた。日本の番号の例は公式に無い〕

### 4-4. アプリのイベント ✅〔公式〕本文（S-01 Supported Events・Conversions API）

- `app_installed`・`app_opened` は**コンバージョン API だけ**（ピクセルでは送れない）。`action_source` は `mobile_app`、データの形は `customer_action`
- 送るときは、既存の**ウェブのデータソースのピクセル ID** を使う。ネイティブのモバイル SDK とモバイル用のデータソースは今は無い
- アプリの成果とモバイル計測の連携は**クリックスルーだけ**（ビュースルーは無い）
- モバイル計測パートナー（AppsFlyer・Adjust・Branch・Singular・Kochava・Airbridge・Tenjin など）と連携 ✅ 本文（K-07、K-08）。各社の設定の手順は ❓（20001372 は未読）

### 4-5. 運用の判断への効き方

- **確定した成果（注文確定・申込みの受付）は API で送る。** ブラウザの離脱・広告ブロック・同意の影響を受けにくい〔推測: 公式の「より確実」の理由づけ〕
- **`oppref` を LP の時点で保存しておく。** フォームの隠し項目やセッションに入れ、注文や申込みのデータと一緒にサーバーへ運ぶ。これが無いと、API の成果はクリックに直接つながらない（詳細マッチングとモデル化だけが頼り）
- **再送は同じ ID・同じ時刻で。** 新しい ID で送り直すと、別の成果に見える ✅ 本文（S-45 20001604）
- **1,000 件まとめて送る設計なら、不正な 1 件で全部落ちることを前提に、失敗したら分けて送り直す処理を入れる**〔推測〕
- **成約まで 7 日を超える商材（不動産・B2B など）は、成約そのものを後から返せない。** 7 日以内に起きる段階（資料請求、来店予約、初回面談の予約など）を成果にする〔推測〕

### 4-6. Google との違い

- Google はクリック ID でクリックから 90 日、個人データ付きで 63 日まで成果を後から取り込める（G24 §5-2）。ChatGPT は**出来事から 7 日**。「月末にまとめて CRM の成約を上げる」運用はできない

## 5. 画像タグ（JavaScript なし）✅〔公式〕本文（S-01 Image Tag）

| 項目 | 決まり |
|---|---|
| 置き方 | 成果のページの `<body>` に 1×1 の隠し画像（`https://bzr.openai.com/v1/sdk/events?pid=…&event=…&data[type]=…`） |
| 送れるもの | 1 回に 1 件。`event_id`・`oppref`・`data[...]` を付けられる。未知の欄は拒否される |
| できないこと | ページを読んだ時点しか測れない（後のクリックやフォーム送信は不可）。まとめて送れない。**`user` を送れない**。`oppref` を自動で拾わない |
| 禁止 | 個人データ・秘密・セッション ID・顧客 ID・**注文 ID** をクエリに入れない |
| ピクセルの予備 | `<noscript>` の中に入れると、JavaScript が無いときだけ動く |
| API と併用 | 画像タグの `event_id` を API の `id` に使い、同じピクセル ID で送る |
| 試し方 | 成功なら `200 image/gif`。これは「受け付けた」までで、後の処理が終わった証拠ではない |

- **運用の判断への効き方**: 画像タグは「サンクス ページを読んだ」だけを測る最後の手段。**注文 ID をイベント ID に使うと「注文 ID をクエリに入れない」に反する**ので、画像タグのイベント ID は別に作った値にする〔推測: 公式の例は `evt_…` 形式のランダムな値〕

## 6. 併用と重複の除外

### 6-1. 決まり ✅〔公式〕本文（S-01 Measurement Pixel・Conversions API・Conversion Tracking、S-45 20001604）

| 条件 | 中身 |
|---|---|
| 鍵 | ピクセル ID ＋ イベント名 ＋ イベント ID（ピクセルは `event_id`、API は `id`、画像タグは `event_id`） |
| カスタム イベント | イベント名の代わりに `custom_event_name` を両方でそろえる |
| どちらを採るか | **先に届いたもの**。後から届いた重複は無視 |
| データソース | 同じウェブサイトなら、ピクセルと API で同じデータソースを使う |
| イベント ID の作り方 | 自分で作る。実際の注文 ID など一意の値。同じ行動の写しには同じ ID、別の行動には別の ID |

### 6-2. 運用の判断への効き方

- **先に届いたほうが採られる**ので、後から送る API の側で金額や照合の情報を直すことはできない。公式ヘルプは「重複を送って元のイベントの値や照合の情報を変えようとしない」と書く ✅ 本文（S-45 20001604）。〔推測〕ピクセルと API で金額を同じにしておかないと、どちらが採られたかで売上がぶれる
- **二重計上の主な原因**（ヘルプが挙げる点検の順）: タグの重複、ページの再読み込み、コールバックの繰り返し、パートナーの連携がすでに同じイベントを送っている（Shopify の連携など）✅ 本文（S-45 20001604）
- **Shopify・HubSpot・計測パートナーを入れる前に、すでに何がどのイベントを送っているかを一覧にする**〔推測〕

### 6-3. Google との違い

- Google は「同じ成果をタグと GA4 の両方でメインにしない」（入札に使う経路を 1 本に）。ChatGPT は「両方送って向こうで 1 件にする」。発想が逆（G24 §2）

## 7. `oppref` とクリックのつながり

### 7-1. 仕組み ✅〔公式〕本文（S-45 20001409 英語版・日本語版、S-01）

- 広告のクリックで、LP の URL の末尾に `?oppref=…` の形で付く（公式の例は `www.openai.com?oppref=gAAAAAb123`）
- 中身は利用者を特定しない参照（公式の言い方は「プライバシーを守る識別子」「不透明な文字列」）。**変えずに**扱う
- ピクセルは拾って Cookie に入れる。API と画像タグは自分で渡す

### 7-2. 落とさないための点検 ✅〔公式〕本文（K-01、S-45 20001409・20001214）

- **リダイレクトと LP の中の移動で保つ**（公式の改善策の筆頭）
- 計測の道具・短縮 URL・リダイレクト・購入手続き・ブラウザとサーバーの受け渡しを含めて、経路の全体を試す
- **他の人のクリックの参照を使い回したり、決まった値で埋めたりしない**
- リダイレクトでパラメータが落ちるなら、リダイレクトか着地 URL の扱いを直す（UTM でも同じ）

### 7-3. トラッキング パラメータ（UTM など）✅〔公式〕本文（S-31、S-45 20001214、S-01 Campaign Management）〔画面〕62 #6

| 項目 | 中身 |
|---|---|
| 固定のパラメータ | UTM などの固定のパラメータは、広告のクリックで保たれる。既存の解析ツールで ChatGPT の広告からの流入を見られる |
| 置き換え（マクロ） | `{campaign_id}`・`{ad_group_id}`・`{ad_id}`・`{ad_account_id}`（ヘルプ）。画面には `{oppref}` もある（62 #6）。開発者文書の例は `click_id={oppref}` |
| 置き場所 | キャンペーン・広告グループ・広告の「ランディングページのクエリパラメータ」。アカウントの既定もある |
| 優先 | ヘルプ: 広告の URL ＞ 広告 ＞ 広告グループ ＞ キャンペーン（広告の URL にすでにあるキーは上書きしない）。開発者文書: アカウント ＜ キャンペーン ＜ 広告グループ ＜ 広告（商品フィードは新しい方式ではフィードが最も低い。旧方式からの移行の期限は 2026-11-05）|
| 公式の例 | `utm_source=openai&utm_medium=paid&utm_campaign={campaign_id}&utm_content={ad_id}` |

- **運用の判断への効き方**:
  - UTM は必ず付ける。GA4 で ChatGPT の広告の流入を分けられる唯一の確実な手〔推測: 付けないと、GA4 では参照元のサイト（chatgpt.com など）からの流入に混ざると考えられる。GA4 での既定の分類は ❓ 公式に記載なし〕
  - `{oppref}` のマクロは、CRM やフォームの道具に別名（例 `click_id`）でクリックの参照を渡したいときに使う〔推測〕。ピクセルは `oppref` という名前の URL パラメータを拾うので、名前を変えた写しだけを残すとピクセルは拾えない〔推測〕
  - 優先の順はヘルプと開発者文書で書き方が違う（ヘルプはアカウントと商品フィードに触れない）△。迷ったら、広告の単位で設定して最終 URL を確かめる〔推測〕

### 7-4. Google との違い

- Google の gclid は自動タグ設定でアカウントの設定として付く。GA4 では自動タグ設定が手動の UTM より優先する（G24 §9）。ChatGPT の `oppref` も OpenAI が付けるが、**GA4 は `oppref` を知らない**ので、GA4 で見るには UTM が要る〔推測〕

## 8. 照合の強化: 詳細マッチング・自動詳細マッチング（AAM）・モデル化

### 8-1. 詳細マッチング（手で送る）✅〔公式〕本文（S-45 20001409、S-01）

- クリックの直接の情報が欠けたときに、正規化してハッシュ化した連絡先などのファースト パーティの情報を成果に添えて、照合を上げる
- ピクセル: `init` の `user` にメール・電話・顧客 ID・名・姓（どれも SHA-256）と国・市・地域・郵便番号（そのまま）。2026-08-19 に電話・氏名・地域・郵便番号が足された
- ログインの後などで情報が後から分かったら、`init` を全部の `user` を付けてもう一度呼ぶ

### 8-2. 自動詳細マッチング（AAM）✅〔公式〕本文（S-45 20001409 英語版・日本語版、S-01、S-37）

| 項目 | 中身 |
|---|---|
| 何をするか | クリックの識別子が無いときに、ピクセルがサイトのフォームなどから顧客情報を自動で見つけ、ブラウザの中で正規化して SHA-256 でハッシュ化し、成果に添える。ハッシュ化する前の情報は送らない。ピクセルの実装を変える必要はない |
| 日本 | **日本以外のウェブのピクセルでは既定でオン。日本の広告アカウントでは、広告主が Ads Manager でオン・オフを選べる**。既存のピクセルは「ピクセルを編集」で選んで「変更を保存」 |
| 日本の既定値 | ❓ 書かれていない（日本語版にも無い） |
| API で作ったピクセル | 開発者文書は「API で作ったウェブのピクセルは自動で AAM を使う」と書く。日本の例外に触れていない △ |
| 公式の勧め | コンバージョン目的のヘルプは「ウェブのピクセルの AAM をオンにすると照合が上がり、最適化の情報が増える」と書く |

- **運用の判断への効き方**:
  - 日本のアカウントでは、**オン・オフを意図して選び、その日付と理由を台帳に残す**。数字の比較で「AAM を変えた日」が境目になる〔推測〕
  - オンにするかは、サイトのプライバシーポリシーでの説明と、外部への送信に関する社内の決まりで決める。公式は「許された情報だけを送り、同意の選択を守る」と書くだけで、日本の法令の当てはめは書かない ❓
  - API で作ったピクセルが日本のアカウントで AAM オンになっているかは、画面の「ピクセルを編集」で確かめる〔推測〕

### 8-3. モデリングによる計測 ✅〔公式〕本文（S-45 20001409）

- 使える場合、OpenAI は観測された成果の集計のパターンから、帰属先が分からない成果の帰属先を推定することがある
- **報告されるコンバージョンの合計に、モデルの推定が含まれることがある**
- どの条件で使われるか、推定の割合を分けて見る列があるかは ❓ 公式に記載なし

### 8-4. Google との違い

- Google の拡張コンバージョンに当たるのが詳細マッチング。違いは、**日本だけ AAM の扱いが違う**こと（Google の拡張コンバージョンの国による既定の差は G24 に記載なし）
- Google の推定コンバージョンは「数字が落ち着くまで最長 5 日」（G06 §5）。ChatGPT のモデル化の確定の時期は ❓

## 9. イベント（標準 12 種とカスタム）

### 9-1. 標準イベント ✅〔公式〕本文（S-01 Supported Events）〔画面〕62 #7

| イベント名 | データの形 | 使う場面 | 送れる道 |
|---|---|---|---|
| `order_created` | `contents` | 購入の完了 | 全部 |
| `lead_created` | `customer_action` | リードのフォーム送信・連絡の依頼 | 全部 |
| `registration_completed` | `customer_action` | アカウントやイベントの登録完了 | 全部 |
| `appointment_scheduled` | `customer_action` | 面談・デモ・相談の予約 | 全部 |
| `items_added` | `contents` | カート・セットへの追加 | 全部 |
| `checkout_started` | `contents` | 購入手続きの開始 | 全部 |
| `contents_viewed` | `contents` | 商品・物件・記事などの閲覧（読み込みの後の操作も） | 全部 |
| `page_viewed` | `contents` | 大事なページの読み込み | 全部 |
| `subscription_created` | `plan_enrollment` | 有料サブスクの開始 | 全部 |
| `trial_started` | `plan_enrollment` | 無料体験の開始 | 全部 |
| `app_installed` | `customer_action` | アプリのインストール | API だけ |
| `app_opened` | `customer_action` | アプリの起動 | API だけ |
| `custom` | `custom` | 上のどれにも当たらない行動 | 全部（`custom_event_name` が必須） |

- 標準は 12 種＋カスタム。画面のレポートの列にも標準イベント 12 種が並ぶ（62 #7）
- 金額（`amount`）を入れたら通貨（`currency`、3 文字の ISO 4217）も必須。`contents[].amount` は 1 個の値段、イベントの `amount` は全体の値段 ✅ 本文
- `group_id` と `variant_dict` は API だけ ✅ 本文

### 9-2. カスタム イベント ✅〔公式〕本文（S-01、S-37）

- 名前は 1〜64 字、英数字・下線・ハイフン、先頭と末尾は英数字、標準イベントの名前と同じにしない。API は小文字にする。小文字で書くよう勧めている
- **コンバージョン最適化の目標にはできない**（計測・レポートだけ）
- 画面の設定は「イベントの種類: カスタム」にし、**送る名前と完全に一致**させる。表示名が同じなだけでは数えない ✅ 本文（S-45 20001214）
- イベントの品質の「イベントの種類の広さ」の点検にはカスタムは入らない ✅ 本文（K-01）

### 9-3. 売上と ROAS ✅〔公式〕本文（S-45 20001214、S-01 Reporting）

- 「注文作成の売上」「注文作成の ROAS」は**帰属した `order_created` だけ**から計算する。ほかの標準・カスタムのイベントの金額は入らない
- 売上は目標の `order_created` と目標でない `order_created` の両方を合わせる（API の `order_created_attributed_sales`）
- `null` は「計算できない」で、0 ではない

### 9-4. 運用の判断への効き方

- **最適化の候補は標準イベントで作る。** 見積もり依頼・来店予約などの独自の行動も、標準の `lead_created`・`appointment_scheduled` に当てはまるなら標準で送る。カスタムにすると最適化に使えない
- **売上を見たいなら購入は必ず `order_created` に値と通貨を付けて送る。** サブスクの売上は「注文作成の ROAS」に入らない〔公式の定義から読める〕
- **画面の CSV のイベント列の名前**は `attributed_event_registration_completed` のような形になる ✅ 本文（S-45 20001214）

### 9-5. Google との違い

- Google はコンバージョン アクションを自由に作り、カウント方法（全件／初回のみ）を選べる（G06 §5）。ChatGPT のカウント方法の設定は ❓ 公式に記載なし。重複の除外はイベント ID で行う

## 10. イベントの品質スコア（EQS）と診断

### 10-1. 中身 ✅〔公式〕本文（K-01、S-45 20001604、K-08）

- 名前: **Event Quality Score（EQS）**。2026-10-05 の公式ブログで紹介（K-08）。ヘルプは「イベントの品質」
- データソース（ピクセル）ごとに評価する
- **完了した 7 暦日分のデータで、毎日更新**（遅れて届くイベントの分の余裕を置く）。直した効果は、古いイベントが窓から抜けるにつれて少しずつ出る
- **点数と警告は「設定のどこを見るか」の手がかりで、成果の予測でも、照合の保証でもない**。低い・出ない＝計測が壊れている、ではない
- 点数の範囲（何点満点か）・良し悪しの目安は ❓ 公式に記載なし
- 点数を上げるために、余分なイベントを送る・識別子を作る・時刻を変えることは禁止

### 10-2. 警告の一覧 ✅〔公式〕本文（K-01）

| 警告 | 意味 | 直し方の要点 |
|---|---|---|
| メール・顧客 ID の情報が少ない | 成果にメールか安定した顧客 ID が少ない | 対応の欄で送る。同じ人には同じ ID。共有の値・仮の値を使わない。ブラウザとサーバーの両方を見る |
| クリックの情報が無い・つながらない | クリック後の成果に、同じクリックにつながる情報が無い | `oppref` をリダイレクトと移動で保つ。API にも渡す |
| コンバージョン API のイベントが遅い | **行動から 1 時間以内に届いたか**を見る | 確定したらすぐ送る。キュー・再送の遅れを見る。再送でも元の時刻を保つ。時刻の単位（ミリ秒）と時計を確かめる |
| 照合の見直しが必要 | 帰属の点検で一部の照合が外された（同じ行動の繰り返し、時刻の食い違い、1 回の表示に多すぎる照合）| 実際の行動の後にだけ送る。重複のタグ・再読み込み・再送を見る |
| 同じ広告の接点に成果が多すぎる | 一部のクリック・表示に成果が集中している（正当な場合もある）| 再読み込みなどで同じ行動を繰り返し送っていないか。正当なら残して説明する |
| 追加の照合情報が少ない | 電話、氏名と地域、IP とユーザー エージェントの組の有無を見る（照合できたかではない）| 電話、名・姓・郵便番号・国をそろえて送る。サーバーは本当の利用者の IP とユーザー エージェントを（サーバーの IP にしない）|
| イベントの種類が少ない | 閲覧・途中の行動・完了の 3 つの段階が少ない（標準イベントだけで見る）| 自社の段階に当てはまるものを送る。架空の段階を作らない |
| ピクセルと API の動きが少ない | 両方の経路で受け付けたイベントが少ない | 両方が届いているか。同じ行動は同じピクセル ID・イベント名・イベント ID |
| 設定した成果の動きが少ない | 付けた成果のどれかのイベントがほぼ無い（広告に照合しなかったイベントも数える）| 名前と設定の一致。古い目標の見直し。本当に少ないなら様子を見る |

- 点数が出ない理由: 成果の設定が無い／成果の量が足りない（0 点とは別）／帰属の証拠が足りない／その点検に要る情報が足りない／処理中 ✅ 本文（K-01）

### 10-3. 運用の判断への効き方

- **立ち上げの 2 週間は、EQS の警告を点検の一覧として使う。** 量の少ないアカウントでは「成果の量が足りない」で点数が出ないのが普通〔推測〕。点数より、警告の中身（とくに「クリックの情報が無い」「API が遅い」）を見る
- **API の送信は 1 時間以内を目標にする。** 夜間にまとめて送る設計は「遅い」の警告になる
- **点数を報告の KPI にしない。** 公式が「成果の予測ではない」と明言している

### 10-4. Google との違い

- Google のタグ診断は「過大計上の可能性（直近 2 日で取引 ID の一致が 10% 未満）」のような具体の基準を持つ（G24 §2・§10）。ChatGPT の EQS は 7 日の窓で毎日更新。基準の数字は「API は 1 時間以内」だけが公開されている

## 11. アトリビューション

### 11-1. 窓と数え方 ✅〔公式〕本文（S-45 20001214 英語版・日本語版、S-01 Reporting・Insights）〔画面〕62 #8

| 設定 | 選べる値 | 既定 |
|---|---|---|
| クリックスルーのレポート期間 | 7・14・30 日 | 30 日 |
| ビュースルーのレポート期間 | 0 日（無効）・1 日 | 1 日 |
| 計上日の基準 | 広告に触れた日（`ad_event_time`）／成果の日（`conversion_time`） | 広告に触れた日 |

- 2 つの窓はそれぞれ別に既定が決まる（クリックの窓を変えてもビューは止まらない）
- **クリックとビューの両方に当てはまる成果は、クリックが手柄を取る**
- ビュースルーは「対象の表示から 1 日以内に成果に至り、その成果に手柄を取れるクリックが無い」ときに数える
- 帰属は**最後の接点（ラストタッチ）**で、**複数の接点への配分（マルチタッチ）ではない**
- 窓の設定は画面の「列を編集」>「コンバージョンイベント」>「アトリビューション期間」。**表示している全部のコンバージョンの列に効く**
- **窓を変えるのはレポートだけ。最適化・入札・課金は変わらない**（ヘルプ、公式ブログの両方）
- 窓が効くのはコンバージョン・売上・CPA・ROAS・クリック後のコンバージョン率。表示・クリック・費用は変わらない ✅ 本文（S-01 Reporting）
- イベント設定の `attribution_window_days` は「30 を使う」とだけ書かれている（設定の側の窓と最適化の関係は ❓）✅ 本文（S-01 Conversion Setup）

### 11-2. ビュースルーの量の目安 ✅〔公式〕本文（K-08）

- OpenAI の初期の分析: 深い段階の成果に最適化した世界のキャンペーンで、**1 日のビュースルーの成果の 52.7% が、照合した表示から 1 時間以内**に起きていた
- 公式の説明: ChatGPT では、作業や判断の途中で広告を見て、すぐには押さずに後で行動することが多い
- 〔推測〕この数字は OpenAI 自身の集計で、業種・国・規模の内訳は無い。自社の数字の見込みには使わない

### 11-3. ビュースルーは「コンバージョン」に入るか（00 §6-3・96 #13・62 #9 の △ の決着）

**結論: レポートの合計には入る（ビューの窓が 1 日なら）。開発者文書のピクセルと API の節の記述が古い。**

| 資料（2026-11-18 に本文で確認） | 書いていること | 判定 |
|---|---|---|
| ヘルプ「Measure Results」20001214（英語版・日本語版とも「23 時間前に更新」） | 「コンバージョン合計には、クリックスルーと対象のビュースルーが含まれる」。FAQ で「含まれますか？ → はい（1 日のとき）。0 日ならクリックだけ」 | 新しい |
| ヘルプ「Troubleshooting conversion tracking」20001604（4 日前） | 「ビューの窓が 1 日なら、コンバージョンはクリックと対象のビューを合わせる」 | 新しい |
| 開発者文書 Reporting・Insights | `conversions` は「選んだ窓の中のクリックとビューの目標の成果」。例: クリック 3 件＋ビュー 2 件＝5 件 | 新しい |
| 開発者文書 Changelog 2026-09-30 | 「成果の合計はクリックスルー＋ビュースルーの目標の成果を含み、以前のレポートと違いうる」。旧来の数え方のモードは無い | 新しい |
| 開発者文書 Measurement Pixel・Conversions API の「Attribution reporting」 | 「ビュースルーは別のキャンペーン単位の指標で、`Conversions` に含まない。CPA・クリック後の CVR・入札・課金・最適化はクリック基準」 | **古い**（2026-11-18 に WebFetch でページ単体も確認したが同じ文のまま） |

- ✅ 判定の理由: 新しいヘルプ 2 本・レポートの開発者文書・変更履歴の 4 つが一致し、日付も新しい。画面でも合計の列とクリックスルー・ビュースルーの列が並んでいる（62 #9）
- △ 残る食い違い: ピクセルの節は「CPA と最適化はクリック基準」と書くが、
  - レポートの CPA は「費用 ÷ コンバージョン」（S-01 Reporting）で、合計にビューが入るので、**レポートの CPA はビュー込み**になる
  - 最適化は**課金の方式で違う**: クリック課金（oCPC）は「クリックの後の成果」に最適化、表示課金（oCPM）は「表示とクリックの両方からの成果」に最適化 ✅ 本文（S-37 20001412）。公式ブログも「高度なコンバージョン最適化は、対象のクリックスルーとビュースルーの成果から学ぶ」と書く ✅ 本文（K-08）
  - したがって 00 §6-3 の〔推測〕「入札と最適化はクリック基準」は、**oCPC についてだけ正しく、oCPM では誤り**
- **運用の判断への効き方**:
  - Google（ビュースルーは別に見る）や GA4（クリック中心）と並べる表では、**ChatGPT をビュー 0 日にそろえる**（00 §6-3 と同じ。理由が「食い違い」から「仕様」に変わった）
  - oCPC と oCPM を比べるときは、ビュー 1 日の合計で比べると oCPM が有利に見える〔推測〕。両方の列（クリックスルー・ビュースルー）を分けて見る
  - API で数字を取る自動化は、**窓を明示して送る**。省略すると「クリック 30 日＋ビュー 1 日＋広告に触れた日」になり、2026-09-30 より前の数字と比べられない ✅ 本文（S-01 Reporting）

### 11-4. Google との違い

- Google はアトリビューション モデル（データドリブン／ラストクリック）を選べ、成果が小数に分かれることがある（G06 §5）。ChatGPT は**ラストタッチだけで、窓もレポート用**。Google の「計測期間を変えると以降の成果に効く」（G06 §5）と違い、ChatGPT の窓は**過去の数字にもさかのぼって見え方を変える**〔推測: レポートの設定として説明されているため。公式に「さかのぼる」とは書かれていない ❓〕

## 12. レポートの指標と遅れ

### 12-1. 指標 ✅〔公式〕本文（S-45 20001214、S-01 Reporting）

| 指標 | 中身 |
|---|---|
| 表示回数・クリック数・費用・CTR・平均 CPC・平均 CPM | 配信と費用。CTR は API では比（0.04＝4%）、費用は通貨の単位（予算のマイクロ単位ではない） |
| コンバージョン | キャンペーンに付けた成果の合計（ビュー 1 日込み、モデル化込みのことがある） |
| CPA | 費用 ÷ コンバージョン |
| クリック後のコンバージョン率 | クリックスルーの成果 ÷ クリック |
| 注文作成の売上・ROAS | 帰属した `order_created` の値 ÷ 費用 |
| リーチ・フリークエンシー | 画面の「視聴者」の列（62 #7） |
| 分け方 | 国・端末・プラットフォーム（API はウェブを パソコン／iOS／Android に分けられる）、商品。画面の「セグメント」は端末・国・プラットフォームで、イベントの列は足さない |

### 12-2. 反映の遅れ ✅〔公式〕本文（S-45 20001214・20001604、S-31、K-06、S-01 Reporting）

| 指標 | 目安 |
|---|---|
| 表示・クリック・CTR | 約 15 分ごと（数分で出ることもある。後で変わりうる） |
| 費用 | 約 7〜8 時間遅れ。**表示の費用が 0 円でも課金が無いとは限らない** |
| 平均 CPC・平均 CPM | 確定した費用に基づくので、さらに後 |
| コンバージョン | 24〜48 時間（ヘルプ）。開発者文書は「少なくとも 1 日」 |
| 新しいキャンペーンで配信が 0 | はっきりした理由が無ければ、開始から少なくとも 24 時間は待ってから問い合わせる |

- 直近のクリックが確定した費用より先に届くので、**最新の費用 ÷ 最新のクリックは、返ってくる CPC と合わない**。返ってくる費用の指標を使う ✅ 本文（S-01）
- 費用の列の見出しにカーソルを当てると、費用のデータがアカウントの時間帯でいつまでかが出る（出ない画面もある）✅ 本文（S-45 20001214）
- 請求の時刻は UTC（62 #12）。〔推測〕請求書と画面の日別の費用は、日の区切りがずれる

### 12-3. 保存期間 ✅〔公式〕本文（S-01 Reporting・Insights）

| 種類 | 遡れる期間 |
|---|---|
| 時間別の配信 | 約 30 日 |
| 時間別以外の配信（商品を除く） | 直近 365 日 |
| 商品のレポート | 約 30 日 |
| コンバージョン専用の API | 1 回 365 日まで。2,000 行を超えると 413 エラー（途中までの結果もページ送りも無い。対象か期間を分けて取り直す） |

- **運用の判断への効き方**: 商品と時間別は 30 日で消える。**月次の報告に使う数字は、毎月 CSV で書き出して手元に残す**〔推測〕

### 12-4. CSV の書き出し ✅〔公式〕本文（S-45 20001214）

- 「現在の表を書き出す」と「選んだ行の累計」は同じ累計の指標、違いは行の範囲。日別は「日別の値を書き出す」
- 選んだイベントの列・ビュースルーの列も CSV に入る

## 13. 数字が合わない理由（GA4・Google 広告・CRM）

### 13-1. 公式が挙げる理由 ✅〔公式〕本文（S-45 20001409・20001214・20001604、K-06）

| 理由 | 中身 |
|---|---|
| 帰属の方法と窓 | ChatGPT はラストタッチ、クリック 30 日＋ビュー 1 日が既定 |
| 時刻・時間帯・日の区切り | 広告に触れた日か成果の日か。アカウントとツールの時間帯 |
| ブラウザ・同意・保存の条件 | Cookie の削除、ブロック、同意の拒否 |
| 重複の扱い | ツールごとに重複の除き方が違う |
| キャンペーン・成果の設定 | 付けた成果、イベントの種類、紐づけの時期 |
| モデル化 | ChatGPT の合計にはモデルの推定が入ることがある |
| 値の違い | 税・送料・割引・手数料、注文全体か品目か、通貨・単位 |
| クリックとセッションの違い | 広告のクリックは広告の操作。解析のセッションは、ページの読み込み・リダイレクト・同意・ブロック・UTM の扱い・窓・時間帯で決まる |

- 公式の言い方: **「差があることは、必ずしもエラーを示さない」** ✅ 本文（S-45 20001409）
- CRM はすべての購入を数え、広告のレポートはその媒体に帰属した購入を数える。媒体ごとに同じ購入の手柄の付け方が違う（例: 広告を押した人が後で直接来て買うと、ある道具は「直接」、別の道具は先の広告の手柄）。それだけで二重計上ではない ✅ 本文（S-45 20001604）

### 13-2. 比べるときの手順 ✅〔公式〕本文（S-45 20001214・20001604）

1. 同じアカウント・キャンペーン・イベント・絞り込み・期間・時間帯・計上日の基準・窓・列にそろえる
2. 加工していない CSV を残す
3. UTM の流入が解析に無いときは、Ads Manager の LP の URL とパラメータを、実際に観測した着地 URL とリダイレクト後の最終 URL と比べる（**この確認のために有料のクリックを新しく起こす必要は無い**）
4. 最終の LP で解析のタグが読み込まれているかを見る
5. 直したら、新しく来た流入で確かめる（過去の欠けは戻らない）

### 13-3. GA4 の接続（ベータ）✅〔公式〕本文（K-02）

| 項目 | 中身 |
|---|---|
| 提供 | ベータ。**担当者に連絡して早期に使う**形（セルフサーブで誰でも使えるとは書かれていない） |
| 権限 | GA4 のプロパティの閲覧者以上の Google アカウント。広告アカウントあたり 1 つの接続、1 つのプロパティ |
| 取り込むもの | 読み取り専用。日付、イベント名と件数、参照元／メディア、キャンペーン名、キーイベントの件数、購入の収益の**集計のレポート**。最初は直近の完了した 30 日分（全流入元）。毎日更新 |
| 使い道 | 帰属の比較、**対象なら**キャンペーンの最適化 |
| 対応づけ | GA4 のイベントを Ads Manager のイベントに対応させる（例 `generate_lead` → リード作成、`page_view` → ページ閲覧） |
| 見え方 | キャンペーンの列に「GA4 コンバージョン」を足せる |
| 注意 | 取り込んだ合計は**プロパティの全流入元の合計で、OpenAI の広告に帰属した成果でも ROAS でもない** |
| 外す | 切断すると新しい取り込みは止まる。取り込み済みのレポートは残る |

- **運用の判断への効き方**:
  - 「GA4 の数字と Ads Manager の数字の差」を見る道具であって、GA4 の成果で入札させる道具ではない。**「最適化に使う」の条件（対象）は ❓ 公式に記載なし**
  - 接続すると、GA4 のプロパティ全体の集計（他媒体の流入元とキャンペーン名を含む）が OpenAI に渡る。社内の取り扱いの決まり・顧客との契約で GA4 のデータを第三者に渡してよいかを先に確かめる〔推測〕。ヘルプは「組織を代表する権限が必要」と書く ✅ 本文（K-02）

### 13-4. GA4 で ChatGPT の広告を見るときの注意〔推測〕

- 公式に書かれているのは「UTM は保たれ、既存の解析で使える」と「審査のクローラーが有料の流入に見えることがある」まで ✅ 本文（S-31）
- 〔推測〕GA4 の参照元／メディアは UTM のとおり（例 `openai / paid`）になる。UTM を付けないと、`chatgpt.com` などからの参照の流入に混ざり、自然の言及（ChatGPT の回答のリンク）と区別できない
- 〔推測〕GA4 の数字は Cookie とセッションの数え方で、ChatGPT の「クリック」より少なくなるのが普通（同意・ブロック・読み込み前の離脱）
- 〔推測〕GA4 にはビュースルーが無いので、ChatGPT のビュー 1 日込みの数字はいつも GA4 より多く見える

### 13-5. Google 広告と並べるとき〔推測〕

| そろえる点 | Google 広告 | ChatGPT の広告 |
|---|---|---|
| 窓 | クリック 30 日が既定（G06 §5） | クリック 30 日が既定。ビューを 0 日に |
| モデル | データドリブン（小数になる） | ラストタッチ |
| 計上日 | クリック日（G06 §5） | 広告に触れた日（既定）|
| 推定 | 推定コンバージョンが入る | モデル化が入ることがある |
| 重複 | 媒体どうしの重複は除かない | 同じ |

- 媒体どうしで同じ申込みを数え合うので、合計が台帳を超えることがある（G26 §2-5 の考え方）。**台帳（CRM）を正とし、媒体の数字は内訳の見積もりとして扱う**

## 14. 審査のクローラーと計測

### 14-1. クローラーの訪問が有料の流入に見える件 ✅〔公式〕本文（S-31、K-06）

- 広告の審査のクローラーが、**トラッキング パラメータ付きで**提出された LP を訪れることがある
- 第三者の解析ツールはそれを有料の流入と分類することがあるが、**課金されるクリックではない**
- 〔推測〕広告を作った・直した直後に、GA4 で UTM 付きの流入が出て、クリック数より多い・すぐ離脱する、という形で現れる。新しい広告の入稿日を台帳に書き、その日の流入を割り引いて読む
- 〔推測〕サーバーのログでは、ユーザー エージェントに `OAI-AdsBot` を含む訪問として分けられる（§14-2）。GA4 がこの訪問を自動で除くかは ❓ 公式に記載なし

### 14-2. OAI-AdsBot と OAI-SearchBot を弾かない設定 ✅〔公式〕本文（S-48 20001243、K-09）

| 項目 | OAI-AdsBot | OAI-SearchBot |
|---|---|---|
| 役割 | 広告として提出されたページの安全性の確認。**広告として提出されたページだけ訪れる**。広告をいつ出すかの判断にページの中身を使うこともある | ChatGPT の検索の結果にサイトを出すため |
| 広告での扱い | **許可が必須**（審査に要る） | 推奨。商品フィードの画像の URL には要る（403 でフィードの処理が止まる） |
| ユーザー エージェント | `… compatible; OAI-AdsBot/1.0; +https://openai.com/adsbot` | `… compatible; OAI-SearchBot/1.4; +https://openai.com/searchbot`（版の番号は変わりうる） |
| IP の一覧 | https://openai.com/adsbot.json | https://openai.com/searchbot.json |
| 学習への利用 | 集めたデータは生成 AI の基盤モデルの学習に使わない | 書かれていない（学習を断る設定は GPTBot で別、各設定は独立）|
| robots.txt | 守るかどうかの記載は無い ❓（ヘルプは robots.txt の確認を手順に入れている） | robots.txt で拒むと ChatGPT の検索の回答に出ない |

**点検の手順**（ヘルプの 5 段、S-48）:

1. 広告に入れる**完全な URL**（トラッキング パラメータ込み）を開き、リダイレクトをたどって最終のページを確かめる。端末や地域で行き先が変わる計測リンクは、それぞれ確かめる
2. robots.txt で OAI-AdsBot（必須）と OAI-SearchBot（推奨）を許す。**リダイレクトの途中のホスト・サブドメイン・外部の行き先も**
3. WAF・CDN・bot 対策が、確認済みの OpenAI のクローラーをログイン・CAPTCHA・ブラウザの確認なしで通すか
4. クローラーが受け取る中身を見る（403・404・429・空白・ログイン画面・確認画面は不可）
5. 直したら、同じ URL とリダイレクトでもう一度試す。状態が変わらなければ再提出

- Cloudflare は OAI-AdsBot を確認済みの bot として許可している ✅ 本文（S-48）
- IP は一覧に頼りきらず、ユーザー エージェント・確認済みの bot の仕組み・許可リスト・robots.txt・提供元の bot 確認を組み合わせる ✅ 本文（S-48）
- 大量の入稿でレート制限（429）が出るなら、小分けにして時間をかけて入稿する ✅ 本文（S-48）
- サポートの手動の回避に頼らない。直しても承認は保証されない ✅ 本文（S-48）

### 14-3. 運用の判断への効き方

- **計測のための計測リンク（短縮 URL・リダイレクト型の計測の道具）を挟むと、クローラーの点検の対象が増え、`oppref` と UTM を落とす点も増える。** ChatGPT の広告では、LP の URL に直接パラメータを付ける形を優先する〔推測〕
- **LPO の道具で出し分けている LP は、クローラーに何が見えるかを確かめる**（96 #17 と同じ。〔推測〕）

## 16. 少額・少量のアカウントでの設計

前提: 日本円の最低の 1 日の予算は 2,500 円（S-34、61 #6）。〔計算〕1 日 2,500 円 × 30.4 日 ≒ 月 76,000 円。仮に CPC 300 円なら月 250 クリック前後、クリック後の CVR 2% なら月 5 件前後（CPC と CVR は仮の数字。公式の日本円の CPC の目安は無い ❓）。

1. **最初の 1 日でやること**: ピクセル（全ページ）＋成果のイベント（購入なら `order_created` に値と通貨）＋UTM（キャンペーン・広告の ID の置き換え）＋OAI-AdsBot の点検。日本のアカウントは AAM のオン・オフを決めて記録〔推測〕
2. **確定した成果は API でも送る**。`oppref` を LP で保存し、イベント ID をピクセルとそろえる
3. **最初の 2 週間で見ること**: ピクセルのテスト、直近 15 分のイベント、EQS の警告（「量が足りない」で点数が出ないのは想定内）
4. **最適化のイベントは件数で選ぶ**。公式は「十分な量のある成果を使う」「まれな成果は評価しにくい」と書く（S-37、S-01）が、件数の基準は ❓ 公式に記載なし。月 5 件では最終の成果の最適化は苦しい〔推測〕。まずクリック目的で始め、成果は計測だけ付ける（61 §4 やれること 3 と同じ）
5. **報告はビュー 0 日の列とビュー 1 日の列の両方を出す**。少額ではビューの数件で CPA が大きく動く〔推測〕
6. **計測を変えた日を台帳に書く**（AAM・API の導入・イベントの差し替え・窓の変更・広告の入稿日〔クローラーの訪問〕）
7. **評価は 2 日遅れで**。費用は 7〜8 時間、成果は 24〜48 時間遅れる

## 17. 判断の型

| 症状・問い | 最初に見るところ | 次の手 |
|---|---|---|
| 成果が 0 のまま | 成果のイベントが送られているか（ネットワーク・コンソール、ピクセルのテスト）| 送られていなければ実装を直す。待っても直らない（S-45 20001604）|
| イベントは届くのに 0 | キャンペーンに付けた設定とイベント名の一致（カスタムは名前の完全一致）、紐づけた時期 | 設定を直し、新しい流入で確かめる。過去は埋まらない（S-45 20001214）|
| 急に成果が倍 | ピクセルと API のイベント ID・名前・ピクセル ID の一致、パートナーの重複、再読み込み | §6。EQS の「照合の見直し」「同じ接点に集中」の警告（K-01）|
| GA4 より大幅に多い | ビューの窓（1 日か 0 日か）、計上日、モデル化 | ビュー 0 日・成果の日にそろえて比べ直す（§11、§13）|
| GA4 で UTM の流入が足りない | 最終 URL に UTM が残っているか（リダイレクト）、解析のタグの読み込み | リダイレクトを直す。新しいクリックを買わずに既存の URL で確かめる（S-45 20001214）|
| GA4 で広告の流入がクリックより多い日がある | その日に広告を作った・直したか（審査のクローラー）| 入稿日の流入を割り引く。サーバーのログで OAI-AdsBot を確かめる（§14-1）|
| 費用が 0 円なのに請求が来た | 費用の反映の遅れ（7〜8 時間）、UTC の請求 | 時間を置いて同じ範囲で比べ直す（K-06）|
| API で 400・全部失敗 | 1 件の不正（7 日より古い時刻、`user` の 4 個以上、金額に通貨が無い）| その 1 件を外して送り直す。同じ ID と時刻で（§4-2）|
| EQS が低い・出ない | 警告の中身。量が足りないだけか | 実際の行動が正しく取れているかを先に。点数を目的にしない（K-01）|
| 成約を最適化に戻したい | 成約までの日数（7 日以内か）| 7 日を超えるなら手前の段階を標準イベントで（§4-5）|
| 「ChatGPT の CPA は Google より安い」と言われた | 両方の窓とビュースルーの扱い | ビュー 0 日・クリック窓をそろえ、台帳の申込み数と照らす。増分は `26` |

## 19. よくある思い込みと実際

| 思い込み | 実際 | 印と出典 | 効く場面 |
|---|---|---|---|
| GA4 のキーイベントを取り込んで最適化できる（Google と同じ） | 成果はピクセルか API で送る。GA4 の接続（ベータ）は集計の比較用で、キャンペーンの成果ではない | ✅ K-02 | 計測の設計 |

| GA4 の有料の流入＝広告のクリック | 審査のクローラーの訪問も有料の流入に見えることがある（課金されない） | ✅ S-31 | 入稿直後の数字 |
| 設定を直せば過去の成果も直る | 紐づけ・設定の修正は先にだけ効く | ✅ S-45 20001214・20001604、S-01 | 計測の修正 |
