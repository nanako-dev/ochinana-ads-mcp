## 0. 先に結論（この章で一番効く 10 点）

1. **国・通貨・時間帯は作った後に変えられない**。別の設定にしたければ別の広告アカウントを作る。日本の法人は「日本・JPY・日本の時間帯」で作る ✅〔仕様〕（S-39、S-38）。セルフサーブを使えるのは「広告を出し請求を受ける法人」が利用可能な国にあるときで、日本は「利用可能」✅（S-32 日本語版、27 days ago の更新）
2. **契約の相手は米国の OpenAI OpCo, LLC、準拠法はカリフォルニア州法**（EEA・スイス・英国以外のすべての顧客）。セルフサーブは所在地に適用される標準の「OpenAI 広告規約」を使い、サポートは**取引先登録の書類・審査票・個別の契約書への署名・条件の交渉をしない** ✅〔仕様〕（T-01 第 12 条の定義、S-39）。日本の会社の稟議・取引先登録は、この前提で組む
3. **名前は 3 つ**（アカウント名＝管理画面の中だけ、ブランド名＝広告に出る名前、法人名＝請求と事業者の確認に使う登記の名前）。最初に入れた 1 つの名前が 3 つ全部に入り、後で「設定 > 一般」で別々に直せる（2026-09-25 から）。**ブランド名の変更はブランド審査が終わるまで配信が止まる。法人名の変更は事業者の審査をやり直し、止まることがある**（ヘルプ）／止まる（開発者文書）で **△** ✅（S-39、S-01）
4. **権限は 5 つ**。テナント（会社の OpenAI の組織）の「global admin」「Ads admin」と、広告アカウントごとの「管理者（Admin）」「メンバー（Member）」「閲覧者（Viewer）」。**ChatGPT のワークスペースや API Platform の組織の役割は、広告の権限にならない**。直接付けた役割とグループで付いた役割のうち**一番高いもの**が効き、各アカウントに**有効な管理者が最低 1 人**残る必要がある ✅〔仕様〕（S-40、29 日前の更新）
5. 自分で作れる広告アカウントは「**所属しているアカウントが 10 未満のとき**」だけ（招待で入ったものも数える）。10 以上でも招待されて入るのは可。追加のアカウントは「条件を満たすセルフサーブの**カード払い**のアカウント」から作る ✅〔仕様〕（S-39、S-56）
6. **事業者の確認は最大 7 営業日**。確認が済む前でも広告は配信され**費用が発生しうる**。支出が一定の額に達すると追加の確認が求められ、承認まで配信が制限されうる。「確認が終わっていないから止まっている」に頼らず、出したくなければ自分でキャンペーンを止める ✅（S-46、24 日前の更新）
7. **請求は後払い**。セルフサーブのカード払いは「支払いの閾値」に達したときと月末に請求される。閾値は自分でもサポートでも変えられず、**閾値以上の請求書の支払いが 2 回続くごと**に上がりうる（例 25 → 50 → 100 → 200 ドル）。支払いが失敗すると配信が止まりうる。**支払っても配信が戻ったとは限らない** ✅〔仕様〕（S-38、12 日前の更新）
8. **日本で請求を受ける広告主に、ChatGPT Ads の請求書では消費税（JCT）を今は課していない**（日本の税番号を入れても入れなくても同じ。OpenAI の他の製品の請求とは扱いが違う）。OpenAI は税の助言をしないので、広告主の側の処理は税理士に確かめる ✅〔仕様〕（S-38）。請求書の請求期間は UTC で、最初と最後の日は 1 日の一部だけのことがある ✅（S-38）
9. **アカウントの費用上限（期間・1 日）は「後払いの請求書払い」のアカウントのもの**。セルフサーブのカード払いには 1 日の上限が無い。カード払いの守りは、キャンペーンの予算と、自分で止めることだけ。**止めても最大 24 時間は広告が出て、その費用は請求される** ✅〔仕様〕（S-01、S-38、S-33）
10. **Ads API キーは 1 本で広告アカウント 1 つに効き、権限の種類を選べない**（作る API の入力は名前だけ）。規約は「API キーで行われたすべての活動に責任を負い、安全かつ機密に保ち、OpenAI の事前の書面の承認なしに広告主その他の第三者と共有・販売・譲渡しない」と定める。漏れたら速やかに OpenAI に知らせる義務がある ✅〔仕様〕（S-01、A-01、T-01 第 1.3・1.4 条）。キーの期限・本数・消し方は公式に記載なし ❓

### 2-2. 国とセルフサーブの可否 ✅〔仕様〕（S-32 日本語版、S-33、S-39）

- セルフサーブの Ads Manager を使うには、**広告を出し、請求を受ける法人**が、提供状況の一覧で「利用可能」の国に拠点を置いている必要がある。日本は「利用可能」（2026-11-24 に日本語版の表で確認。表は国を五十音で並べ、すべて「利用可能」と書く）
- 「アカウントの作成」と「セルフサーブを使えること」は別。一覧に無い国でもアカウントは作れ、使えるようになったら知らせが来る。**作ってもその国が対応するまでは使えない** ✅（S-32、S-33）
- 使い方は 2 つ: ①OpenAI の広告チーム・代理店パートナー・技術パートナーを通じて（新しく対象になった欧州の市場などの案内）②セルフサーブ。大きな広告主は営業の窓口へのフォームがある ✅（S-32）
- 新しいセルフサーブのアカウントは、最初は自国にしか出稿できない場合がある（00§1-2、23§3-3）
- **運用の判断への効き方**: 日本の法人が日本向けに出すなら、自分でセルフサーブを始められる。海外の親会社の名前で日本向けに出すときは、親会社の国で判断される〔推測〕（31§6）。**請求を受ける法人と広告アカウントの国をそろえる**（カードの国も同じにする。§6-5）

### 2-3. 運用の判断への効き方（2 章のまとめ）

- 最初に決めること: ①どの法人が請求を受けるか（＝広告アカウントの国・通貨・時間帯が決まる）②どのメールで登録するか（規約の通知・請求書・領収書が届く）③セルフサーブか営業・代理店経由か（請求書払いと費用上限は営業経由の後払いの請求書払いのもの）〔推測〕

## 3. 器と名前の関係

### 3-1. 何がどこに属すか ✅〔仕様〕（S-40、S-39、S-01）

| 層 | 何か | 管理する場所 | 出典 |
|---|---|---|---|
| OpenAI のアカウント（ログイン） | ChatGPT で使う OpenAI のアカウント。Ads Manager は「ChatGPT で使う OpenAI のアカウント」でログインするか、新しく作る | ads.openai.com の Login／Sign up | S-39 |
| テナント（会社の OpenAI の組織） | ドメイン・ID 基盤（IdP）・ログインの方針・ディレクトリ（SCIM）をまとめる単位。広告だけのテナント（Ads-only tenant）もある | **Admin Console**（admin.openai.com） | S-40、S-56 |
| 広告アカウント（advertiser account／ad account） | キャンペーン・クリエイティブ・フィード・オーディエンス・コンバージョンの計測元を持つ。ブランド名とアイコンで広告主を示す。国・通貨・時間帯・権限・請求を持つ | Ads Manager の「設定」「請求」 | S-01 Account Details、00§2-1 |
| キャンペーン以下 | キャンペーン → 広告グループ → 広告 | Ads Manager | 00§2-1 |

- **ChatGPT のワークスペース（Business・Enterprise）や API Platform（platform.openai.com）の組織は、広告アカウントとは別**。そこでの役割は広告の権限にならず、ワークスペースへの招待も広告アカウントへの招待にならない ✅（S-40）
- テナントに入る、SSO を使う、同期されたディレクトリに載る、のどれも**自動では広告のアクセスにならない**。広告アカウントごとに役割を付ける ✅（S-40）
- 開発者文書: 広告アカウントは「キャンペーン・クリエイティブ素材・フィード・オーディエンス・コンバージョンの計測元を持つ」✅（S-01 Account Details & Branding）

### 3-2. 3 つの名前 ✅〔仕様〕（S-39、16 時間前の更新。S-01 Ad Account）

| 名前 | 何に使うか | 変えたとき | API の欄 |
|---|---|---|---|
| アカウント名（Account Name） | Ads Manager の中で見分けるための名前 | 審査なし。Ads Manager の中だけに効く | `account_name` |
| ブランド名（Brand Name） | ChatGPT で広告と並んで出る公開の名前 | **ブランド審査が始まり、新しい名前が承認されるまで配信が止まる** | `brand_name` |
| 法人名（Legal Name） | 登記上の正式な名前。**請求と事業者の確認に使う** | **事業者の審査をやり直す。配信が止まることがある**（ヘルプ）／**承認まで配信が止まる**（開発者文書）△ | `legal_name`（旧 `name` も同じ値を返す） |

- 登録のときに入れる「広告主名」1 つが 3 つ全部に入る。作った後に「設定 > 一般」で別々に直せる。2026-09-25 から 3 つを別々に管理できるようになり、それ以前に作ったアカウントは 3 つとも同じ名前から始まる ✅（S-39）
- △ **法人名の変更で配信が止まるか**: ヘルプは「Legal Name changes restart business review and may pause ad serving」（止まることがある）、開発者文書（Account Management と Ad Account の両方）は「Changing the legal or public brand name pauses ad delivery until the account passes review」（承認まで止まる）。00§2-1・94#17 はヘルプの側で書いている。**止まる前提で、配信を止めてもよい時期に変える**のが安全〔推測〕
- API の細目 ✅〔仕様〕（S-01 Ad Account）:
  - 名前は前後の空白を除いて **2〜1,000 字**、`<` と `>` は使えない。空・`null` は拒否
  - 旧い `name` の欄は 3 つを同じ値で上書きする。`name` と個別の欄を同時に送ると `422`
  - 設定していないアカウント名・ブランド名は法人名が既定になる
  - 名前の変更（ブランドの更新）はアカウントで**許可されている必要がある**。`403` ならパートナー担当へ
  - `503` が返っても**保存されていることがある**。取り直して値を確かめてから同じ要求を送る
- **運用の判断への効き方**:
  - 法人名は**登記の名前**（例「株式会社〇〇」）を入れる ✅〔公式の推奨〕（S-39「Use your registered business name for Legal Name」）。事業者の確認は法人名と事業・LP の表記の一致を見るので、LP の運営者の表記・特定商取引法の表記と同じ書き方にそろえる〔推測〕（34§1-7）
  - ブランド名は広告で出る名前。**立ち上げ前に決め切る**。配信中に変えると承認まで止まる
  - アカウント名は自由に変えてよい（審査なし）。代理店は「広告主名＋用途」などで見分けやすくする〔推測〕

### 3-3. アイコン（ロゴ）と URL ✅〔仕様〕（S-01、S-50）

- ブランド審査が承認されるまで、アカウントは広告を出せない。`review.reason` が `missing_favicon` なら、アイコンを上げてから有効なキャンペーンを作る ✅（S-01 API Partner Setup）
- △ **アイコンの下限**: 開発者文書の Account Details は「JPEG・PNG・WebP、**256 × 256 画素以上**」、同じ文書の API Partner Setup は「**128 × 128 画素以上**」。94 の「残っていること」に挙がっていた食い違いは、2026-11-24 時点でも同じ文書の中で残っている。**256 × 256 以上で作れば両方を満たす**〔推測〕
- ロゴを差し替えるとブランド審査に入り、**承認まで今の公開のロゴのまま**（プラグインのヘルプ）✅（S-50）
- API でアイコンを上げるときは `purpose=account_favicon`。サイトの URL を渡して API に適当なアイコンを探させることもできる ✅（S-01）。返る `preview_url` はアイコンの下見で、恒久の URL ではない（保存しない）✅（S-01）

### 3-4. 国・通貨・時間帯は固定 ✅〔仕様〕（S-39、S-38、S-01、62#11）

- 国（または地域）・通貨・時間帯は**作った後に変えられない**。別の設定は別の広告アカウント。サポートに頼んでも変わらない ✅（S-38「Contacting Support does not enable a change to the account's fixed country or currency」）
- 1 日のアカウント上限があるあいだは、時間帯は変えられない（そもそも変えられない設定だが、API の文書はこの条件も書く）✅（S-01）
- 画面は日本の時間帯で表示しても、**請求は UTC** 〔画面〕（62#12）。請求書の請求期間も UTC ✅（S-38）

### 3-5. 広告アカウントを増やす ✅〔仕様〕（S-39、S-56、12 日前の更新）

| 決まり | 中身 |
|---|---|
| 作成の上限 | **所属しているアカウントが 10 以上になると、自分では新しく作れない**。数えるのは自分で作ったものと招待で入ったものの両方。「別枠で 10 作れる」のではない |
| 例 | 9 に所属 → あと 1 つ作れる可能性がある。2 つ作って 8 に招待されている（計 10）→ 作れない |
| 招待は別 | 10 以上でも、既存のアカウントの管理者に招待されて入るのは可 |
| 追加の作り方 | 同じログインで Ads Manager に入り、**条件を満たすセルフサーブの「カード払い」のアカウント**を選び、アカウントのメニューの「Create account」（あるとき） |
| 作れる条件 | カード払いのセルフサーブであること、組織の権限、残りの作成枠。**10 未満でも作れるとは限らない** |
| 作った後 | 新しいアカウントも請求・事業者の確認・アカウントの審査をすべて済ませる。**アカウントを増やしても確認・審査・資格の要件は逃れられない** |
| 会社にテナントがあるとき | 作る権限が無いと出たら、IT の担当か管理者に Admin Console（admin.openai.com）で「Ads Admin」の役割を付けてもらう（Users → 利用者 → Direct roles → ＋ → Ads Admin）✅（S-56） |
| サポートに伝えること | ログインのメール、選んでいるアカウントの名前と ID、所属しているアカウントの数（招待を含む）、Create account が無いのかエラーなのか、エラーの文面か画面、日時と時間帯、権限の問題なら設定の流れに出た組織。**パスワード・カードの情報・その他の機密の認証情報は入れない** |

- プラグインからは「自社のための広告アカウントを 1 つ作る」手伝いができる（セルフサーブが使える場合）✅（S-50、69§4）
- **運用の判断への効き方**:
  - 代理店の担当者は、広告主のアカウントに招待されるたびに「所属の数」が増え、**自社の検証用のアカウントを新しく作れなくなる**ことがある。不要になった広告主のアカウントからは外してもらう〔推測〕
  - 1 つの広告主で国・通貨を変えたいときも、別のアカウントを作るしかない（3-4）

### 3-6. 代理店（広告仲介事業者）として扱うとき ✅〔仕様〕（T-01 第 2 条・第 3 条・第 12 条、S-38、S-39）

| 決まり | 中身 | 出典 |
|---|---|---|
| アカウントの持ち方 | 広告主ごとに別のアカウントを作り、同じログインで切り替える | S-39 |
| 代理店の表明 | 広告主のために出稿・管理する権利・権限・同意があること、**出稿の前に**広告主と書面の契約を結び、広告主を広告規約に拘束していること、権限の範囲で行動すること、広告主の規約の遵守と作為・不作為に責任を負うこと。求められたら証拠を出す | T-01 第 2.1 条 |
| 広告主の審査 | 代理店は、合理的な手順で ①広告主の法的な存在と適格性（その国で広告に要る免許・登録）②制裁や政府の制限対象者の一覧に載っていないこと ③法令と OpenAI のポリシーを守っていること、を確かめた広告主だけを紹介・出稿・管理できる。満たさないと知った・疑うときは出稿・管理を続けてはいけない | T-01 第 2.2 条 |
| レポートの共有 | 代理店は、広告主に**その広告主のキャンペーンのレポートだけ**を渡せる。OpenAI が広告主に広告主のレポートを直接渡すこともある | T-01 第 2.1・5.4 条 |
| 代理店の支払い義務 | 代理店の OpenAI への支払いは、広告主からの回収を条件にしない（回収のリスクは代理店） | T-01 第 3.1 条 |
| 請求書の相手（適用対象顧客） | ①広告主が直接なら広告主 ②代理店が**自社の正式な法人名と請求先住所を請求書の受領者として載せる**なら代理店が本人 ③載せないなら代理店は開示代理人で、広告主が相手。請求書の送付や管理だけに使う住所は「請求先住所」に当たらない | T-01 第 12 条 |
| セルフサーブのカード払い | **承認された商用の請求の取り決めが無いセルフサーブのカード払いのアカウント**では、代理店のカードや代理店の請求の担当を使っても、**代理店は請求書の法的な顧客にならない**。既存の請求書の顧客を別の会社に替えたり、既存の請求書を別の会社の名前で出し直したりはできない | S-38 |

- **運用の判断への効き方**:
  - 代理店がカードで立て替える形は、セルフサーブでは**請求書の宛名が広告主のまま**になる。代理店名の請求書が要るなら、営業・パートナーの承認済みの請求の取り決めが要る〔推測: S-38 の書き方から〕
  - 代理店は広告主との書面の契約（広告規約に拘束する内容）と、広告主の確認の記録（法人の存在・免許・制裁の一覧）を**出稿前に**残しておく〔推測: T-01 第 2 条の表明の裏づけ〕

## 4. 権限と招待

### 4-1. 5 つの役割 ✅〔仕様〕（S-40、29 日前の更新。S-39）

| 役割 | 範囲 | できること |
|---|---|---|
| global admin | テナント | テナント全体のドメイン・ID 基盤・ログインの方針・ディレクトリの接続を管理する。条件を満たす広告アカウントを作れる |
| Ads admin | テナント | 条件を満たす広告アカウントを作れる。テナントの ID の管理はしない。**既存の広告アカウントへのアクセスは自動では付かない** |
| ad account admin（管理者） | 1 つの広告アカウント | アカウントと、利用者・グループのアクセスを管理する。「Full access to the platform」（S-39）。**有効な管理者が最低 1 人は残る必要がある** |
| ad account member（メンバー） | 1 つの広告アカウント | 広告の資源を使い・更新する。アカウントの管理の権限は無い。「Create and manage campaigns」（S-39） |
| ad account viewer（閲覧者） | 1 つの広告アカウント | 広告の資源を見る。書き込み・アカウントの管理の権限は無い。「View content only」（S-39） |

- テナントの ID を管理し、アカウントを作り、そのアカウントを管理する人は、**複数の役割が要る**ことがある ✅（S-40）
- 1 つの広告アカウントの中では、**直接付けた役割とグループで付いた役割のうち一番高いもの**（管理者 → メンバー → 閲覧者の順）が効く。**直接の役割を下げても、グループがより高い役割を与えていれば下がらない** ✅（S-40）
- 「メンバーであることは、アカウントの設定を終えるのに要る管理者の役割を持つことにはならない」✅（S-56）。請求・事業者の確認などの設定は管理者が行う〔推測: S-56・S-46「管理者に認証を依頼」の書き方から〕
- ❓ **役割ごとの細目**（メンバーが請求の画面を見られるか、閲覧者が CSV を書き出せるか、API キーを作れる役割、請求の上限を管理する権限〔S-01 は「請求を管理する権限」とだけ書く〕）は公式に表が無い。確かめ方: 管理画面の「設定 > ユーザー」の役割の説明と、テスト用の利用者で見る
- **運用の判断への効き方**: 代理店の運用担当・外注先にはメンバー、レポートを見るだけの社内の人には閲覧者、管理者は社内の 2 人以上〔推測〕（34§6-2 の「管理者を 2 人以上」と同じ考え）

### 4-2. 招待する・役割を変える・外す（2 つの入口）✅〔仕様〕（S-39、S-40、S-56）

| 入口 | 使う場面 | 手順 |
|---|---|---|
| **Ads Manager の「設定 > ユーザー」** | ふつうの招待。会社のテナントの設定が無くても使える | 「Invite」→ ログインに使うメールを入れる → 役割（管理者・メンバー・閲覧者）を選ぶ（S-39）。管理者の役割を付け替えるのも「ユーザー」タブ（S-56） |
| **Admin Console（admin.openai.com）** | 会社のテナントで、SSO・SCIM・グループで管理するとき | テナントを選ぶ → 広告アカウントを選ぶ → 「Users & groups」→ 利用者か、そのアカウント用のグループを探す → 役割を付ける → 本人にテナントに紐づく**仕事のメール**でログインしてもらう（S-40） |
| ChatGPT の中のプラグイン | 自然な文で一覧・招待・役割の変更・削除 | 利用者と招待中の一覧、招待、役割の変更、利用者の削除。変更の前に確認が出る（S-50、69§4） |

- 役割は**広告アカウントごとに別々に**付ける ✅（S-40）
- 本人が見つからないときは、権限のある管理者が招待したか、同期したかを確かめる。**ChatGPT のワークスペースへの招待は広告アカウントへのアクセスにならない** ✅（S-40）
- 招待されたメールと違うメールでログインすると入れない。**招待を受けたメールで入る** ✅（S-56）
- **外すときの順** ✅〔公式の推奨〕（S-40）:
  1. その人が唯一の有効な管理者なら、**先に別の管理者を付ける**（最低 1 人は必要）
  2. 広告アカウントの「Users & groups」で、その人の直接の役割とアカウント用のグループの割り当てを見る
  3. 直接の役割を外す・変えるか、グループの所属を直す
  4. 同期しているグループなら、ID 基盤の側で所属を直す
  5. 別の管理者が残っていること、その人に残るアクセスが意図どおりかを確かめる
- 「1 つのアクセスの道を外しても、別の道が残っていることがある」。SCIM で管理する利用者は直接の役割と同期グループの両方、手で管理する利用者は直接の役割と手で管理するグループの両方を見る ✅（S-40）

### 4-3. 会社のテナントで管理する（SSO と SCIM）✅〔仕様〕（S-40）

- **ログインの方針**: Admin Console → Global settings → Access で、広告（Ads）の SSO の設定を見る。**共有の ID 基盤の接続や他の製品の SSO を有効にしても、広告の SSO は自動では有効にならない**

| 方針 | 意味 |
|---|---|
| Required | SSO がログインの手段として使える。ただし、**すでにログインしている人は、SSO でログインし直さずに Required のアカウントに入れることがある** |
| Optional | 条件を満たす利用者は、設定した ID 基盤か、他の許可されたログインの手段を使える |
| Off | その製品・資源では SSO を使えない。他の許可された手段でログインする |

- 〔公式の推奨〕試すあいだは Optional のままにする。Required や Off にする前に、利用者が入れることと、権限のある管理者に**回復の道**があることを確かめる
- **多要素認証（MFA）と条件付きアクセス**は、自社の **ID 基盤の側**で設定する ✅
- **SCIM（ディレクトリの同期）**: 広告アカウントは**テナント全体の SCIM ディレクトリ**を使う（アカウントごとのディレクトリではない）。広告だけのテナントを含め、条件を満たすテナントは利用者とグループを同期できるが、**各広告アカウントへのアクセスは別に付ける**
  - 同期した利用者を、Admin Console で手で広告アカウントのグループに足したり、同期グループの所属を変えたりはできない（ID 基盤の側で管理する）
  - 同期グループに広告アカウントのアクセスを付けるには、グループの「Product access」で広告アカウントを選んで保存。**最初の役割はメンバー**。管理者は ID 基盤の所属を変えずに、そのグループの役割を変えられる
  - SCIM は、現在と新しいメールのドメインがどちらもテナントで確認済みなら、同期した利用者の主たるメールを既存の OpenAI のアカウントのまま更新できる。**更新するとその人はログアウトされ**、新しいメールで入り直す
- **Ads admin の付け方**: Admin Console → 対象のテナント → Global settings → Users & groups → Users → 利用者のプロフィール → 「Access & roles」か「Direct roles」→ テナントの単位のアクセスを足す（製品を聞かれたら Cloud Console）→ Ads Admin を選んで保存。広告アカウントがまだ無ければ、global admin か Ads admin が最初のアカウントを作る（アカウントの単位の役割はアカウントができるまで出ないことがある）
- **運用の判断への効き方**: 会社に ID 基盤があり、社員の入退社を ID 基盤で管理しているなら、SSO と SCIM で広告のアクセスもそこに寄せると、退職者の外し漏れが減る〔推測〕。ただし Required でも「ログイン済みの人は SSO を通らずに入れることがある」ので、**退職時は ID 基盤の停止に加え、広告アカウントの役割も外す**〔推測: S-40 の Required の注記から〕

### 4-4. 入れないとき・アクセスを失ったとき ✅〔公式の推奨〕（S-56、S-40）

- 入れないときの確認の順: ①選んでいるテナントと広告アカウント ②仕事のメールと広告のログインの方針 ③正しい招待を受けたか ④アカウントの役割（直接・グループ）⑤最近のディレクトリの変更・ID 基盤の割り当て ⑥最初の広告アカウントを global admin か Ads admin が作る必要があるか（S-40）
- **キャンペーンが動いている最中にアクセスを失ったとき**（「Your saved ad account is no longer available」やアクセスの権限のエラー）（S-56、12 日前の更新）:
  1. 使うつもりのメールでログインしているか、正しいアカウントを選んでいるか、そのメールで招待を受けたかを確かめる
  2. 別の権限のある管理者が入れるなら、アクセスを確かめてもらう。配信を止めたいなら、入れる人にキャンペーンを止めてもらう
  3. **アクセスのエラーでキャンペーンが止まったと思わない**（配信は続いているかもしれない）
  4. 誰も入れないなら、すぐに ads-support@openai.com かヘルプの右下の窓へ。「アクセスがふさがれていて、キャンペーンが配信中かもしれない」と書き、止めたいならキャンペーンを名指しして**はっきり停止を頼む**。**問い合わせただけでは停止の確認にならない**
  5. 伝えること: ログインのメール、広告アカウントの名前と ID、対象のキャンペーンの名前か ID、エラーの文面か画面、日時と時間帯、別の管理者が入れるか、最近のワークスペース・アカウントの変更。パスワード・カードの情報は入れない
- **運用の判断への効き方**: 誰も入れなくなる事態は「管理者 1 人」で起きる。管理者を 2 人以上、別々の人（同じ人の別メールではなく）に〔推測〕。止めたいときの連絡の文面（アカウント ID・キャンペーン ID・「停止を依頼」）を手順書に置いておく〔推測〕

## 5. 事業者の確認・ブランド審査・アカウントの審査・ドメインの承認

審査の層の全体と直し方は 34§1・§5。ここでは**アカウントの側の確認**だけを並べる。

### 5-1. 4 つの確認は別々 ✅〔仕様〕（S-46、24 日前の更新。S-01）

| 確認 | 何を見るか | どこに出るか | 出典 |
|---|---|---|---|
| 事業者の確認（business verification） | 事業者の身元・所有者・提携関係の正確さ。法人名を使う | Ads Manager の表示（バナー・確認の画面） | S-46、S-39、S-33 |
| ブランド審査（brand review） | ブランド名・アイコン・URL | API の `review.status`・`review.reason` | S-01 |
| アカウントの審査（account integrity review） | アカウントの健全性 | API の `account_integrity_review.review.status`（**返らないことがあり、返らないことを承認とも却下とも読まない**） | S-01 |
| ドメインの承認 | 広告主の身元と、示したドメインが合っているか | 不承認は理由と次の手を書いた**メール** | S-46 |

- 「アカウントの確認、アカウントの承認、広告の審査、広告の配信は別々の確認で、1 つが済んでも他が済んだことにはならない」✅（S-46）
- 開発者文書: 「有効（active）でブランドが承認済みのアカウントでも、別のアカウントの審査、使い切った費用の上限、キャンペーンの単位の配信の問題が残りうる」✅（S-01）
- 広告ポリシー（v1.7）: 広告主が登録するとき、正当な事業者か・資格要件を満たすか・安全に参加できるかを評価し、**広告主の認証、アカウントの品質の評価、詐欺・不正・悪用・欺瞞のリスクの兆候の分析**を含むことがある。制限の区分（例 金融）では**身元の確認の強化や手動の審査**が要ることがある ✅（S-19 日本語版、Updated 2026-11-20）

### 5-2. 事業者の確認の状態と次の手 ✅〔仕様〕（S-46）

| 状態 | 意味 | 次の手 |
|---|---|---|
| 失敗 | 事業者の身元・所有者・提携関係の正確さを確かめられなかった | アカウント・広告・LP が、事業と他の個人・組織・ブランドとの関係を正確に示しているか直す |
| 進行中 | まだ最終の結果が出ていない。**待ちの確認も含み、いつも審査が進んでいるとは限らない**。Ads Manager は、ページが見えているときと、タブに戻ったときに結果を確かめ直す | **最大 7 営業日**。過ぎたらサポート |
| 未開始 | 確認の画面が開かない | 正しいアカウントで再読み込みか再ログイン（新しいブラウザで）。だめならサポート（アカウント ID、押したボタンかリンク、エラーの文面か画面、日時と時間帯、エラーの前に確認の画面が開いたか）。**本人確認の書類・パスワード・支払い情報は送らない** |
| 確認のせいで広告を保存できない | 確認が要るセルフサーブのアカウントで、**別のドメインを広告のリンク先にする**と、先に確認の承認が要ることがある | 管理者に頼むよう出たら管理者が確認を済ませる。「Try again」は**確認の試行の回数を使いうる**。「保存」を押すだけでは再試行にならない |

- **確認の前の配信と費用**: 一部のアカウントは、追加の確認が要る前に配信を始められる（広告の承認、請求、アカウントの準備、キャンペーンの状態・予算・期間がそろえば）。**この期間にも費用が発生しうる**。支出が一定の額に達すると追加の確認が要ることがあり、その基準額は**変わりうる**。基準額は予算とも、カードに請求する時期を決める「支払いの閾値」とも別で、**無料の広告クレジットではない** ✅（S-46）
- 〔公式の推奨〕確認が済んでいないことで止まっていると思わない。出す準備ができていなければキャンペーンを一時停止して状態を確かめ、予算と期間で費用を管理する。確認を求められたら案内に従う（承認まで配信が制限されうる）✅（S-46）
- 画面の表示〔画面〕: 「この確認が未完了でも、広告配信を開始できます。後で配信が停止されないよう、今すぐ認証手続きを完了してください」（62#13）
- ❓ 確認で求められる書類（日本の登記事項証明書・法人番号など）の具体は公式に記載なし。開発者文書・00§7-1 は「法人名・登録住所・必要なら登録番号」まで

### 5-3. 業種が対象外・ドメインの不承認 ✅〔仕様〕（S-46）

- 業種が対象外: 広告ポリシーがその業種・サービスの広告を今は禁じている。**登録や免許のある事業でも、すべての広告の区分・市場で自動的に出せるわけではない**。広告主アカウントの判断が誤りと考えるなら、**判断を知らせるメールの中の異議のリンク**から。見つからない・開けないならサポート
- ドメインの不承認: 広告主の身元と示したドメインが合うことを確かめられなかった。理由と次の手を書いたメールが届く。誤りと考えるならメールのリンクから異議
- 区分と国の表は 34§2-3・31§2-2。日本は「その他すべての国」の列

### 5-4. 運用の判断への効き方

- 出稿の**前に**、法人名（登記）・ブランド名・LP の運営者の表記・広告のリンク先のドメインをそろえる。リンク先を別のドメインにする予定があるなら、確認の承認を先に済ませる〔推測: S-46 の「別のドメインで保存できない」から〕
- 確認の「Try again」は回数を使う。**原因を直してから**押す〔推測〕
- 確認の結果を待つあいだに費用が出るのは仕様。少額で試すなら、キャンペーンの予算と期間で上限を決めておく（カード払いではアカウントの上限が使えない。§7）

## 6. 請求・支払い・消費税・請求書

### 6-1. 配信の前に済ませる設定 ✅〔仕様〕（S-38、12 日前の更新。S-39、S-56）

- **請求の設定が済むまで、キャンペーンは配信されない**
- セルフサーブのカード払いは 2 段: ①**請求のプロフィール**（会社名・会社の住所・請求書の送付先のメール。このメールは請求書と請求の連絡に使う）②**支払い方法**（クレジットカードと請求先の住所）
- 請求書払いの顧客（営業経由）は住所が 2 つ: **請求先（bill-to）**＝請求書を受け取る会社、**購入者（sold-to）**＝広告アカウントを持ち契約に名前のある法人。同じなら「Same as billing address」のまま。請求書の送付先のメールに加え、写しを受け取るメールを**カンマ区切り**で足せ、任意で**注文番号（PO）**を請求書に載せられる ✅（S-39）
- カードを足すと、支払い方法を確かめる**一時的な与信の確保**がかかることがある。金額は国で違い、広告アカウントの請求の通貨で求める（設定の画面か請求の画面に予定額が出る）。銀行はカードの通貨で同じ額を見せることがある。**広告の請求ではなく**、確認後に自動で解除されるが、銀行によっては **8 日以上**見えたままのことがある ✅（S-38）
- 「請求 > アクティビティ」に「Authorization hold」の記録が出る。状態は Active（保留中）・Canceled／Expired（終了。銀行の解除に時間がかかることがある）・Captured（回収された。対応する支払いと請求書を見る）・Status unavailable。古い与信は出ないことがある ✅（S-38）

### 6-2. いつ請求されるか（後払いと支払いの閾値）✅〔仕様〕（S-38）

- 今は**後払い**（配信の後に請求）。セルフサーブのカード払いは、保存した支払い方法に請求する。**営業が管理する後払いの請求書の条件の広告主は、その請求書の取り決めに従う**（閾値の請求ではない）
- **支払いの閾値**: セルフサーブのカード払いのアカウントは、登録のときに閾値が割り当てられ、未払いの費用が閾値に達すると請求される。月末に残高があれば、閾値に達していなくても**月末に請求**。支払いのたびに**領収書のメール**が届く
- 閾値は予算でも、アカウントの費用上限でもない。**自分で変えられず、サポートも変えない**。支払いの実績などで自動で上がりうる
- 上がり方（今の既定）: **閾値以上（税抜き）の請求書の支払いが 2 回成功するごと**に上がりうる。米ドルの例 ― 25 ドル × 2 回 → 50 ドル × 2 回 → 100 ドル × 2 回 → 200 ドル。閾値と条件はアカウントと通貨で違い、保証ではない。**税が乗るとカードへの請求は閾値を超えうる**。支払いの失敗・異議・チャージバックは上がるのを止めうる
- 同じ額の請求が 2 回あっても重複とは限らない（閾値ごとに別の請求書が出る）
- 費用の数字は 7〜8 時間遅れうる。**費用が 0 や遅れて見えても、費用が発生していないとは限らない**（表示・クリック・CTR は約 15 分ごと）✅（S-38、S-54）
- ❓ **日本円の閾値の初期値と上がり方**は記載なし（例は米ドルだけ）。確かめ方: 「請求 > 概要」と請求書の額

### 6-3. 支払いが失敗したとき ✅〔仕様〕（S-38、S-56）

1. セルフサーブのカード払いで、閾値に達した後の支払いが失敗すると、**問題が解決するまで配信が止まりうる**。失敗はメールで届く。キャンペーン・広告グループ・広告が「Not serving」になり、状態の吹き出しに理由が出る
2. 対象の広告アカウントを選び、「請求」で未払いの請求書と支払いの状態を見る。支払い方法を変えるなら「請求の設定」で
3. **支払い方法を保存しただけでは、未払いの請求書が支払われたことにならない**。請求書が「支払い済み」になったかを確かめる
4. 支払った後に、キャンペーン・広告グループ・広告の状態をもう一度見る。**支払いが成功しても配信が戻ったとは限らない**（アカウント・請求・ポリシー・キャンペーンの他の要件が残りうる）
5. 解決しなければ ads-support@openai.com へ: 広告アカウント ID、請求書 ID（あれば）、エラーの文面、起きた時刻、伏せ字にした画面。**カードの番号の全体やセキュリティ コードは送らない**。カードが断られ続けるならカードの発行会社へ
- インドには PayNow（請求書を Ads Manager で直接払う）があるが、日本には記載なし ✅（S-38 はインドの広告主に限って書く）

### 6-4. 請求書に載せるもの・請求書の読み方 ✅〔仕様〕（S-38、S-39）

| 項目 | 中身 |
|---|---|
| 税番号（VAT・税の ID） | 「請求 > 設定」→ 請求のプロフィールの「Edit」（アカウントによっては「支払い方法 > Edit」の画面）→ 税の ID の種類を選んで番号を入れる。**使える種類は請求の国で決まる**。**これからの請求書にだけ効き、出た請求書は直らない** |
| 請求書の送付先 | 請求のプロフィールの請求書の送付先のメール。請求書払いは写しのメールを複数（カンマ区切り）と PO 番号 |
| 請求期間 | セルフサーブの閾値の請求書は、フッターにおおよその請求期間を載せる。**日付は UTC**で、最初と最後の日は 1 日の一部だけのことがある。キャンペーンごとの突き合わせには使えない |
| 突き合わせ | フッターの期間を起点に、Ads Manager のレポートの時間帯と日付を見る。日単位のレポートは請求書の端の時間を含むことがある |
| 請求の数字が違うと思ったら | 請求書 ID か請求 ID、対象の期間、額、対象のキャンペーン ID、レポートの画面か書き出しをそろえてサポートへ |

- ❓ 日本の**適格請求書（インボイス制度）**の登録番号の記載、請求書の書式・言語は、公式に記載なし（JCT を課していないので記載が無いのは自然〔推測〕）。確かめ方: 「請求 > 書類」の請求書を開いて見る〔画面〕（62#16 に「請求（概要・アクティビティ・書類・設定）」のメニュー）

### 6-5. カード・法人・代理店の制約 ✅〔仕様〕（S-38）

- **請求の情報と支払い方法は、Ads Manager のアカウントを作ったときの法人と国にそろえる**。例: 米国の事業のアカウントなら米国の請求先住所と支払い方法。**別の国のカードは受け付けられないことがある**
- 請求の情報が誤っている、別の法人で請求を受けたい: **同じ事業の情報の訂正**と、**アカウントの責任を負う法人の変更**は別の話。サポートに広告アカウント ID・今の情報・求める訂正か変更・理由を伝える。サポートは次の手を案内するが、国・通貨は変わらない
- 代理店のカード・代理店の請求の担当: 3-6 の表の最後の行（セルフサーブのカード払いでは、代理店は請求書の法的な顧客にならない。既存の請求書を別の会社の名前で出し直せない）
- 支払い方法を消したい: 自分で消せない場合は、残高を片づけ、続けたくないキャンペーンを止め・終え、**アカウントの停止（deactivation）や支払い方法の相談はサポートへ**（広告アカウント ID と請求の情報）

### 6-6. 日本の消費税（JCT）✅〔仕様〕（S-38）・❓

- ✅ 「OpenAI は、日本で請求を受ける広告主の ChatGPT Ads の請求書に、**今は日本の消費税（JCT）を課していない**。日本の税番号を出しても出さなくても同じ」。この扱いは ChatGPT Ads に固有で、OpenAI の請求書の消費税の一般の案内とは違うことがある
- ✅ 「OpenAI は税の助言をできない。JCT や事業に適用される税の義務は税の専門家に相談する」
- ✅ 規約: 料金には税を含まない。OpenAI は**法で義務づけられる場合**に取引税（売上税・付加価値税・デジタルサービス税など）を請求・徴収・納付する。免税は有効な証明書を受け取った後、将来に向かってだけ効く。支払いは控除・源泉徴収なしで行い、法で控除・源泉が要る場合は OpenAI が全額を受け取れるよう上乗せして払う（T-01 第 3.3 条）。管理画面などへのアクセスは広告サービスに付随するもので、ソフトウェアの購入・ライセンスではない（同）
- ✅ 代理店が広告主に請求する分の税は、代理店が単独で責任を負う（T-01 第 3.3 条）。開示代理人として広告主の税番号を出すときは、正式な法人名・請求先住所・税番号の正確さを表明する（第 3.4 条）
- ❓ **広告主の側の消費税の処理**（国外の事業者から受ける役務としての扱い、仕入税額控除・申告での扱い）は公式に記載なし。「今は課していない」は将来変わりうる。**経理・税理士に、契約の相手が米国の OpenAI OpCo, LLC であること（§2-1）と、請求書に JCT が載っていないことを伝えて確かめる**〔推測〕
- **運用の判断への効き方**: Google（10% が乗る）と同じ予算の組み方をすると、請求の額の感覚がずれる。社内の予算表では「ChatGPT は請求書の額＝税抜きの費用（JCT なし）」と注記し、税の処理は税理士の判断を待つ〔推測〕

### 6-7. 返金・料金の異議・遅延 ✅〔仕様〕（S-38、T-01 第 3 条）

| 場面 | 決まり | 出典 |
|---|---|---|
| 返金 | 配信済みの有効な費用は**原則として返金の対象外**。気が変わった、はっきり示された正確な配信開始・請求の案内を見落とした、成果が期待より少なかった、はそれだけでは返金の理由にならない | S-38 |
| 技術の問題・誤った請求・**不正な操作** | 証拠があればサポートへ。サポートは請求と配信の記録と証拠を調べる。**配信されたことだけでは、争う操作が承認されていたことにも、請求が正しいことにもならない**。返金できるかは調査の結果と方針による。根本の原因を特定しなくても報告できる | S-38 |
| サポートに伝えること | 広告アカウント ID、関係する請求書・請求の ID、対象のキャンペーン ID、日付と時刻（時間帯つき）、争う額と通貨、画面や記録。**カードの情報の全体・パスワードは入れない** | S-38 |
| 規約の異議の期限 | 料金に異議を出すときは、**対象の行為が起きた日から 30 日以内**に通知する。調整は OpenAI の裁量で、**譲渡できない補償措置かクレジットの形だけ**（アカウントを閉じる前に使う） | T-01 第 3.2 条 |
| 支払いの遅れ | 異議の無い額の支払いが遅れると、未払い残高に**月 1.5% の金融手数料**がかかることがある | T-01 第 3.1 条 |
| 料金の決め方 | 指標に基づく料金は **OpenAI の測定値・データ**で決まる。価格の誤りの訂正の調整も払う | T-01 第 3.1 条 |
| 無効なクリック | OpenAI は、表示・クリックなどが人によるもので有効で不正でないことを**保証しない**。自動化などで無効なクリック・表示を生むことは広告主に禁止 | T-01 第 8.3 条・第 1.2 条 |

## 7. 費用の上限（アカウントの単位）

キャンペーンの予算（1 日の予算＝7 日の平均、1 日 2 倍・週 7 倍）は 02§7。ここはアカウント全体の上限だけ。

### 7-1. 種類と使えるアカウント ✅〔仕様〕（S-01 Ad Account・Account Management、S-38、S-33）

| 上限 | 中身 | 使えるアカウント |
|---|---|---|
| 期間の上限（date range limit・spend-limit window） | 決めた期間のアカウント全体の総額 | △ 開発者文書の Account Management は「**一部のアカウントだけ**」、同じ文書の Ad Account の参照は「アカウントの費用上限は**後払いの請求書払いのアカウントだけ**」と書く。ヘルプは請求書払いのアカウントに「既存の Date range の選択肢と並んで」1 日の上限がある、と書く |
| 1 日の上限（daily limit。2026-09-09 追加） | 毎日アカウントの時間帯の 0 時に戻る、キャンペーンで共有する 1 日の枠。終わりの日は任意 | **後払いの請求書払いの、条件を満たすアカウントだけ**。「**セルフサーブのカード払いの広告主には使えない**」（S-38）。画面は「請求 > Account limits」 |

- 請求書払いのアカウントが他の請求に変わっても、既存の 1 日の上限は見る・消すことはできる ✅（S-01）
- **この節の呼び出しは、読むだけでも「アカウントの請求を管理する権限」が要る** ✅（S-01）。65§2-2 と同じ

### 7-2. 決まりの細目 ✅〔仕様〕（S-01）

- 額はアカウントの通貨、マイクロの単位の 0 以上の整数（`100000000` が 100 通貨単位）。最大 10 億通貨単位
- 日付は `YYYY-MM-DD`。開始日の 0 時から終了日の 0 時まで（アカウントの時間帯）。**終了日は含まない**
- 1 日の上限と期間の上限は**重ねられない**。予定の期間の上限は最大 **60 件**先まで。名前・IO 番号は各 256 字まで
- 1 日の上限は**翌日以降**から始まる（今日は不可）。繰り越さず、夏時間でも変わらない
- **上限は課金の対象の広告費に効き、税や請求書の総額には効かない**
- **上限に達してから配信が止まるまで時間がかかることがある**
- 額の変更は保存で効く。すでに使った額より下げるのは拒否（`422`・`budget_window_amount_below_spend`）。**遡らない**（遅れて来る請求は、その出来事が起きたときの上限で数える）。同時の請求で保存中に費用が足されることがある。**下げても請求済みの費用は戻らない**
- 使い切った期間の上限を消す・上げると、他の要件が無ければ配信が再開しうる。期間の上限を消しても、アカウントの他の上限は消えない
- アカウントの上限は**キャンペーンに予算を配らない・配信の速さを調整しない**。キャンペーンに予算が残っていても、アカウントの上限を使い切れば止まる。逆に上限を消してもキャンペーンの予算は残る

### 7-3. 止めても費用が出る時間 ✅〔仕様〕（S-38、T-01 第 9.1 条）

- キャンペーンを止めても、配信の仕組みに反映するまで時間がかかり、**最大 24 時間は広告が出ることがある**。その間の費用は請求の対象。止めた後・終えた後も、レポートと請求は前の配信を反映して更新されうる（ただし予算の上限は超えない）✅（S-38）
- 規約: キャンペーンの取り消し・変更は、効くまで**最長 1 営業日**かかることがあり、効く前の料金は払う ✅（T-01 第 9.1 条）
- **アカウント全体を止める**: API の `POST /ad_account/pause`（すべてのキャンペーンの配信を止める）と `POST /ad_account/activate`。止めても子のキャンペーンなどの状態の値は書き換わらない。再開しても、すべてのキャンペーンが有効になる・広告が承認される・予算に余地がある、とは限らない ✅（S-01）。管理画面でアカウント全体を止めるボタンは ❓（記載なし）

### 7-4. 運用の判断への効き方

- **カード払いのセルフサーブの守りは 3 つだけ**: キャンペーンの予算（1 日の予算は 1 日 2 倍まで出る）、期間（終了日）、自分で止めること〔推測: 7-1 の使える範囲から〕。少額で試すなら、**通期予算（キャンペーンの総額）**で上限を固定するのが分かりやすい（02§7）〔推測〕
- 「月の上限」を守りたい会社は、請求書払い（営業経由）に移れるかを営業に聞く〔推測〕
- 止めた直後の 24 時間の費用を見込んで、予算の残りに余裕を持つ〔推測〕

  - キーは**管理者が作り、作った人の手元のファイルに置く**（チャットに貼らない、フォルダや git に置かない）。運用 MCP は読むだけの呼び出しに絞る（65§2・§6）
  - キーを外注先・代理店のツールに渡す前に、①規約の第 1.4 条の承認が要るか ②代わりに外注先を「メンバー」で招いて画面で作業してもらえないか、を考える〔推測〕
  - 漏れた疑いがあれば、①そのキーを消す（手順は ❓。画面の API キーの一覧で消せるかを確かめる）②監査ログで不審な変更を見る（§10）③ads-support@openai.com に知らせる（規約の義務）〔推測: 消し方は記載なし〕

### 9-3. 呼び出しの上限と安全 ✅〔仕様〕（S-01）

- 端点ごとに毎分 600、全体で毎分 1,200。広告アカウントと IP の両方の単位。一括のジョブの作成は 1 アカウント 10 秒に 10 回
- API で作るキャンペーン等は停止の状態で作り、子の資源をそろえて確かめてから有効にするのが公式の手順（パートナーの手順は「`paused` で作る」と明記）✅（S-01 API Partner Setup）

## 10. 変更の追跡（誰がいつ何を変えたか）

### 10-1. 画面と API ✅〔仕様〕（S-01、S-54、62#16、S-50、A-02）

- ❓ **監査ログ・画面の変更履歴の保存期間**、`actor_type` の値の一覧（例に出る `sofa` の意味）、OpenAI の自動の機能（クリエイティブの強化など）による変更が記録されるか、は記載なし

### 10-2. 運用の判断への効き方

- 保存期間が分からないので、**監査ログを毎日手元に写す**〔推測〕（65§6-4 の `chatgpt_get_change_history` の案）
- 一括の編集は**最新の書き出しから**始める。他の人が変えた後の古いファイルで上書きしない ✅〔公式の推奨〕（h20001215「Start from a fresh export whenever possible, especially if other users may have changed the account」）

## 15. 判断の型・少額のアカウントでの注意

### 15-1. 判断の型〔推測。根拠は各章〕

| 場面 | 判断 |
|---|---|
| どの法人で作るか | 請求を受ける法人＝広告アカウントの国・通貨。カードの国も同じに（§2-2・§6-5） |
| 誰を管理者に | 社内の 2 人以上。外注先・代理店はメンバー、見るだけの人は閲覧者（§4-1） |
| 会社に ID 基盤がある | SSO（試すあいだは Optional）と SCIM で寄せ、MFA は ID 基盤で。退職時は広告の役割も外す（§4-3） |
| 名前・ロゴを変えたい | 配信を止めてもよい時期に。ブランド名は立ち上げ前に決め切る（§3-2・§3-3） |
| 費用を絶対に超えたくない | カード払いならキャンペーンの通期予算と終了日で固定。止めた後の 24 時間を見込む（§7） |
| 請求書を経理に | 請求書の送付先のメールを会社の窓口に。JCT は今は課していない旨と契約の相手を経理に伝え、処理は税理士に（§6-4・§6-6） |
| キーを作る・渡す | 管理者が作り手元に保存。外部に渡す前に規約の第 1.4 条（§9-2） |
| 止まった | §8-4 の順で切り分け |

### 15-2. 少額のアカウントでの注意〔推測〕

- 最初の支払いの閾値は低く（米ドルの例は 25 ドル）、月の初めは**小刻みに何度も請求**が来る。カードの利用明細に同じ額が並んでも重複とは限らない（S-38）
- カード払いはアカウントの費用上限が使えない。**最低の 1 日の予算 2,500 円**（02§7-4）× 1 日 2 倍の振れ幅を見込む
- 事業者の確認の前に費用が出始める。確認で止まると、学習の途中で配信が切れる（34§1-7）
