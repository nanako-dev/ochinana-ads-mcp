## 1. タグの全体像 — 誰が何をしているか

### 1-1. 部品の一覧

| 部品（日本語ヘルプの表記） | 何をするか | 印 |
|---|---|---|
| Google タグ（gtag.js） | 1 つのタグで Google 広告・GA4 など複数の製品に送る。旧「グローバル サイトタグ」は Google タグになった（書き換え不要）。1 つのタグ ID に複数の「送信先」（広告アカウント、GA4 プロパティ）をつなぐ。タグの設定を変えると、つないだ送信先すべてに効く | ✅ 11994839 |
| イベント スニペット | 成果の発生を知らせる部分。Google タグと組み合わせて使う | ✅ 7521212 |
| Google タグ マネージャー（GTM） | タグをコードの代わりに管理画面で出し入れする箱（コンテナ）。Google 広告のタグを入れると、先に Google タグを読み込む | ✅ tagmanager/7549390 |
| コンバージョン リンカー | 着地ページの URL からクリックの情報を読み取り、自社ドメインのファーストパーティ Cookie とローカル ストレージに保存する。成果のタグが後でそれを読み、クリックと成果を結ぶ | ✅ tagmanager/7549390 |
| 自動タグ設定 | 広告のクリック時に URL へ gclid（Google のクリック ID）を付ける。新規アカウントは既定で有効（詳細は 06 の 2 章、15 の 5-29） | ✅ 3095550 |
| gbraid・wbraid | iOS で gclid が付かない場面向けの識別子。wbraid は 2021-03、gbraid は 2021-05 に導入（15 の 5-30、4-23、4-53） | ✅ 10417364 |
| gad_source・gad_campaignid | Google 広告のクリックに自動で付く集計用のパラメータ。前者は配信元（検索・ディスプレイなど）、後者はキャンペーンを示す。個人を特定しない。広告主は変えられない。gad_source は旧名 gad | ✅ 16193746 |

### 1-2. コンバージョン リンカーが要る場面・要らない場面 ✅

| 場面 | 要否 |
|---|---|
| ページに直接 Google タグを入れている | 要らない。Google タグ自身がファーストパーティ Cookie を置く。`conversion_linker` を false にして止められるが、Google は精度が落ちるので勧めない |
| GTM で、全ページで Google タグか送信先タグを読み込んでいる | 別のリンカー タグは要らない |
| GTM で、上のどちらも全ページにない | リンカー タグを「All Pages」のトリガーで入れる |
| 着地ドメインと成果のドメインが違う | 「ドメイン間のリンク」を有効にし、自動リンクの対象ドメインを足す。フォームの装飾はクエリ パラメータ方式のときだけ効く（フラグメント方式は不可） |
| GA4 だけを入れている | GA4 は gclid を Cookie に残さない（旧 UA は残した）。GA4 の成果は Google 広告へ取り込む形になる |

出典: tagmanager/answer/7549390、google-ads/answer/7521212、11994839

### 1-3. ファーストパーティ Cookie と有効期間 ✅

Google の広告用 Cookie の一覧（business.safety.google/adscookies）より。どれも「パートナーのドメインから設定」、つまり広告主のサイト側に置かれる Cookie。

| Cookie | 製品 | 期間 |
|---|---|---|
| `_gcl_aw` | Google 広告（gclid を保存） | 90 日 |
| `_gcl_gb`・`_gcl_gs`・`_gcl_ag` | Google 広告 | 90 日 |
| `_gcl_au` | Google 広告・キャンペーン マネージャーなど | 90 日 |
| `_gcl_dc` | キャンペーン マネージャー・DV360・検索広告 360 | 90 日 |
| FPGCLAW・FPGCLGB・FPGSID・FPAU・FPGCLGS | サーバーサイドで置く系統（推測: 名前の FP は first-party。サーバーから置く形） | 90 日 |
| ローカル ストレージ `_gcl_ls` | コンバージョン リンカー | 記載なし ❓ |

- ✅ 90 日は、オフライン取り込みで gclid を使える期限（クリックから 90 日、15 の 4-46）と同じ長さ
- ✅ リンカーの Cookie は接頭辞・ドメイン・パスを上書きできる。上書きしたら、読む側のタグにも同じ接頭辞を入れる
- 推測: クリックの計測期間を 90 日にしても、Cookie が先に消えると成果は結べない。次の ITP の節を参照

出典: business.safety.google/adscookies、tagmanager/answer/7549390

### 1-4. ブラウザの制限（ITP など）の影響

| 制限 | 中身 | 印 |
|---|---|---|
| Safari の ITP: スクリプトで書いた Cookie | `document.cookie` で書いた Cookie とローカル ストレージなどは、そのサイトを 7 日使わないと消される | ✅ webkit.org（Apple の一次資料） |
| ITP: リンク装飾 | 追跡に使う分類のドメインから、URL のパラメータ（クリック ID など）付きで来たとき、着地ページでスクリプトが書く Cookie は 24 時間に縮められる。条件は 2 つともそろうこと: ①追跡能力ありと分類されたドメインがその遷移をさせた ②遷移の最後の URL にクエリ（`?` 以降）かフラグメント（`#` 以降）がある。対象は着地したそのページで `document.cookie` が書く Cookie だけ（ITP 2.2、2019） | ✅ webkit.org（blog/8828、tracking-prevention） |
| ITP: CNAME の偽装 | 第三者のサーバーを自社サブドメインに見せかけた（CNAME・IP の偽装）と判定されると、HTTP の応答で置いた Cookie も 7 日に縮む。自社で運用するサーバーなら対象外 | ✅ webkit.org |
| Safari のクリック ID の除去 | 「高度なトラッキングとフィンガープリント保護」で gclid などが URL から外される。既定ではプライベート ブラウズだけ。gbraid・wbraid は外されないという分析がある | 第三者（PPC Land、各計測ベンダー）。Apple の一次資料は取得できず ❓ |
| Safari 26（2025-09） | 指紋（端末の特徴）への保護が通常の閲覧にも既定で広がった、と複数の報道。クリック ID の除去が通常の閲覧でも既定になったかは、報道の間で食い違う | 第三者。❓ |

- 推測: gclid 付きの着地で JavaScript が書く `_gcl_aw` は、Safari では 24 時間〜7 日で消えうる。翌日以降に成果が出る商材ほど、Safari の成果が取りこぼされる。拡張コンバージョン（4 章）とサーバーから置く Cookie（6 章）は、この穴を埋めるためのもの
- 第三者の対処例: 最終ページ URL のサフィックスに `{gclid}` を別名で入れて、除去されても残るようにする（PPC Land などの紹介）。Google が勧めているわけではない ❓

出典: webkit.org/tracking-prevention/、ppc.land（Safari とクリック ID の記事）、Safari 26 についての報道（9to5mac ほか）

## 2. Google 広告のタグと GA4 の取り込みの併用・二重計上の防ぎ方

どちらで取るかの比較（反映時間、ビュースルー、計上日など）は 06 の 1 章にある。ここでは「両方入れたときに二重に数えない」ことだけを書く。

| 論点 | 中身 | 印 |
|---|---|---|
| Google の立場 | 両方を選べ、成果ごとに使い分けられる（06 の 1 章） | ✅ |
| 自動での防止 | 2022-10-03 以降、GA4 から新しく取り込んだアクションは既定でサブ（入札に使わない）になる。同じイベントを 2 回入札に使わないため | ✅ analytics/11053134（旧記事） |
| Google の注意 | 二重計上がないことは保証できない。重複しうるものはサブにする | ✅ analytics/11053134 |
| 公式の原則 | 「ファネル下流のアクションのみをメインに」（06 の 9 章） | ✅ 2375435 |
| サーバーサイドへ移すとき | サーバー側の Google 広告タグが動いたら、ウェブ側の同じタグを外す（重複を避けるため） | ✅ server-side/ads-setup |
| 取引 ID | 同じ成果を複数経路で送るなら取引 ID（注文 ID）をそろえる。拡張コンバージョンを API で送るときは、二重計上を避けるため取引 ID が必須 | ✅ 11062876 |
| 診断での検知 | タグ診断に「コンバージョンが過大にカウントされている可能性」（直近 2 日で取引 ID の一致が 10% 未満）がある | ✅ 14681508 |
| 第三者の主張 | 1 つの成果につき、メインの経路は 1 本（タグか GA4 か）にする。どちらをメインにするかは意見が割れる（Adswerve と Analytics Mania はタグ派、06 の 1 章。GA4 取り込みを勧めるガイドもある） | 第三者 |

### 型: 同じ成果をタグと GA4 の両方で持つとき

1. 入札に使うのは片方だけ（メイン）。もう片方はサブで比較用
2. カスタム目標に両方を入れない（カスタム目標はサブでも入札に使う。06 の 4 章、15 の 4-30）
3. 「すべてのコンバージョン」列をアクション別に分け、件数の比がおおむね一定かを見る。急に比が変わったら、どちらかの経路が壊れた合図（実務家の tips、T2 の 8-8）

出典: analytics/answer/11053134、google-ads/answer/2375435、11062876、14681508／developers.google.com/tag-platform/tag-manager/server-side/ads-setup

## 3. 同意モード（v2）

### 3-1. 同意の種類 ✅

| 種類 | 何を決めるか | 拒否・未設定のとき |
|---|---|---|
| `ad_storage` | 広告用の保存（ウェブの Cookie、アプリの端末 ID） | 広告用 Cookie を新しく書かず、既存の Cookie も読まない。IP アドレスは短縮される |
| `ad_user_data` | 広告のために利用者のデータを Google へ送ってよいか | 拡張コンバージョンやタグでの成果計測に必要。拒否だと、クリック ID に基づく成果の受け渡し（GA4 の成果での入札最適化など）が制限され、成果は Cookie なしの ping で送られうる |
| `ad_personalization` | パーソナライズド広告（リマーケティングを含む） | リマーケティングにデータが入らない |
| `analytics_storage` | 分析用の保存（訪問時間などを測る Cookie） | GA の Cookie を読み書きしない。GA には Cookie なしの ping が送られ、モデル化に使われる |
| ほか 3 種 | `functionality_storage`・`personalization_storage`・`security_storage` | 広告の計測には直接は関わらない |

- ✅ v2 で増えたのは `ad_user_data` と `ad_personalization`（2023-11 に追加、と開発者向け資料）
- ✅ EEA 向けの記事は「未設定」を「拒否」と同じに扱う
- ❓ EEA での必須化の日付（2024-03 と広く言われる）は、取得した公式ページに書かれていなかった。第三者（Search Engine Journal、各 CMP〔同意管理ツール〕ベンダー）は 2024-03 と書く → 確かめ方: Google 広告ヘルプの「EU ユーザーの同意ポリシー」更新の告知を探す

出典: developers.google.com/tag-platform/security/concepts/consent-mode、google-ads/answer/13802165、tag-platform/security/guides/consent

### 3-2. 基本と高度の違い ✅

日本語ヘルプの表記は「基本の同意モード」「高度な同意モード」（08 の 10 章は「詳細」と書いているが、ヘルプの表記は「高度」）。

| 項目 | 基本 | 高度 |
|---|---|---|
| タグを読み込む時点 | 同意バナーで選ぶまで止める | ページを開いたら読み込む |
| 拒否のとき送るもの | 何も送らない（同意の状態すら送らない） | Cookie なしの ping（同意の状態、成果の発生、GA のイベント） |
| ping に入るもの | — | 時刻、ユーザー エージェント、参照元、クリック ID があったかの印、同意の真偽、ページごとの乱数など |
| 成果のモデル化 | 一般的なモデル | 広告主ごとのモデル（より細かい） |
| 同意したあと | Cookie を書き、全部送る | 同じ |

- ✅ 同意モードはバナーそのものではない。バナー（CMP）は別に用意する
- ✅ 既定値は `gtag('consent','default',…)` で、すべての計測コマンドより前に置く。`region`（ISO 3166-2）で地域ごとに既定値を変えられ、細かい地域の指定が優先。Google は「バナーを出す地域だけに拒否の既定値を絞ると、ほかの地域の計測を守れる」と書く
- ✅ `wait_for_update`（ミリ秒）でバナーの応答を待てる。例は 500
- ✅ `url_passthrough` を true にすると、Cookie が拒否でもクリック情報（gclid・wbraid など）を同じドメイン内の URL で受け渡す
- ✅ `ads_data_redaction` を true にすると、`ad_storage` 拒否のときクリック ID を伏せ、第三者 Cookie のないドメインで送る
- ✅ GTM には「Consent Initialization - All Pages」のトリガーがあり、ほかのトリガーより先に動く。コンテナの設定で「同意の概要」を有効にすると、同意の設定がないタグを一覧できる
- △ 高度の既定値について、Google 広告ヘルプ（10000067）は「特に選ばなければ同意済みが既定、EEA・スイス・英国では違う」と書き、開発者向けの例は 4 種すべてを拒否にしている。地域で既定値を変える前提で読む

出典: google-ads/answer/10000067（英・日）、tagmanager/answer/10718549、developers.google.com/tag-platform/security/guides/consent

### 3-3. 同意が無いときのモデル化 ✅

| 項目 | 中身 |
|---|---|
| 条件 | 国とドメインの組ごとに、7 日間で 1 日あたり 700 回の広告クリック（日本語では「1 日 700 クリックを 7 日間」と 08 の 10 章） |
| 開始 | 2021-04 から。条件を満たすと学習期間を経て、少しずつ出る |
| 出る列 | 「コンバージョン」「コンバージョン値」列。入札にも使われる。観測した成果と同じ粒度 |
| 偏りの方向 | 多く見積もらないように作られている。起きた成果の一部は数えられないことがある |
| Google の例 | 同意する人はしない人より 2〜5 倍成果に至りやすい。同意率 50% の例で、成果は 19% 減り、モデル化で 18% 戻る |
| 効果の表示 | 実装から 7 日以上で、同意モードの効果が見られる（データ量が足りる区分だけ） |

- 推測: 少量のアカウントは 700 クリックの条件に届かない（08 の 10 章と同じ判断）。届かないと、拒否された分は単に消える

出典: google-ads/answer/10548233、10000067

### 3-4. 日本で要るのか

| 誰の記述か | 中身 | 印 |
|---|---|---|
| Google の EU ユーザーの同意ポリシー | 対象は EEA・英国・スイスの利用者（06 の 8 章） | ✅ |
| Google の同意モードの資料 | 日本や EEA 以外の地域の義務には触れていない。地域ごとに既定値を分ける方法だけを示す | ✅（記載なしを確認） |
| 総務省（電気通信事業法の外部送信規律、2023-06-16 施行） | タグなどで利用者の情報を外へ送る事業者は、①通知または公表、②同意の取得、③オプトアウトの提供、のいずれかが要る。ファーストパーティ Cookie の ID も送信される情報の例。自社商品の販売だけのサイト、自社の事業紹介やブログだけのサイトは対象外 | ✅ 公的資料 |

- 推測: 日本の利用者だけなら、Google のポリシー上は同意モードの実装は求められていない。日本の法令は「同意」に限らず「通知・公表」でも足りる。どの選択肢が要るかは事業とサイトの種類で決まり、このメモでは判断しない
- 推測: 日本向けに同意バナーを入れるなら、高度な同意モードで地域を絞るのが計測への影響を最小にする（Google 自身が地域を絞ることを勧めている）
- 同意モードのタグ診断（10 章）には EEA 向けの項目が多い。日本だけのサイトで「EEA の同意がない」と出る場合の意味は ❓ → 確かめ方: 診断の詳細で、対象の地域とページを見る

出典: google.com/about/company/user-consent-policy、soumu.go.jp（外部送信規律の説明ページ）

## 4. 拡張コンバージョン（ウェブ向け・リード向け）

### 4-1. 仕組み ✅

| 項目 | 中身 |
|---|---|
| 何をするか | 成果の時点で得た自社データ（メールアドレス、電話番号、氏名＋住所）を SHA-256 でハッシュ化（元に戻せない変換）して送り、広告を見た・押したときにログインしていた Google アカウントと照らす |
| 照合の場所 | Google は「機密コンピューティング環境」で照合すると書く。Google タグ ゲートウェイとサーバーサイド GTM では、送信前に暗号化される（Google 広告のタグだけ） |
| ウェブ向け | サイト上の成果（購入・申込み）を、Cookie で結べなかった分まで拾う |
| リード向け | サイトで取ったリード（フォーム送信）のハッシュ化データを保存し、後で成約したときに同じデータを取り込む。gclid がなくても結べる。エンゲージ ビュー成果とデバイスをまたぐ成果も取れる |
| 前提 | 顧客データに関する規約（データ処理規約）への同意。拒否すると使えない（15 の 4-43、4-44） |

出典: google-ads/answer/9888656、15713840、16884284

### 4-2. 必要なデータ ✅

| 項目 | ルール |
|---|---|
| 最低限 | メール（推奨）、電話番号、住所一式のどれか 1 つ |
| 住所 | 姓・名・郵便番号・国が必須。番地・市区町村・都道府県は任意 |
| 電話 | E.164 形式（+ と国番号を含め 11〜15 桁、記号なし）。単独でも送れるがメールと一緒が推奨 |
| 国 | ISO 3166-1 alpha-2 の 2 文字 |
| 形式 | すべて文字列。取っていない項目は空で送らず消す |
| 正規化 | 前後の空白を除く、小文字にする、gmail.com などでは @ の前のピリオドを除く。それから SHA-256（16 進） |

出典: google-ads/answer/13262500

### 4-3. 設定方法の種類

| 方法 | 中身 | 印 |
|---|---|---|

### 5-3. 成約データを入札に戻す設計（Google の型）✅（13489421）

1. リードから売上までの段階を書き出す（Google は「リード ジャーニー マッピング」と呼ぶ）。段階ごとにアクション・値・遅れを付ける
2. 入札に向ける段階は 1 つ。複数の段階の目標を混ぜない
3. 値の差を付けられるなら値に基づく入札（値の最大化、目標広告費用対効果）。付けられないなら、有望・成約リードに目標アクション単価
4. 選ぶアクションは「アカウント全体で過去 30 日に 15 件以上」。理想は広告の操作から 7 日以内に起きる成果
5. 送るのは毎日が理想

- 06 の 15 章はかつて「月 15 件（Jellyfish の記述）は公式で確認できず」としていたが、このリード向けの公式ページに「過去 30 日で 15 件以上」とある（リード獲得の文脈に限った目安）。06 は 2026-11-17 の裏取りで §11・§15 を直し済み（13489421 で ✅）
- 第三者（Menachem Ani、SEJ、T2 の 8-17）: 営業の期間が 90 日を超えるなら、見込みの値を予測して早い段階で送る

- 推測: 数字が急に変わったら「計測が変わった」を先に疑う。サイトの改修、同意バナーの更新、GTM の公開の日付を記録しておくと、折れ点と突き合わせられる（T2 の 8-4、8-13 と同じ趣旨）

## 11. プライバシー サンドボックスとサードパーティ Cookie（2026 年時点）

08 の 10 章に詳しい。要点だけ。

- ✅ Chrome はサードパーティ Cookie を廃止せず、利用者が選ぶ今の形を続ける（2025-04-22 の発表、08）
- ✅ 2025-10-17: 採用が少ないとして、Attribution Reporting API、Topics、Protected Audience、IP Protection、Private Aggregation、Related Website Sets などを終了すると発表。CHIPS、FedCM、Private State Tokens は続ける。計測は W3C で検討中の共通規格を支持
- 推測: Google 広告の成果計測はもともとファーストパーティ Cookie（1 章）で、サードパーティ Cookie の存続はほぼ影響しない。影響が大きいのは Safari の制限と同意の取得率

## 15. 少額・少量のアカウントでの注意

- 同意モードのモデル化（1 日 700 クリック）にも、拡張コンバージョンの警告（週 20 件）にも届かない。届かない機能に期待しない ✅
- サーバーサイド GTM は最低 2 台で月約 90 米ドル。少額の広告費とは釣り合わない ✅（費用）・推測（判断）
- 1 件の成果の重みが大きいので、二重計上 1 件で学習が狂う。メインの経路を 1 本にする（2 章）
- 点検は 10 章の 1〜3（ステータス、タグ診断、Tag Assistant）で足りる。0 円でできる
- Safari の比率と、成果がクリックから何日後に起きるかを先に見る。同じ日に完結する成果なら、Cookie の寿命の問題は小さい（推測）
- 個人情報を取らないサイトでは、拡張コンバージョンとリード向けの取り込みは使えない（4-5）

## 16. 判断の型

1. **成果はどの経路で何本届いているか**: アクション別に「タグ」「GA4 取り込み」「取り込み」を書き出す。同じ成果を 2 本のメインで取っていないか（2 章）
2. **クリック ID は着地まで届いているか**: 自分で広告を押し、着地 URL に gclid・gad_source が残るか。リダイレクトと別ドメインを確かめる（9 章）
3. **Cookie は成果の時点まで残るか**: 成果までの日数と Safari の比率。長く、比率が高いなら、ゲートウェイか拡張コンバージョンを考える（1-4、4 章、6 章）
4. **同意は誰に要るか**: 利用者の地域を見る。EEA などがいれば v2 の 4 種を。日本だけなら法令上の選択肢を別に確認（3-4）
5. **自社データはあるか**: メール・電話があるなら拡張コンバージョン。成約が後で分かるならリード向け＋データ マネージャー（4・5 章）
6. **入札に戻す段階は 1 つか**: 段階ごとにアクションを分け、入札は 1 段階。件数（30 日 15 件）と遅れ（7 日以内）で選ぶ（5-3）
7. **壊れたら上から順に**: ステータス → タグ診断 → Tag Assistant → 拡張の診断 → 自社の台帳（10 章）
