# 型03 制御の輪（工程の分解）

- 確認日: 2026-11-17
- 位置づけ: 第 2 部の入口。型01 で導いた「差を見て直す輪」を、6 つの工程に分け、工程どうしの依存関係と、輪を回す速さを決める
- 既存メモとの関係: 手順の細部は 28・35・36・37 にある。この章は「なぜその工程が要るか」「工程の間で何を受け渡すか」「どの速さで回すか」を書き、細部は番号で送る
- 根拠の印: 〔公式〕〔データ〕〔経験則〕〔推論〕〔未確認〕。断りのない段落は〔推論〕

## この章の問い

運用の輪は、どんな工程からできているか。各工程は何を受け取り、何を出し、何を基準に良し悪しを決めるか。工程はどう依存し合い、どこで誤ると、どこに症状が出るか。輪はどの速さで回すべきか。

## 結論

1. 輪は 6 工程: **目的を決める → 設計する → 配信する → 読む → 決める → 変えて残す**（→ 読むに戻る）
2. 各工程は、前の工程の出力を入力にする。だから上流の誤りは下流のすべてを誤らせるが、**症状は下流（読む）にしか出ない**。症状を見たら、原因は上流から順に疑う
3. 輪は 1 つではなく、速さの違う 3 つが重なっている。**事故の輪**（毎日。止めるだけ）、**改善の輪**（評価窓ごと。1 つ変える）、**目的の輪**（四半期ごと。目的と目標を見直す）
4. 輪の速さは好みでは決まらない。その輪で使う数字が「いつ確定し、何件で判定できるか」（型04）で決まる。毎日判定できるのは表示・費用・ステータスだけなので、毎日できるのは事故の発見だけである
5. 改善の輪 1 回は、仮説 → 変更 → 待つ → 判定 → 記録、の決まった書式で回す

---

## §1 輪の全体

```
        ┌───────────────── 目的の輪（四半期）─────────────────┐
        ▼                                                          │
 工1 目的を決める ──→ 工2 設計する ──→ 工3 配信する ──→ 工4 読む ──→ 工5 決める ──→ 工6 変えて残す
                          ▲               （内側の輪＝機械）     │  ▲                      │
                          │                                      │  └── 事故の輪（毎日）──┘（止める・戻すだけ）
                          └──────────── 改善の輪（評価窓ごと）───┴──────────────────────────┘
```

- 工3（配信する）の中で、機械が内側の輪を回している（型01§5-1）。人が直接手を出せるのは工3 以外の 5 つである
- 工6 の「残す」は工程の一部であって、後片付けではない。残さなければ次の工4 で「何が効いたか」を読めず、輪が閉じない（型11§3）

## §2 6 つの工程

### 工1 目的を決める

| | 中身 |
|---|---|
| 入力 | 事業の数字（粗利、成約率、継続、受けられる量）、広告の受け持ち（どの客を、どの経路で）、使える費用 |
| 出力 | 目的関数の値（g・q・ι）、損益分岐 BE、目標 T と量の目標、優先順位（量か効率か）、判定の約束（評価窓、判定不能を許すこと）。合意書の形で残す（型11§7） |
| 判断の基準 | 「管理画面の成果が増えたら、利益が増えたと言えるか」に、式でつながる形で「はい」と言えること（型02§4） |
| 典型的な失敗 | 推奨値や業界平均を目標にする（28§8-4）／管理画面の 1 件を事業の 1 件と同じに扱う（q・ι を掛けない）／量の下限を決めない／目標を損益分岐そのものに置く（型02§3 より利益が 0 になる点） |
| 手順の細部 | 28§8、37§1 |

### 工2 設計する

| | 中身 |
|---|---|
| 入力 | 工1 の出力 |
| 出力 | 機械への入力一式（型05 の 6 類）: 何を成果として教えるか（計測と成果の定義）、何を渡すか（広告文・LP）、どこを囲うか（キーワード・除外・地域）、どう換えるか（入札戦略・目標値・予算）、どう束ねるか（構成） |
| 判断の基準 | (a) 計測のテスト送信が 1 件として入る (b) 入札に使われる成果が工1 の目的と一致する (c) 予算と目標の組で、評価に足る件数（閾04）が見込める (d) 低い日予算・きつい目標・狭い範囲を同時に重ねていない（02§12） |
| 典型的な失敗 | 計測を確かめずに配信する／既定の成果（軽い行動）がメインのまま／少量なのに分けすぎる（35:D03）／絞る設定を重ねて機械が動けない |
| 手順の細部 | 28§3、37§2、35 の A〜D |

### 工3 配信する

| | 中身 |
|---|---|
| 入力 | 工2 の設計 |
| 出力 | 表示・クリック・成果のデータ、機械の学習 |
| 判断の基準 | 人の基準は 1 つだけ: **事故が無いか**（出ているか、使いすぎていないか、計測が止まっていないか、不適切な掲載が無いか） |
| 典型的な失敗 | 学習の途中で触る（型04§2）／逆に、止まっているのに気づかない |
| 手順の細部 | 36§2（日次の点検） |

### 工4 読む

| | 中身 |
|---|---|
| 入力 | 工3 のデータ、変更の記録（工6 の出力）、台帳（自社の実数） |
| 出力 | **状態の判定**（型06 の 9 状態のどれか）と、目標との差の大きさ・確からしさ |
| 判断の基準 | 型04§9 の 3 条件を満たした数字だけを判定に使う: 確定している／評価窓が明けている／件数が足りる。満たさない数字は「暫定」「判定不能」と書く |
| 典型的な失敗 | 当日・前日の成果で判断する（28§4-4）／偶然の振れを変化と読む／直近の遅れを悪化と読む／前後比較で季節・曜日をそろえない（26§8）／管理画面の成果を「広告が起こした成果」と読む |
| 手順の細部 | 36§3〜§5、26§8 |

### 工5 決める

| | 中身 |
|---|---|
| 入力 | 工4 の状態の判定 |
| 出力 | 次の一手（何を・どれだけ・なぜ）、または「何もしない」。変える場合は仮説の 1 枚（型11§2）: 予想する効果、判定の指標、待つ期間、戻す条件 |
| 判断の基準 | 型07 の順序（計測 → 定義 → 絞る → 素材 → 構成 → 入札・予算 → 広げる）と門（止血が先／計測が壊れている間は触らない／1 単位 1 窓 1 実験／戻せない手は後） |
| 典型的な失敗 | 状態を判定せずに打ち手を選ぶ（「単価が高い → 入札を下げる」）／複数の手を同時に入れる／「何もしない」を選べない／戻す条件を決めずに変える |
| 手順の細部 | 37§4、28§6 |

### 工6 変えて残す

| | 中身 |
|---|---|
| 入力 | 工5 の仮説の 1 枚 |
| 出力 | 変更そのもの、変更の記録（いつ・何を・なぜ・判定日）、判定日の予定 |
| 判断の基準 | 記録を読んだ別の人が、何をなぜ変え、いつ何で判定するかを再現できること |
| 典型的な失敗 | 記録しない／理由を書かない／自動適用や担当者以外の変更が記録に入らない（28§10-4）／判定日が来ても判定しない |
| 手順の細部 | 28§10、36§8、型11§3 |

## §3 工程の依存関係

### 3-1. 受け渡しの表

各工程は、前の工程の出力を「正しいもの」として受け取る。だから、渡すものの条件を満たしていなければ、次の工程は始めてはいけない。

| 渡す側 → 受ける側 | 渡すもの | 受け取る条件（満たさなければ戻す） |
|---|---|---|
| 工1 → 工2 | BE、T、量の目標、g・q・ι の置き方 | 式でつながっている。置いた値に根拠か「仮置き」の印がある |
| 工2 → 工3 | 6 類の入力一式 | 計測のテストが通る。成果の定義が目的と一致する |
| 工3 → 工4 | データ | 事故が無い期間である（あれば、その期間を除くか注記する） |
| 工4 → 工5 | 状態の判定 | 型04§9 の 3 条件を満たした数字で判定している |
| 工5 → 工6 | 仮説の 1 枚 | 判定の指標・待つ期間・戻す条件が書いてある |
| 工6 → 工4 | 変更の記録 | 次に読むとき、いつ何を変えたかが分かる |

### 3-2. 誤りの伝わり方: 症状は下流、原因は上流

上流の誤りは下流のすべてに伝わるが、気づくのは工4（読む）である。

| 誤った工程 | 下流で起きること | 工4 での見え方 |
|---|---|---|
| 工1（目的） | 機械は間違った目標に向けて正しく最適化する | 管理画面は目標どおり。なのに事業の数字（受注・利益）が良くならない |
| 工2（設計。特に教える類） | 機械が誤った正解から学ぶ | 成果率が不自然に高い、台帳と合わない、成果は増えたのに質が下がった |
| 工3（配信中の事故） | データに穴か異常値が入る | 急な 0、急な倍増 |
| 工4（読み違い） | 偶然や遅れに対して手を打つ | 打った手が効いたり効かなかったりして、一貫しない |
| 工5（決め方） | 効果の小さい手に窓を使う、同時に複数変える | 何が効いたか分からない |
| 工6（残さない） | 次の工4 が変更と結果を結べない | 同じ失敗を繰り返す |

ここから、型06 の決定木と型07 の順序を支える原則が出る。

**上流優先の原則: 工4 で差を見たら、原因は上流から順に疑い、上流から順に直す。** 下流だけ直しても、上流の誤りが残っていれば直した効果は測れず、機械は誤った方向へ学び続ける。

- 「管理画面は目標どおりなのに事業が良くならない」は、下流（入札・広告文）をいくら直しても解けない。工1 か工2 の教える類に戻るしかない
- 既存メモが場面ごとに「計測から」と書いている（28§0、35§1-2）のは、この原則の個別の現れである

### 3-3. 輪が閉じているかの点検

輪が閉じていない（どこかで受け渡しが切れている）と、型01§4 の「直す輪は放置を上回る」は成り立たない。切れやすい所は 3 つある。

| 切れ目 | 症状 | 閉じ方 |
|---|---|---|
| 工6 → 工4（記録が次の読みに使われない） | 変更と結果が結べない。判定日が流れる | 記録に判定日を入れ、判定日を点検の予定に載せる（型11§3） |
| 工4 → 工1（事業の数字が戻らない） | q・ι・g が最初の仮置きのまま | 目的の輪（§4）で四半期ごとに台帳と突き合わせる |
| 工5 → 工6（決めたが変えない／変えたが決めていない） | 「提案したが実行されていない」「誰かが変えたが理由が分からない」 | 変更の権限と承認の線を決めておく（型11§8） |

## §4 3 つの時間の輪

### 4-1. なぜ輪は 3 つに分かれるか

輪を回す速さは、その輪で使う数字が「いつ確定するか」と「何件あれば判定できるか」で決まる（型04）。数字によってこの 2 つが大きく違うので、輪は自然に 3 つに分かれる。

| 数字 | 確定までの時間 | 判定に要る量がたまる時間 | 判定できる速さ |
|---|---|---|---|
| ステータス、表示回数、費用 | 数時間〜1 日（インプレッション シェアは別で、公式の 2 つのページが 24〜48 時間と約 3 日に割れる △。遅いほうの 3 日で扱う。ルール表 `R-報告-023`） | 件数が多く、0 か倍かはすぐ分かる | 毎日 |
| 成果数、成果率、獲得単価 | 管理画面への反映はラストクリック以外のモデルで約 15 時間（`R-報告-007`）。そのうえで成果の遅れを待つので L 日（閾03。最短 5 日） | 30 件（閾04）、差を言うなら 15.7 ÷ δ² 件（閾05） | 評価窓 W（閾02。最短 14 日）ごと |
| q、ι、g、β | 成約や継続が分かるまで（数週間〜数か月） | 複数の評価窓 | 四半期ごと |

- 「毎日見て毎日直す」が成り立たないのは、怠けてよいからではなく、**毎日の成果の数字が判定の条件を満たさないから**である。満たさない数字で直すことは、型01§4-3 の「誤った方向に直す」に当たり、放置より悪くなりうる
- 逆に「月に 1 回しか見ない」も成り立たない。表示や費用の事故は毎日判定でき、放っておくと損失が日数に比例して増えるからである

### 4-2. 3 つの輪

| | 事故の輪 | 改善の輪 | 目的の輪 |
|---|---|---|---|
| 速さ | 毎日（自動の通知でよい） | 評価窓 W ごと（少量なら判定期間 P ごと。型04§9） | 四半期ごと、および事業が変わったとき |
| 使う数字 | ステータス、表示、費用、成果が 0 の日数 | 確定した成果・単価・率、検索語句、品質の診断 | 台帳の実数、q・ι・g、区間単価、β |
| 問い | 止まっていないか、暴走していないか、壊れていないか | 状態はどれか、次の 1 手は何か | 目的と目標は今も正しいか、受け持ちは正しいか |
| 許される行動 | **止める・戻す・直す（修理）だけ** | 1 単位に 1 つの実験、または束ねた修理 | 目標値・成果の定義・構成・受け持ちの見直し |
| 触る類 | 状態（オン・オフ）、明白な誤設定 | 6 類のうち型07 の順で 1 つ | 教える・束ねる・換える（目標）・事業 |
| 通る工程 | 工4（簡易）→ 工5 → 工6 | 工4 → 工5 → 工6 | 工1 → 工2 |
| 既存メモ | 36§2、36:D1〜 | 37§4、36§3 | 36:Q、37§8 |

- 3 つの輪は入れ子である。事故の輪で見つけたものが修理で済めば事故の輪の中で閉じ、原因が設計にあれば改善の輪へ、目的にあれば目的の輪へ上げる
- 輪を取り違えると害が出る。改善の輪でやるべき判定（単価が高い）を事故の輪でやると「毎日触る」になり、目的の輪でやるべき見直し（目標が損益と合っていない）を改善の輪でやると「入札をいじり続ける」になる

### 4-3. 「見る頻度」と「触る頻度」は別

36§0 が言う「見る頻度と触る頻度を分ける」は、この 3 つの輪で説明できる。見るのは毎日でよい（事故の輪）。触ってよい頻度は、触る対象の数字が判定できる速さで決まる（改善の輪は W ごと）。**毎日見ることと、毎日触らないことは、矛盾しない。**

## §5 改善の輪 1 回の書式

改善の輪の 1 回は、必ず次の 7 つの段を通る。段を飛ばすと、型11 の「判断の質」が保てない。

| 段 | やること | 出すもの | 根拠の章 |
|---|---|---|---|
| 1 読む | 確定した数字で状態を判定する | 状0〜状8 のどれか | 型06§2 |
| 2 絞る | その状態で許される打ち手の中から、順序と点数で 1 つ選ぶ | 候補の表と、選んだ理由 | 型07§2〜§4 |
| 3 書く | 仮説の 1 枚を書く（何を・なぜ・どの指標が・どれだけ・いつまでに／判定の指標と期間／戻す条件／修理か実験か） | 仮説の 1 枚 | 型11§2 |
| 4 変える | 変更し、記録する。判定日を予定に入れる | 変更の記録 | 型11§3 |
| 5 待つ | 評価窓が明けるまで、その単位には次の実験を入れない。事故だけ見る | — | 型04§6、型07§4（門 3） |
| 6 判定する | 判定日に、確定した数字で「効いた／効かなかった／判定不能」を決める | 判定 | 型04§9、型11§4 |
| 7 残す | 判定と学びを記録し、残すか戻すかを決める。次の輪へ | 記録 | 型11§4 |

- 段 5 の「待つ」は何もしないことではない。別の単位（別のキャンペーン）の輪、配信に触れない準備（LP の制作、計測の整備）、検索語句の点検は並行して進められる（型07§3）
- 1 回の輪にかかる時間は、最短で W ＋ L（評価窓 ＋ 確定待ち）である。W ＝ 14 日、L ＝ 7 日なら 3 週間。**1 つの単位で 1 年に回せる改善の輪は、多くて 17 回、少量のアカウントでは数回**である。だから 1 回の輪に何を載せるか（段 2）が、運用の成果の大半を決める〔推論〕
