### 1-1. 運用の判断への効き方（どれを選ぶか）
- **日次の進捗を Google スプレッドシートに貯めるだけなら ②（スクリプト）が一番早い**〔推測〕。申し込みも鍵も要らず、アカウントの中で毎日決まった時刻に動き、スプレッドシートに書ける（P-21、P-22、P-24）。ただしスクリプトを動かすビジネス ID は**更新以上の権限**を持つので、コードが書き込みをしないことを人が読んで確かめる（principles 2。§2-B）
- **AI（Claude Code）から読むなら ④（公式 MCP）か、運用 MCP に足す ③**。④はすぐ動くが、運用 MCP の許可リスト・知識ベース・点検とはつながらない。③で運用 MCP に足せば、Google と同じ `get_performance` の形で読める（§6）〔推測〕
- **① は人が見る用**。定期作成のメールは「できました」の知らせだけなので、機械で取り込む道には向かない〔推測〕（P-29）
- ③④ の前提は「LINEヤフー広告の申し込みが済んでいること」と「ルート MCC の管理権限を持つビジネス ID」（P-04）。運用の原則では LINEヤフーは「つなぐと決めたときに足す」（`ads-mcp/principles.md` 5）

### 1-2. 公式 MCP サーバー（④）のくわしい中身 ✅〔公式〕P-19（README.ja.md と src、v0.0.1、2026-09-11 作成）
MCP クライアントの設定は `"type": "http"` と URL だけ
- 鍵の渡し方: 環境変数 `LY_ADS_CLIENT_ID`・`LY_ADS_CLIENT_SECRET`（MCP 用 OAuth クライアント）、`LY_ADS_MCP_JWT_SIGNING_KEY`（自分で作る 32 文字以上の乱数、`openssl rand -base64 32`、シークレットと同じ値は不可）、任意で `LY_ADS_REPORT_OUTPUT_DIR`（CSV の置き場、既定は起動したフォルダの `reports`）。**アクセストークンと更新トークンは FastMCP の OAuth Proxy が持ち、MCP クライアントには設定しない**。接続するとブラウザに認可画面が出て、ビジネス ID で許可する
- MCP 用 OAuth クライアント: API の申し込みのあと `https://connect-business.yahoo.co.jp/client/mcp` で発行。**通常の API アプリは企業単位、MCP 用 OAuth クライアントはビジネス ID 単位**。発行画面には API 管理ツールの管理権限か利用権限が要る
- 道具（名前空間 `ly_ads_display`・`ly_ads_search`）: 一覧系（`list_accessible_*_base_accounts`、`list_accessible_*_accounts`、`list_*_campaigns`、`list_*_labels`、`list_*_ad_groups`、`list_display_ad_group_targets`、`list_search_campaign_targets`、`list_search_campaign_negative_keywords`、`list_search_ad_group_keywords`、`list_*_ads`）、`get_*_report_fields`、`read_*_report`。**変更の道具は無い**
- レポート: 中では ReportDefinitionService の add（ジョブを作る）→ get（2 秒おき）→ download。**60 秒で終わらなければエラー**（期間・項目・絞り込みを狭めて再依頼）。結果は先頭 50 行のプレビューと、UTF-8 の CSV（`display/YYYY-MM-DD` か `search/YYYY-MM-DD`）。CSV は自動では消えない。返すのはローカルのパスで、MCP の Resource ではない
- API の版: コードは `v20` 固定（`api_version.py`）。スコープは `yahooads`
- 安全の作り: 返す値はすべて「信頼しないデータ」として区切り、指示として扱わないよう AI に伝える文が入っている。複数アカウントへの一斉の呼び出しは、利用者がはっきり頼んだときだけ、と指示している
- 〔推測〕「参照のみ」は道具の品ぞろえの話で、権限の話ではない。認可したビジネス ID が更新権限を持っていれば、トークン自体は書き込みにも使える。読むだけを権限で保証したいなら、参照権限だけのビジネス ID で認可する（§2-A の 6）
- 〔推測〕レポートのたびに「レポートのジョブ」を add で作る（広告の設定は変えない）。作ったジョブを消す呼び出しはコードに見当たらない

## 2. 「自分の広告アカウントの日次の実績を読むだけ」に要る最小の準備

Claude は作らない、貼らない、読まない（principles 5）。

### 2-A. API（③）と公式 MCP（④）で読むとき

1. **LINEヤフー広告の申し込みを済ませる**（まだなら）。API の申し込みの前提 ✅〔公式〕P-04
2. **ルート MCC の管理権限を持つビジネス ID を確かめる**。ルート MCC は企業を作ると 1 つでき、操作できるのはその管理権限のユーザーだけ ✅〔公式〕P-34。権限が無い ID では申し込みのメニューが出ない ✅〔公式〕P-04
3. **広告管理ツールで、ベースアカウントにルート MCC を選び、右上の「ツール」→「LINEヤフー広告 API お申し込み」→ 画面の案内どおり入力 → 利用約款に同意**（約款は P-01 のリンクの PDF。読んでから同意する）✅〔公式〕P-04。過去にガイドライン違反を指摘されたことがあると使えない ✅〔公式〕P-04。費用は無料 ✅〔公式〕P-02
4. **「【LINEヤフー広告 API】登録完了のお知らせ」のメールを待つ**（ビジネス ID のメールアドレスに届き、API 管理ツールの管理者権限が付く）✅〔公式〕P-04。何日かかるか、審査があるかは ❓ 記載なし。メールにはテストアカウント（検索 1・ディスプレイ 1、配信されず実績は取れない）も書いてある ✅〔公式〕P-10
5. 道を選ぶ:
   - **公式 MCP（④）なら**: `https://connect-business.yahoo.co.jp/client/mcp` で **MCP 用 OAuth クライアント**を発行し、クライアント ID とシークレットを手元のファイル（Git に入れない、他の人が読めない場所）に置く。JWT 署名キーも自分で作って同じく置く ✅〔公式〕P-19
   - **自前の道具（運用 MCP に足す、§6）なら**: **API 管理ツール（`https://connect-business.yahoo.co.jp/cooperation/`）の「登録アプリケーション」→「登録」**で、アプリケーション名・説明・リダイレクト URI（手元で使うだけなら `oob`）を入れて登録し、クライアント ID・シークレットを手元のファイルに置く ✅〔公式〕P-05。ブラウザで `https://biz-oauth.yahoo.co.jp/oauth/v1/authorize?response_type=code&client_id=…&redirect_uri=oob&scope=yahooads&state=…` を開いて認可し、出てきた認可コード（10 分で失効）を `https://biz-oauth.yahoo.co.jp/oauth/v1/token` に送って更新トークンを得る ✅〔公式〕P-06。
6. **読むだけにしたいなら、認可に使うビジネス ID を「参照権限」だけにする**〔推測。権限の定義は ✅〔公式〕P-33、認証に要る権限は「参照または更新」✅〔公式〕P-03〕。申し込みと認可は別のビジネス ID でもよい（パターン 1・2 の書き方から〔推測〕P-03）。参照権限の ID で ReportDefinitionService の add（ジョブの作成）が通るかは ❓ 記載なし（管理画面では参照権限でもレポートを作れる ✅ P-29）
7. 最初の呼び出し: `BaseAccountService/get` で使えるベースアカウント ID を確かめ、以後は `x-z-base-account-id` に入れる ✅〔公式〕P-06。権限が足りないと HTTP 403・エラー 0098 ✅〔公式〕P-07
8. 止めたいとき: API 管理ツールの承認済みアプリから解除するか、`https://biz-oauth.yahoo.co.jp/oauth/v1/revoke` にトークンを送る ✅〔公式〕P-06、P-08。契約の解約は問い合わせフォームから、5 営業日ほど ✅〔公式〕P-11

### 2-B. スクリプト（②）で Google スプレッドシートに書くとき

1. 広告管理ツールの「ツール」→「LINEヤフー広告 スクリプト」→「新規作成」でスクリプト名と中身を入れる ✅〔公式〕P-28

3. スクリプトの中でスプレッドシート ID（URL の `/d/` と `/edit` の間）を指定する ✅〔公式〕P-25
4. 「承認」でビジネス ID の承認をし、「実行」で試す。**保存・実行・定期実行の設定ができるのは管理権限か更新権限のユーザーで、参照権限ではできない** ✅〔公式〕P-23

### 3-1. 流れ（検索・ディスプレイ共通）✅〔公式〕P-14、P-15、P-18

### 3-4. 運用の判断への効き方
- **日次の表は「毎朝 9 時以降に、前日を含む過去 N 日を取り直して上書き」にする**〔推測〕。理由は 2 つ: ディスプレイは前日分の確定が朝（P-18、P-32）、成果はクリックの日に計上され、計測期間（1〜90 日、設定ごと）の中で後から増える（06 §4-3）。N は使っているコンバージョン設定の計測期間に合わせ、少なくとも 7 日、長い商材は 30 日以上〔推測〕
- インプレッションシェア系は前日分が夜 10 時まで来ないので、朝の取得では前日の値が欠ける。翌日の取得で埋める〔推測〕（P-31）
- 「今日」を含めた値は確定前（P-29、P-30、P-18）。日次の表には入れないか、別の列にする〔推測〕
- 検索とディスプレイは別の呼び出し・別のアカウント ID・別の項目名（§4）。1 本の表にするときは「媒体」の列を足して縦に積む〔推測〕

| インプレッションシェア | `metrics.search_impression_share` | `IMPRESSION_SHARE`、`BUDGET_LOST_IMPRESSION_SHARE` → 損失率（予算）、`QUALITY_LOST_IMPRESSION_SHARE` → **損失率（ランク）** | `IMPRESSION_SHARE`、`BUDGET_LOST_…`、`RANK_LOST_…`（広告 ID と組み合わせ不可。取れないと空） | 検索の「ランク」は項目名が QUALITY。損失率（予算）の意味は Google と違う（00 §11-2） |

### 4-2. 成果の定義（日次の列の中身）
- 計上日: **きっかけのクリックの日（複数なら最後のクリックの日）**。計測期間はコンバージョン設定ごとに 1〜90 日（7 日以上を推奨）✅〔公式〕06 B-22、B-01
- 検索の「コンバージョン数」: 入札に使う成果（自動入札への利用「する」の設定、またはキャンペーン単位で選んだもの）。「（全て）」はすべての設定 ✅〔公式〕06 §4-2・§4-3
- ディスプレイの「コンバージョン数」: クリック後と、**動画を 10 秒以上視聴した後**の成果（「コンバージョン列に含める」設定のもの）。クリック後だけは「（クリック経由）」✅〔公式〕06 B-24
- ビュースルー（ディスプレイだけ）: 表示から **1 日（24 時間）固定**、計上はビューの日、「コンバージョン数」には入らない ✅〔公式〕06 B-08
- 計測方法: 毎回／初回のみ。管理画面で作ると初期値は「毎回」、API で作ると ONE_PER_CLICK ✅〔公式〕06 §4-1
- アトリビューションモデルを選ぶ設定: 検索・ディスプレイとも見当たらない ❓（06 §14-1）

### 4-3. Google と意味が違う列（日次の表で取り違えやすいもの）

| 列 | Google | LINEヤフー | 表での扱い〔推測〕 |
|---|---|---|---|
| コンバージョン数（ディスプレイ） | クリック後（ビュースルーは別の列） | **動画 10 秒視聴後を含む** | 媒体をまたいで並べるなら「（クリック経由）」を使う |
| コンバージョン数（検索） | 入札に使う成果 | 入札に使う成果＋**推定の合算**（2025-10-22〜） | 前後の比較に注記 |
| 費用 | マイクロ単位の整数 | 検索は円の整数、ディスプレイは小数 | 円にそろえ、丸めは 1 か所で |
| インプレッション | 表示回数 | ディスプレイはビューアブル・メジャードが別にあり、課金の数え方が違う | 費用÷表示の CPM を媒体で比べない |
| 損失率（予算） | 予算による損失 | 入札価格とアカウント残高による損失も含む（検索） | 「予算を足せば取れる」と読まない |
| 「月」 | 月 | 検索の `MONTH` は「毎月」、`MONTH_OF_YEAR` が「月」（1〜12 月の別） | 期間の軸は `DAY` から自分で作る |

### 4-4. 推定コンバージョンが日次の列にどう効くか
- 事実: 推定コンバージョン（直接測れない成果をモデルで推定したもの）は、**検索ではウェブページのコンバージョン、2025-10-22 以降の分**、**ディスプレイではクリック経由、2023-02-27 以降の分**が、「コンバージョン数」「コンバージョン数（全て）」（ディスプレイは「（クリック経由）」も）に合算される。**抜き出しも除外もできない**。合算されないのはディスプレイのコンバージョン経路・アトリビューションモデル比較・横断リーチの各レポート ✅〔公式〕S-164（06 §7、B-12、B-13）
- 日次の列への効き方〔推測〕:
  1. API のレポートの `CONVERSIONS`・`ALL_CONV`・`CONVERSIONS_VIA_AD_CLICK` も、管理画面のパフォーマンスレポートの数字なので推定を含む（API のレポートは「広告管理ツールのレポート機能を API でもサポート」と公式 P-14、P-15）。**「タグで測った件数だけ」の列は作れない**
  2. 推定は後から計算して入る作りと考えられるので、直近の日の件数が後から変わる理由の 1 つになりうる。どれくらい遅れて入るかは ❓ 記載なし。§3-4 の「過去 N 日の取り直し」で吸収する
  3. 推定を含まない数字が欲しいときの唯一の公式の道だったディスプレイの経路・モデル比較レポートは **2027-01-13 に終了予定**（S-42）。その後は媒体の中に推定抜きの件数は残らない
  4. 自社の受注データや GA4 と突き合わせると、媒体の件数が多く出る一因になる。日次の表には「媒体の件数（推定を含む）」と書いた列名にし、実数の列（自社のデータ）と分けて置く
  5. 検索の 2025-10-22 をまたぐ比較（前年同月比など）には注記の列を付ける

## 6. 運用 MCP（`ads-mcp`）につなぐときの案〔推測〕

ここは書き手の設計の案。今の運用 MCP は、Google 広告を読むだけの道具 45 個、許可リスト（`ochinana_ads/config.py`、Google のアカウント 2 つ）、認証ファイルは環境変数で場所だけ指し中身は google-ads ライブラリが読む、という作り（`ads-mcp/README.md`、`principles.md` 版 0.3）。

### 6-1. 2 つの道と、どちらから始めるか
- **道 1: 公式 MCP（④）をそのまま横に置く**。Claude Code に `ly-ads-mcp` を `type: http` で足すだけ。早いが、運用 MCP の許可リスト・点検（`run_checks`）・外れの検出（`get_anomalies`）・知識ベースとはつながらない。アカウントの絞り込みは「認可した ID が見られるアカウント」だけで決まる
- **道 2: 運用 MCP に LINEヤフーの読み取りの道具を足す**。③の API を自前で呼ぶ。Google と同じ形の道具・許可リスト・記録の形にそろえられる
- 〔推測〕**まず道 1 で「何が取れるか・取れた数字が管理画面と合うか」を確かめ、日次の表と点検に組み込む段で道 2 を作る**。どちらも、認可に使うビジネス ID を参照権限だけにしておけば、読むだけを権限で保証できる（§2-A の 6）

### 6-2. 道 2 の形（Google の道具に合わせる）

| Google の道具 | LINEヤフーでの中身 | 呼ぶもの |
|---|---|---|
| `list_accounts` | 使えるベースアカウントと、その下の検索・ディスプレイの広告アカウント（媒体の列を付ける） | `BaseAccountService/get`、`AccountService/get` |
| `get_performance`（期間合計） | 検索は CAMPAIGN・ADGROUP・KEYWORDS、ディスプレイは AD の種類で、項目は §4-1 の共通の列 | `ReportDefinitionService` の add → get → download |
| 日次の系列（`get_anomalies`・`measure_effect` の材料） | 同じレポートに `DAY` を足す。直近 N 日は毎回取り直す（§3-4） | 同上 |
| `get_search_terms` | 検索の SEARCH_QUERY（検索回数の少ないクエリーは出ない、P-29） | 同上 |
| `get_keywords` | キーワードとマッチタイプ、除外キーワード | 検索の `AdGroupCriterionService`・`CampaignCriterionService` など（未読 ❓） |
| `get_change_history` | 操作履歴（検索・ディスプレイとも `auditlog` のサービスがある） | `AuditLogService`（中身は未読 ❓） |

- 許可リスト: `config.py` に LINEヤフーの広告アカウント ID を**検索・ディスプレイ別に**足す。ベースアカウント ID も許可リストに入れ、それ以外は API を呼ぶ前に断る（Google と同じ）。
- 書き込みを持たない: 呼んでよい端点を `…/get`・`getReportFields`・`download` と、レポートのジョブの `ReportDefinitionService/add`・`remove`（自分が作ったジョブの後片付け）に限る。テストで「それ以外の端点の文字列がコードに無い」ことを確かめる（Google 側の「変える呼び出しはコードのどこにも無い」テストと同じ考え方）
- 取り込みの作り: ジョブを作って 2〜5 秒おきに見る。上限 5 件／秒なので間隔は十分。403・0003 なら 30 秒待つ（P-09）。60 秒で打ち切る公式 MCP の作りを参考にする
- 列の正規化: §4-1 の左の列（日付・媒体・キャンペーン・表示・クリック・費用〔円〕・成果〔件・値〕）にそろえ、元の項目名も残す。費用は検索が整数・ディスプレイが小数（P-16、P-17）。コンバージョンは「（全て）」と「入札に使う成果」の両方を持ち、ディスプレイは「（クリック経由）」も持つ
- 版: v20 で作り、v21（2026-12-09 予定）の変更を見て上げる。v20 の終了日は ❓（v19 は 2027-01-14 にサポート終了、2027-03 ごろシステム終了）（P-13）

### 6-3. 日次の進捗のスプレッドシート
- 〔推測〕LINEヤフーの分は、**②スクリプトで毎日 9 時に「過去 30 日 × キャンペーン × 日」を取り、Google スプレッドシートの LINEヤフー用のシートを上書き**する形が、申し込みなしで今すぐ作れる。Google 広告の分は Google 広告スクリプトか運用 MCP で同じ形に書き、別のシートで合算する
- スクリプトの上限に収まるか: 実行 10 分、URL リクエスト 10 回、メール 5 通、ログ 100KB（P-21）。キャンペーン × 日の 30 日分は小さいので収まる見込み〔推測〕。過去を長く取りすぎると 10 分を超えることがある（P-25）
- スクリプトの中で検索とディスプレイは `AdsUtilities.getSearchReport`・`getDisplayReport` で別に取る。どちらのアカウントで動いているかは `getProductType()`（SEARCH／DISPLAY／MCC）で分かる。MCC で動かして配下のアカウントのレポートを出すサンプルもある ✅〔公式〕P-26、P-25
- 失敗の知らせは翌日のメールなので、シートの最終更新日時の列を置いて、朝の点検で目で見る〔推測〕
