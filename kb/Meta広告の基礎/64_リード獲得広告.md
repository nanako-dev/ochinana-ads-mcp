## 0. 先に結論（この章で一番効く 10 点）

1. リード獲得広告は 3 つの形がある。**インスタントフォーム**（広告の中のフォーム）、**通話**、**メッセージ**（Messenger・Instagram・WhatsApp の会話に誘導）。この章の中心はインスタントフォーム ✅〔仕様〕（H:1481110642181372）
2. フォームの種類は 3 つ。**大量用（既定）**、**高い意向**（連絡先の欄に「ビジネスから連絡が来る」旨の説明が付き、**送信前の確認画面**が入る）、**リッチクリエイティブ**（色・画像・補足の文。イントロが必須）。**高い意向はモバイルの Facebook フィードと Instagram フィードだけに出て、デスクトップには出ない** ✅〔仕様〕（H:252352181957512、H:1019886738092553）
3. **質問は合計 15 件まで**。1 つ以上の質問が必須。カスタム質問は多肢選択式・短い回答・条件付き回答・販売店情報・予約リクエスト ✅〔仕様〕（H:774623835981457）。**Google のリードフォームの独自の質問は 5 問まで**（G15 2-59）
4. **定型の質問**（メール・電話・氏名・住所・生年月日・勤務先など）は Facebook・Instagram のプロフィールの情報で**事前入力**される。利用者は**生年月日を除いて**編集できる ✅〔仕様〕（H:438193446367413）
5. **プライバシーポリシーのリンクは、日本語のヘルプでは「任意」**（おすすめ）と書かれている。Google のリードフォームは必須（G15 2-55）。**ただしポリシーを置かない理由は無い**（日本の個人情報保護法の利用目的の明示、9 章）✅（H:1019886738092553、H:1550411888622740）
6. **リードをダウンロードできるのは、送信から最長 90 日**。通算の結果を出しても、ダウンロードできるのは過去 90 日分だけ。だから**ダウンロードした件数が管理画面の結果より少ない**ことがある。**CRM につなぐか頻繁に落とす** ✅〔仕様〕（H:1526849577619206）。Google は Google 広告に 60 日保存（G15 2-58）
7. **2026-04 から、CRM 用コンバージョン API の連携なしでは、新しいキャンペーンで「適格リード」のパフォーマンス目標を使えない。既存のキャンペーンも 2026-08 から影響を受ける** ✅〔仕様〕（H:782657799338685）。「質の高いリードに最適化したいなら CRM の連携が前提」になった
8. △ **適格リードはどのフォームで使えるか、公式の中で食い違う**。日本語のヘルプは「ウェブサイトフォームとインスタントフォームの両方で使用できる」、CRM 連携の開発者文書の概要は「今はリード広告（インスタントフォーム）だけ」、同じ文書の FAQ は「インスタントフォームかウェブサイトフォーム」（4-2）。既存の 06§9-3 はインスタントフォーム専用と書いている
9. **インスタントフォームを送信できるのは iOS・Android の Facebook モバイルアプリだけで、Safari・Chrome などのモバイルブラウザーでは送信できない**と書かれている ✅〔仕様〕（H:588763988207510）。条件付きロジック・販売店情報・予約リクエストなどは、機能ごとに出る面が違う（2-6）
10. 質の上げ方の公式の推奨は、**高い意向のフォーム、多肢選択式の質問（多いほど質の高いリード、少ないほど送信数）、短い回答を減らす、類似オーディエンスは「フォーム送信者」ではなく「既存顧客」から、CRM の連携、送信後の完了画面、設問数の A/B テスト**。公式の実績値として、CRM 連携＋適格リード（インスタントフォーム）で高クオリティリードの単価が 21% 減（Meta の自己申告）✅〔公式の推奨〕（H:435270316658768、H:782657799338685）

## 2. インスタントフォームの仕様

### 2-1. フォームの種類 ✅〔仕様〕（H:252352181957512、H:1019886738092553、D:Create）

| 種類 | 中身 | 出る面 | 向く場面（公式） |
|---|---|---|---|
| 大量用（既定） | モバイルで素早く簡単に送信 | ― | 多くのリードを取る |
| 高い意向 | ①連絡先の欄に、ビジネスがフォローアップする旨のインラインの説明 ②**入力した情報を確かめる追加の確認画面** | **モバイルの Facebook フィードと Instagram フィードだけ**。デスクトップには出ない | 販売店での試乗の予約など、意向の高いリード。送信後のフォローアップや絞り込みが要るとき |
| リッチクリエイティブ | カラーテーマ、画像、補足の文（商品説明・プロモーション） | ― | 文脈を詳しく伝え、フォームに個性を持たせる。**イントロの設定が必須** |

- API では `is_optimized_for_quality=true` で「送信前に回答を見直して確定する手順」が入る（＝高い意向）。**既定はリードの量に最適化**と書かれている ✅（D:Create）
- 種類は作成時の [フォームタイプ] で選ぶ（既定は大量用）

### 2-2. 質問 ✅〔仕様〕（H:774623835981457、H:438193446367413、D:Create）

**数**: インスタントフォームに設定できる質問は**合計 15 件**。**1 つ以上の質問が必須**。カスタム質問は広告が承認されてから表示される。

**定型の質問**（プロフィールの情報で事前入力。H:438193446367413）

| 分類 | 項目 |
|---|---|
| 連絡先 | メールアドレス、電話番号、WhatsApp 電話番号、住所、市区町村、都道府県、州、国、郵便番号 |
| ユーザー情報 | 姓と名 |
| 車両情報 | VIN（車両識別番号）、ナンバープレート（**条件を満たす広告主だけ**） |
| 利用者層 | 生年月日、性別、既婚／未婚、交際ステータス、兵役経験 |
| 勤務先 | 役職、職場の電話番号、仕事用メールアドレス、会社名 |
| ナショナル ID | CPF（ブラジル）、DNI（アルゼンチン）、DNI（ペルー）、RUT（チリ）、CC（コロンビア）、CI（エクアドル）、RFC（メキシコ）。**1 フォームに 1 つだけ、その ID の国の人にだけ配信**。形式を確かめるだけで、本物かは確かめない（D:Create） |

- 利用者は**生年月日を除き**、自動入力された情報を編集できる
- プロフィールにメール・電話などが無ければ、手で入力するよう促される
- △ API の文書（D:Create）のナショナル ID の国はアルゼンチン・ブラジル・チリ・コロンビア・エクアドル・ペルーの 6 か国で、ヘルプの RFC（メキシコ）が入っていない。日本向けには関係しない

**カスタム質問の種類**（H:774623835981457）

| 種類 | 中身 |
|---|---|
| 多肢選択式 | 選択肢から選ぶ。**選択肢を減らすために範囲を使う**のが推奨（「2001」「2002」「2003」「2004」の 4 つでなく「2001〜2004」の 1 つ） |
| 短い回答 | 自由回答 |
| 条件付き回答 | 前の質問の答えで、次の質問の選択肢が変わる（2-3） |
| 販売店情報 | 最寄りの店舗・所在地を探せる。**ポートフォリオでページに設定した所在地**を使う（ストアのページの構造が要る。D:Create）。郵便番号を尋ねるなら定型の質問を足す。API で返る値は選ばれた店舗の **Store Number**（D:Retrieving） |
| 予約リクエスト | 予約・来店の日時をリクエストできる。API では `DATE_TIME`、`inline_context` で質問の下に確認の文を出せる（D:Create） |

- API の質問の型（D:Create）: `FULL_NAME`・`FIRST_NAME`・`LAST_NAME`・`EMAIL`・`PHONE`・`CUSTOM`・`DATE_TIME`・ナショナル ID の各型・`STORE_LOOKUP`（`context_provider_type=LOCATION_MANAGER`）。質問の順番は `key` で決まる
- **CRM のためのフィールド名**: CRM やほかのソフトでリードを管理するなら、特定の質問を入れたり、各質問にカスタムのフィールド名を付けたりする必要があることがある（H:1019886738092553）。カスタムのフィールド ID を付けると、API の返す値もその ID になる（D:Retrieving）

### 2-3. 条件付き回答 ✅〔仕様〕（H:154286325106161）

- カスタム質問で作る。**利用者が前の質問にどう答えたかで、表示される回答の選択肢が変わる**。商品・サービスごとに選択肢が違うときに便利
- 例（公式）: 「T シャツとスウェットのどちらを探していますか」→ T シャツなら赤・黄、スウェットなら緑・黒だけを色の選択肢に出す
- 作り方: [質問] → [+ 質問を追加] → [条件付き] → **UTF-8 の CSV**を読み込む（列見出しが質問、各セルが回答。行が組み合わせ）
- 注: **フォームを見る全員に、同じ質問が同じ順番で出る。変わるのは選択肢で、質問は変わらない**
- △ 同じページの冒頭は「条件付き質問では、利用者がその前の質問にどのように回答したかによって、**次の質問やランディングページが変更**されます」とも書く。作成画面には [条件付きロジック] のオン・オフもある（H:774623835981457）。**「条件付き回答」（選択肢が変わる）と「条件付きロジック」（次の質問・行き先が変わる）は別の機能**と読める〔推測〕。条件付きロジックの細目のページは見つけていない ❓

### 2-4. プライバシーポリシー・カスタム免責事項・通知 ✅〔仕様〕

**プライバシーポリシー**（H:1247534515288168、H:1019886738092553）

- [プライバシーポリシー] の欄に URL を入れられる。**日本語のヘルプは「プライバシーポリシーへのリンク(任意)」**、ウェブサイトかアプリに置くことを「おすすめ」と書く
- **PDF・画像・直接ダウンロードするものへはリンクできない**
- **リード獲得広告専用のポリシーを作る必要はない**。今使っているポリシーの URL でよい
- 書くとよい事項（公式の例 8 つ）: 取得する情報の種類／取得した情報の用途／関連会社や第三者と共有するか／顧客が自分の情報を確認・削除できるか／法的要請への対応／ポリシーを変えたときの通知の方法／問い合わせの方法／発効日
- 現地の法律で掲載の場所や方法が決まっていないか確かめる、と公式は書く（日本は 9 章）
- △ 「プライバシーポリシーは必須」という説明は Google のリードフォーム（G15 2-55）や古い解説に多い。**今の Meta の日本語のヘルプは任意**。リード獲得広告の利用規約・広告規定の側で必須かは、今回本文で確かめていない ❓

**カスタム免責事項**（H:1550411888622740）

- Facebook のプライバシーの免責事項に加えて、広告主が同意を求める法的な通知・免責事項を足せる。**プライバシーの免責事項とカスタム免責事項の追加は、どちらも任意**
- **チェックボックス**を入れられる（例: 個人情報を共有する許可を求める）。必須にしないなら [任意] にする。複数のチェックボックスも作れる
- **免責事項を足すと、利用者は同意しない限りフォームを送信できない**
- **すでに広告で使っているフォームには、カスタム免責事項を足せない**。フォームを複製して足す
- API では、チェックボックスの回答は `field_data` に入らず、`custom_disclaimer_responses`（`checkbox_key`・`is_checked`）で別に返る（D:Retrieving）

**適切に明示された通知**（H:1019886738092553）

- 連絡先を集める理由と、その情報の使い方・共有の仕方を利用者に明確に知らせることを推奨。フォーム作成の [質問] で設定する
- **リード獲得広告で連絡先を集めた目的に合うときだけ**、利用者にメッセージを送る

### 2-5. イントロ・完了画面・そのほかの設定 ✅〔仕様〕

| 設定 | 中身 | 出典 |
|---|---|---|
| イントロ | 任意。商品・サービスの説明、送信で何が得られるか。**リッチクリエイティブでは必須** | H:1019886738092553 |
| 完了画面（サンクスページ） | 送信後の画面をカスタマイズし、次の行動を促す。API の `thank_you_page`（`title`・`body`・`button_type`・`button_text`） | H:435270316658768、D:Create |
| 限定コンテンツ（ゲーテッド） | 送信後にファイルのダウンロードを報酬にする。API の `upload_gated_file` と、完了画面の `button_type=VIEW_ON_FACEBOOK` | D:Create |
| トラッキングパラメーター | リードの出どころを追う鍵と値。**広告には表示されない** | D:Create、H:357992214682464（目次から） |
| オーガニックのリードの除外 | API の `block_display_for_non_targeted_viewer=true`。画面では [シェア] を [制限]（既定）（2-7） | D:Create、H:1131888990173231 |
| 言語 | フォームの言語を変えられる | H:144047185946009（目次から。本文未取得） |

### 4-3. 運用の判断への効き方

- **質を最適化したいなら、CRM の連携は「後でやる」ではなく最初の設計に入れる**。2026-04 からは連携なしで新しく適格リードを選べない（4-1）
- **月 200 件に届かない商材**は、Meta の目安（4-2）に届かない。この場合も連携自体はできるが、学習が進むかは ❓。まずリード数の最大化＋フォームの質の対策（6 章）で、CRM 側で質を測る〔推測〕
- **最適化の段階は「最も早い良い段階」**（例: 商談化）。成約は遅く、数も少ない。Meta はその下の段階にも最適化すると書く（4-2）
- **テストのリード・社内の送信を CRM のイベントに混ぜない**。ファネルの「その他の段階」に外す（4-2 の公式の例はテストのイベント）

## 5. リードの取り出し

### 5-1. 取り出し方の一覧 ✅〔仕様〕（H:734933888443065、D:Lead Ads、D:Retrieving、D:Connecting CRM）

| 方法 | 中身 | 向く場面 |
|---|---|---|
| 広告マネージャ | CSV でダウンロード | 少量・手作業 |
| Business Suite の [インスタントフォーム] ページ | CSV でダウンロード。**オーガニックのリードはこちらだけ** | 同上 |
| Business Suite のリードセンター | リードの管理・ダウンロード、リードタブでチャット | 少数の営業チーム |
| 広告マネージャのアプリ | モバイルでリードの表示・管理 | 外出先での確認 |
| CRM のパートナー連携 | 対応する CRM・ツール（Mailchimp・Salesforce など。H:908902042493104 に一覧）。Zapier でもつなげる | 開発なしで自動化 |
| Webhooks（リアルタイム） | 新しいリードのたびに通知（`leadgen_id`・`page_id`・`form_id`・`adgroup_id`・`ad_id`・`created_time`）→ `leadgen_id` で中身を取る。成功時の遅れは**最大数分** | 自社の CRM へ即時に流す |
| Graph API の一括読み取り | 広告ごと（`/{AD_ID}/leads`）かフォームごと（`/{FORM_ID}/leads`）。**フォームは複数の広告で使い回せるので、フォームの方が広告より多くのリードを持ちうる** | 1 日に数回まとめて取る |
| CSV の書き出し API | `/ads/lead_gen/export_csv/` にフォーム ID と期間（`from_date`・`to_date`、UNIX 時刻） | 期間を区切って取る |

- 公式の CRM 連携の手引きは、**手動のダウンロードは推奨しない**（CRM のイベント送信と組むなら特に）。パートナー・Webhooks・一括読み取りに問題があるときの一時しのぎとする（D:Connecting CRM）
- どの方法でも、**15〜17 桁の Meta のリード ID** をダウンロードのデータに入れる（適格リードのため。4-2）

### 5-2. 90 日の窓（期限切れのリード）✅〔仕様〕（H:1526849577619206）

- **リードのデータをダウンロードできるのは、送信から最長 90 日**
- 広告マネージャの [結果] 列やページの [リード獲得数] は選んだ期間の新規のリードの総数を出すが、**ダウンロードできるのは過去 90 日に送信されたものだけ**。キャンペーンの通算の結果を見ていても同じ
- 理由は「セキュリティと保管上の理由」。Meta は「90 日はほとんどの場合に十分」「それ以上たつと顧客の興味が薄れる」と書く
- 推奨: **リードを頻繁にダウンロードするか、CRM システムを使う**
- メッセージ（ページの受信箱）は 90 日たっても消えない（3 章）
- 〔推測〕API の一括読み取り・Webhooks で 90 日より古いリードを取れるかは、開発者文書に明記が無い ❓。API の呼び出しの上限の式に「過去 90 日に作られたリードの数」が使われている（5-4）ので、同じ窓と見て設計する

### 5-3. 数が合わないときの理由 ✅（H:1526849577619206、H:1131888990173231、D:Retrieving）

| ずれ | 理由 |
|---|---|
| ダウンロード ＜ 管理画面の結果 | 90 日を過ぎたリードはダウンロードできない |
| ダウンロード ＞ 管理画面の結果 | オーガニックのリード（[結果] に含まない）、テストのリード（[結果] に数えない） |
| CSV に広告 ID が無い行 | オーガニック、広告のプレビューからの送信、**取り出す人が広告アカウントの広告主の権限を持っていない** |
| フォームの件数 ＞ 広告の件数 | フォームを複数の広告で使い回している |
| 対象の地域の外からのリード | 配信の地域の判定は完全ではなく、設定した地域以外からリードが来ることがある（H:734933888443065） |

### 5-4. API の権限と上限 ✅〔仕様〕（D:Lead Ads、D:Retrieving、D:Create）

- **前提**: Facebook ページが必須。**リードはページに属す**（Instagram で出しても、リードはページのもの）。Instagram アカウントは Instagram に出すときだけ
- **アプリの審査**: リードを取るには `leads_retrieval` と `pages_manage_ads` の審査、その後に**ビジネス認証**
- **開発モードのアプリではリードを取れない**（同じアプリの役割を持つ人が送ったリードだけ）。ライブモードで全リード
- **トークン**: ユーザーのトークンはアプリのアクティブな利用者の数で上限が決まる（ふつう 1 人）ので、**ページのトークン**を使う。Webhooks は**長期のページのトークン**とアプリのページへのインストールが要る
- 要る許可: 全リードと広告の情報を取るには `ads_management`・`leads_retrieval`・`pages_show_list`・`pages_read_engagement`・`pages_manage_ads`（Webhooks なら `pages_manage_metadata` も）。広告とページで広告を出せる人のトークン
- **呼び出しの上限**: 1 つのページについて **200 × 24 × 過去 90 日に作られたリードの数** を 24 時間で超えると誤り
- 一括読み取りの絞り込み: `time_created` で `LESS_THAN`・`GREATER_THAN`・`GREATER_THAN_OR_EQUAL`
- フォームを作る許可: `ads_management`・`pages_manage_ads`・`pages_read_engagement`・`pages_show_list` と、ページで `ADVERTISE` のタスクができる人のページのトークン

### 5-5. リードへのアクセスを絞る（リードアクセス）✅〔仕様〕（H:1440176552713521、D:Retrieving）

- リードアクセスで、**ポートフォリオのフルアクセス許可の人が**、リードをダウンロードできる人・CRM・パートナーを決められる
- **絞っていないときの既定**: ページの管理者全員か、メッセージのアクセス許可を持つ人がダウンロードできる
- **絞ると、新しい人・CRM・パートナーは手で足す**必要がある（足し忘れると CRM の連携が止まる〔推測〕）
- 公式の想定: ページの管理者全員や、ページの権限を持つ第三者にリードを見せず、特定の社員だけに限りたい組織
- 権限全体は `27_アカウント管理と安全.md` §3

### 5-6. テストのリード ✅〔仕様〕（D:Testing）

- **リード獲得広告のテストツール**（developers.facebook.com/tools/lead-ads-testing）。開発者モードでは使えない
- **1 つのフォームに作れるテストのリードは 1 件**。作り直すには先に消す。テストのリードはオーガニック扱いで広告に紐づかない
- API の `POST /{FORM_ID}/test_leads`: テストのリードが無いこと、フォームを持つページで広告主以上のページの役割、ページのトークン
- 消せるのはリードの持ち主だけ
- Webhooks の届き方を [Track Status] で見られる（pending → success／failed と誤りの番号）

### 5-7. 運用の判断への効き方

- **リードは「放っておくと消える」前提で、初日から自動で外へ出す**。90 日の窓（5-2）
- **数のずれの問い合わせは 5-3 の表から**。オーガニックとテストは [結果] に入らない
- **CRM の連携が止まる原因は権限**〔推測〕。リードアクセスを絞った、担当者のトークンが切れた、アプリが開発モード、のどれか。システムユーザーで組む（27§3-5）
- **返信は速く**: 公式にはリードへの返信のベストプラクティスの記事がある（H:2246428158756947、本文未取得 ❓）。〔推測〕フォームの完了画面と最初の連絡の時刻を、CRM の段階の時刻として送れば、適格リードの学習にも効く

## 6. リードの質の上げ方（公式の推奨）

### 6-1. 広告とキャンペーンの側 ✅〔公式の推奨〕（H:435270316658768）

| 推奨 | 中身 |
|---|---|
| 魅力のある画像・動画と CTA | フォームを開くよう促す必要がある。**フォームに記入するメリットが明確に伝わる**広告にする |
| 予算をチームの対応量に合わせる | 短期間に大量のリードを取ると、営業・コールセンターが追いつかない。Advantage+ キャンペーン予算で**広告スケジュール**を使い、チームが対応できるようにする |
| Advantage+ 配置で Facebook・Instagram・WhatsApp に出す | リーチを広げる。Instagram では一部の機能が使えない。**過去 12 か月にブランドセーフティと適合性のコントロールを使った広告主は、WhatsApp ステータスの配置が自動でオプトアウト** |
| 類似オーディエンスは既存の優良顧客から | **フォームを送信した人ではなく、既存の顧客に基づく**オーディエンスを推奨。価値の高い人に届く |
| 途中でやめた人に再び届ける | エンゲージメントのカスタムオーディエンスで、**フォームを開いたが送信しなかった人**に（保持の最大は 90 日。M-ターゲティング-039） |
| CRM をつなぐ | 適格リード（4 章） |

### 6-2. フォームの側 ✅〔公式の推奨〕（H:435270316658768）

| 推奨 | 中身 |
|---|---|
| イントロを使う | ビジネスの情報と、送信で得られるメリット |
| 簡潔にする | 質問を多くしすぎない。目標に沿った質問だけ、数はできるだけ少なく |
| 定型の質問を足す | 事前入力で送信が簡単になる |
| **多肢選択式で質を上げる** | 購入の予定・希望の製品などを尋ねる。**多肢選択式の質問が少ないと送信数が多くなり、多いと通常は質の高いリードが多く取れる** |
| 短い回答を減らす | 複数の情報を打たせると送信されない原因。多肢選択式で同じ情報を集める |
| 完了画面を使う | 送信後に次の行動を促す |
| クーポンコード | フォームの最後に載せ、サイトへ来る動機にする |
| 設問数を変えて A/B テスト | **完了率・リード単価・コンバージョン単価**を、設問数ごとに測る |

### 6-4. 運用の判断への効き方

- **「数」と「質」はフォームの設計で引き換え**（6-2 の公式の記述）。最初は大量用で量を見て、CRM で商談化率が低ければ、高い意向・多肢選択式の追加・短い回答の削減の順で締める〔推測〕
- **類似オーディエンスの種は「フォーム送信者」ではなく「成約した顧客」**（6-1）。送信者を種にすると、送信しやすい人（＝質の低い人）に寄る〔推測。根拠は公式の推奨の理由の記述〕
- **営業の対応量で予算を決める**（6-1）。リードの単価が安くても、48 時間以内に連絡できない量を取ると成約率が落ちる〔推測〕
- 「品質が先、入札は後」の順（運用の型）: リードの質が悪いときに入札・予算をいじる前に、フォーム（6-2）と最適化の目標（4 章）を直す

## 7. 禁止の質問と規定（34 と重ならない範囲で）

### 7-1. インスタントフォームで禁止されている質問 ✅〔仕様〕（H:219356599612120）

前提: インスタントフォームを作って出す前に、**リード獲得広告の利用規約に同意**する。すべての広告は広告規定に従う。広告規定により、次の情報を求める質問やテキストは**禁止**（「〜を含むがこれらに限定されない」）。

| 分類 | 例（公式） |
|---|---|
| アカウント番号 | フリークエントフライヤー・ポイントカード・ケーブルテレビや電話の番号 |
| 犯罪歴・逮捕歴 | ― |
| 財務関連 | クレジット・デビットカードの番号、銀行口座、ルーティング番号、クレジットスコア、純資産、**収入**、破産・負債の状況 |
| 政府発行の識別番号 | 社会保障番号、**運転免許証番号**、写真付き身分証の番号、パスポート番号、軍の身分証の番号 |
| 健康 | 本人・家族の現在・過去の身体・精神の疾患、治療・投薬の副作用、病状・障がい |
| 保険 | 保険会社名、プランの詳細、使用状況、証券番号 |
| 政治観 | 投票先、候補者を応援しているか |
| 人種・民族 | ― |
| 宗教・哲学の信条 | ― |
| 性的指向・性生活 | ― |
| **定型の質問とまったく同じか非常によく似た情報** | （定型の質問の欄を使う） |
| 労働組合への加入 | ― |
| **ログイン情報** | 新規・既存のアカウントのユーザー名やパスワード |
| **子どもの生年月日** | ― |

- 違反の質問が見つかると、**リード獲得広告は掲載されない**
- △ 34 の M45 は広告規定の入口の要約として「事前の書面の許可なしに、一部の種類の情報を質問で求めてはいけない」と書く。このヘルプは同じ種類を「禁止」と書き、許可の道に触れない。**日本向けの運用では「聞けない」と扱う**〔推測〕
- 〔推測〕日本の運用で引っかかりやすいのは、**「年収」「借入額」（財務）**、**「持病」「お悩みの症状」（健康）**、**「ご加入中の保険会社」（保険）**、**「メールアドレスをもう一度」（定型と同じ）**。金融の業種の個人情報・金融情報の扱いは 34§2-11

### 7-2. 米国・カナダ向けの住宅・雇用・金融の制限 ✅〔仕様〕（H:1481110642181372）

- 差別につながる行為を防ぐため、**米国の、または米国とカナダをターゲットにする住宅・雇用・金融商品とサービス**のリード獲得広告では、**年齢・性別・配偶関係・交際ステータス**などの個人の情報と、**住所・市区町村・郵便番号**などの位置の情報を集めることが禁止
- カスタムのフィールドでサービスの提供場所の希望を尋ねるのはよいが、禁止の自動入力の質問をまねたり、禁止の情報を尋ねたりしてはいけない
- 日本向けだけの運用では直接は関係しない。北米にも出す日本企業は注意

### 7-3. 審査と編集

- カスタム質問は**広告が承認されてから**表示される（H:774623835981457）。審査の時間と再審査の引き金は 34§1
- **使用中のフォームにはカスタム免責事項を足せない**（2-4）。フォームの編集の細目のページ（H:1025066254239352）は本文未取得 ❓。〔推測〕使用中のフォームは中身を変えにくい前提で、直すときは複製して新しい広告に付ける（審査と学習のやり直しを織り込む）

## 9. 日本の個人情報保護との関係（地図だけ。法律の助言ではない）

条文は e-Gov 法令 API で 2026-11-22 に取得した（個人情報の保護に関する法律〔平成十五年法律第五十七号〕、特定電子メールの送信の適正化等に関する法律〔平成十四年法律第二十六号〕）。当てはめは書き手の読み〔推測〕で、判断は専門家に確かめる。

| フォームの場面 | 当たりうる条文（見出し） | 条文の要点（原文の要約） | フォームでの手当て〔推測〕 |
|---|---|---|---|
| フォームで氏名・連絡先を集める | 個人情報保護法 第 21 条（取得に際しての利用目的の通知等）第 2 項 | 本人から直接、書面（**電磁的記録を含む**）に記載された個人情報を取得する場合は、**あらかじめ本人に利用目的を明示**しなければならない | フォームの「適切に明示された通知」（2-4）とイントロに利用目的を書く。プライバシーポリシーの URL を入れる（Meta の上では任意でも） |

| 健康・病歴などを聞きたくなる | 同 第 2 条第 3 項（要配慮個人情報の定義）、第 20 条（適正な取得）第 2 項 | 人種・信条・社会的身分・病歴・犯罪の経歴などは要配慮個人情報で、法令の例外を除き**あらかじめ本人の同意**なしに取得してはならない | そもそも Meta のフォームで健康・犯罪歴・人種・宗教などは**禁止**（7-1）。聞かない |
| CRM・代理店・提携先にリードを渡す | 同 第 27 条（第三者提供の制限） | 原則、本人の同意なく個人データを第三者に提供してはならない（例外の規定がある） | 誰に渡すかをポリシーとカスタム免責事項に書く。委託・共同利用の扱いは同条の規定で確かめる |
| 海外の CRM・ツールに入れる | 同 第 28 条（外国にある第三者への提供の制限） | 外国にある第三者への提供の制限 | 使うツールのサーバーの所在と、条の要件を確かめる |
| 集めたメールに広告のメールを送る | 特定電子メール法 第 3 条（特定電子メールの送信の制限） | 送信者は、**あらかじめ送信を求める旨か同意する旨を通知した者**など、条に掲げる者以外に特定電子メールを送ってはならない。同意の記録の保存（同条第 2 項） | カスタム免責事項の**チェックボックス**で、メールマガジン等の受信の同意を別に取る（必須にしないなら [任意]）。API の `custom_disclaimer_responses` を CRM に残す（同意の記録） |

- 景品表示法・特定商取引法（申し込みの表示）など、広告の中身の法令は `../Google広告の基礎/31_日本の広告法規とポリシー.md`（G31）と 31 の地図
- Meta の側の規定（禁止の質問）と日本の法令は別に効く。**Meta で通ったから法令上よい、ではない**（34 と同じ考え方）

## 12. 少額・少量のアカウントでの注意〔推測〕

- 月 200 件に届かないなら、適格リードの目安（4-2）に届かない。まず「リード数の最大化」＋高い意向のフォーム＋多肢選択式 2〜3 問で、CRM（スプレッドシートでもよい）に成約の結果を付ける
- リードが少ないうちは、手作業のダウンロードで回しがち。**90 日の窓**を忘れない。週 1 回のダウンロードを予定に入れるか、Zapier などで自動で流す
- 営業が 1 人なら、予算を絞り、広告スケジュールで対応できる時間帯に寄せる（6-1）

## 13. 判断の型

| 状況 | まず見るもの | 次の手 |
|---|---|---|
| リードの数は出るが質が悪い | CRM の段階ごとの転換率、フォームの種類、質問の構成 | 高い意向 → 多肢選択式を足す → 短い回答を減らす → 適格リード（CRM 連携） |
| リードが少ない・単価が高い | 設問数、イントロ、広告の訴求、配置 | 設問数の A/B テスト（完了率・単価）、定型の質問の活用、Advantage+ 配置 |
| 数が合わない | 90 日、オーガニック、テスト、フォームの使い回し | 5-3 の表 |
| CRM につなぎたい | CRM の対応、開発の手、件数 | パートナー → Zapier → Webhooks の順。リード ID を残す |
| 適格リードを使いたい | 月の件数、成約までの日数、段階の数 | 4-2 の条件。2026-04 以降は CAPI 連携が先 |
| 審査で落ちた | 禁止の質問、業種の規定 | 7-1 と 34 |
| 北米にも出す | 住宅・雇用・金融か | 7-2 の禁止の項目を外す |
| フォームを直したい | 使用中か | 複製して新しい広告に付ける（審査・学習のやり直しを織り込む） |

## 14. 既存の章との食い違い・補足

- **06§9-3・rules.csv M-計測-063・06 の思い込み表（583 行目）・90 の 389 行目** は、CRM 用 CAPI の「コンバージョンリード」（日本語のヘルプでは「適格リード」）を**インスタントフォーム専用**と書く。今回読んだ日本語のヘルプ（H:782657799338685）は「ウェブサイトフォームとインスタントフォームの両方で使用できる」、開発者文書の FAQ も「インスタントフォームかウェブサイトフォーム」。開発者文書の概要だけが「今はインスタントフォームだけ」。

- **2026-04・2026-08 の適格リードの変更**（CAPI 連携が前提）は、既存の章に無い新しい事実
- **34 の M45**（事前の書面の許可）と、このヘルプの「禁止」の書き方の違いは 7-1 に △ で書いた。34§14 の ❓（事前許可が要る質問の種類の一覧）は、このヘルプの一覧で埋められる
- **00§8-2** は「リード獲得広告（管理画面の名前は ❓）」と書く。管理画面の名前は「リード獲得広告」、フォームは「インスタントフォーム」（H:1481110642181372）
