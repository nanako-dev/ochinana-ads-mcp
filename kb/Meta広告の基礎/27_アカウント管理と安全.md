## 0. 先に結論（この章で一番効く 10 点）

1. **権限は 2 段で考える**。ビジネスポートフォリオ（会社の器）への権限と、ビジネスアセット（ページ・広告アカウント・Instagram など）への権限は別。どちらにも「フルアクセス許可」と「部分的なアクセス許可」がある。**ポートフォリオのフルアクセス許可が無くても、アセットのフルアクセス許可は持てる** ✅〔仕様〕（H:442345745885606）
2. ポートフォリオの部分的なアクセス許可は「**基本**（旧 従業員。追加したときの既定）」と「**アプリと統合**（旧 開発者。CAPI の設定・アクセストークンの作成）」。**お金を見る・動かす権限（財務）は別の「詳細オプション」で、フルアクセス許可にも既定では含まれない** ✅〔仕様〕（H:442345745885606）
3. **一時的なアクセス**を付けられる。基本のアクセス許可だけで、期間は **3 日〜75 日**。期限が来ると自動で外れ、ポートフォリオと割り当てたアセットから消える。短期の外注・検証に使う ✅〔仕様〕（H:442345745885606）
4. **システムユーザー**（人ではない API 用の利用者）は、アプリのアクセスの段階で数が決まる。標準アクセスでシステムユーザー 1・管理者システムユーザー 1、高度なアクセスでシステムユーザー 10・管理者システムユーザー 1。トークンは作った画面でしか見られない ✅〔仕様〕（D:System Users overview、D:Generate access token）
5. 認証は 4 種類あり、名前が似ていて取り違えやすい。**二段階認証**（人のログイン）／**ビジネス認証**（会社が実在するか。最大 14 営業日）／**広告主の認証**（広告の透明性のため、誰が宣伝し誰が払うか。34§6-6）／**業種・SIEP の認証**。さらに API でリードを取るアプリには、アプリの審査のあとにビジネス認証が要る ✅（H:865384580786591、H:2058515294227817、H:983527276402621、D:Lead Ads）
6. 支払いは大きく 2 つ。**自動請求**（支払い単位額に達したときと毎月の請求日に請求。PayPal・主要なクレジットカード・デビットカード）と**利用可能残高**（前払い。1 日 1 回を上限に引き落とし）。条件を満たす会社には**月極請求書払い**（クレジットライン、支払い期限は請求書の発行日から 30 日後）がある ✅〔仕様〕（H:716180208457684、H:2086865811541431）
7. **日本の消費税の扱いを書いたヘルプのページは見つからなかった**。ヘルプの検索では米国・インド・シンガポール・オーストラリアなど十数か国の税のページが出るが、日本は無い ❓。API には `tax_id`・`tax_id_status`・`is_tax_id_required` がある ✅（D:Ad Account）。日本の扱いは請求書・領収書の表記で確かめる（16 章）
8. **広告アカウントはポートフォリオから消せない。閉鎖するだけ**。閉鎖すると配信は全部止まり、未払いはカードに請求され、支払い方法が外れる。処理に数日かかる。セキュリティの公式の推奨は「**過去 1 年広告を出していない広告アカウントを閉じる**」「**90 日ログインしていない人を外す**」「**フルアクセス許可は理想は 10 人以下、アクティブな人を 2 人**」 ✅（H:190760004667059、H:608572510632070）
9. **ピア承認**で、公開前に信頼できる人の 2 回目の確認を入れられる。保護の段は「デフォルト（不審な広告だけ）」「追加（すべての広告）」「カスタム（選んだ予算を超える広告）」。ほかに**信頼できるドメインのリスト**（リスト外の URL の広告は承認が要る）と、メッセージ誘導広告をまとめて承認制にする設定がある ✅〔仕様〕（H:529947753306370）
10. **変更の追跡はアクティビティ履歴**（誰が・いつ・何を）。変更者の欄に、人の名前・自動ルールの名前・ビジネスアイデンティティ・「Meta」（審査の仕組みや削除された人の変更）が出る。**何日さかのぼれるかは公式に書かれていない** ❓（Google は管理画面 2 年・API 30 日、G27 0 章）✅（H:289211751238030）

## 1. Google（G27）との対比

| 本人確認 | 広告主の適格性確認（G15 §7） | ビジネス認証・広告主の認証・二段階認証・業種の認証が別々 ✅（4 章） | Meta は「どの認証を求められているか」を通知の文面で確かめてから動く |

## 2. 器と所有

### 2-1. 何がどこに属すか ✅〔仕様〕

- ビジネスポートフォリオは、ページ・Instagram アカウントなどのアセットをまとめて 1 か所で管理し、それに携わる人のアクセスを管理する器（H:442345745885606）。旧称はビジネスマネージャ（00§2-1）
- アセットの種類は 14（H:1242256693745272）: ページ、広告アカウント、Instagram プロフィール、Threads プロフィール、アプリ、データセットとピクセル、コマースアカウント、カタログ、WhatsApp アカウント、カスタムコンバージョン、オフラインイベントセット、ビジネスアセットグループ、パブリッシャーブロックリスト、プロパティ
- **人をポートフォリオに入れただけでは何も触れない**。アクセスを始める前に、その人が管理するページ・広告アカウント・カタログなどのアセットを割り当てる必要がある（H:1242256693745272）
- アセットは 1 つのポートフォリオにだけ属す。1 人が作れるポートフォリオは 2 つまで、1 人が管理できる広告アカウントは 25 まで、1 つの広告アカウントに割り当てられる人は 25 まで（00§2-1、M-アカウント-002・003・007・008）

### 2-2. 広告アカウントの閉鎖（消せない、閉じる）✅〔仕様〕（H:190760004667059）

| 項目 | 中身 |
|---|---|
| 誰ができるか | ポートフォリオか広告アカウントのフルアクセス許可を持つ人。閉じられるのは**そのポートフォリオが所有する広告アカウントだけ**。パートナーが所有するものなど、別のポートフォリオに属する広告アカウントは閉じられない |
| 削除 | **広告アカウントをポートフォリオから削除することはできない**。使っていない広告アカウントは閉鎖して不正利用から守る |
| 閉じると | 現在のキャンペーンがすべて止まり、再開も新しい作成もできない。クリエイティブ・配信結果・請求などの履歴は見られる。**未払い残高はクレジットカードに請求され、その後、登録された支払い方法が削除される** |
| 時間 | 閉鎖には数日かかることがある。処理待ちの間は取り消せる |
| 戻せるか | 閉鎖した広告アカウントは、再開できる場合とできない場合がある（条件は記載なし ❓） |
| 場所 | Meta Business Suite の [設定] → [アカウント] の [広告アカウント] → 名前 → [利用解除]。ポートフォリオに入っていない広告アカウントは広告マネージャで閉じる |

- △ セキュリティのベストプラクティスのページ（H:608572510632070）は「アクティブでない広告アカウントを**閉鎖または削除**しましょう」と書き、同じ段落の注で「広告アカウントをポートフォリオから**削除することはできません**」と書く。閉鎖のページ（H:190760004667059）も「削除することはできません」。**実際に取れる手は閉鎖**と読む
- 閉じた広告アカウントも作成数の上限に数える（00§2-1、M-アカウント-009）

### 2-3. 運用の判断への効き方

- **広告アカウントは広告主のポートフォリオで作る**〔推測〕。代理店のポートフォリオで作ると、契約が終わったとき広告主の側から閉じることも、履歴を持ち帰ることもできない（パートナー所有のものは閉じられない、2-2）。履歴（学習のもと、過去の成果）を持ち帰れないのは大きい
- **使っていない広告アカウントは閉じる**〔公式の推奨〕。Meta は「悪質行為者は過去 1 年間に広告を掲載していない広告アカウントを狙う可能性が高い」と書く（H:608572510632070）
- 閉じる前に未払いを払う。閉じると支払い方法が外れる（2-2）

## 3. 権限

### 3-1. ポートフォリオへの権限 ✅〔仕様〕（H:442345745885606）

| 段 | 名前（旧称） | できること |
|---|---|---|
| フル | フルアクセス許可（旧 全権限・ビジネス管理者） | ポートフォリオの設定・メンバー・ツール・アセットのすべてを管理。アセットやメンバーを取り込む・外す、パートナーと共有したアセットへのアクセスを管理、ポートフォリオ内のすべてのアセットを見る、ポートフォリオを削除、詳細オプションを自分に割り当てる。**ポートフォリオ内のすべてのアセットに自動で割り当てられる**ので、広告の公開や支払い情報の更新もできる |
| 部分 | 基本（旧 従業員） | 割り当てられたアセットだけで作業。**メンバーを追加したときの既定**。フルアクセス許可の人が誰かは見られる |
| 部分 | アプリと統合（旧 開発者） | コンバージョン API の設定、イベントのモニタリング、アプリの編集、アクセストークンの作成 |
| 追加 | 詳細オプション: 財務 | 取引・請求書・消化額・支払い方法などの財務情報を見る・管理する。フルアクセス許可・部分的なアクセス許可のどちらにも足せる。**フルアクセス許可でも既定では含まれない** |
| 期限付き | 一時的なアクセス | **基本のアクセス許可だけ、3 日〜75 日**。期限で自動的に外れ、ポートフォリオと割り当てたアセットから削除される |

- 注: ポートフォリオの財務のアクセス許可は、Meta Business Suite の「支払いアカウントの財務管理者」とは別物（H:442345745885606）。後者は収益化（パブリッシャー側の受け取り）の支払いアカウントの役割で、追加するには相手と Facebook 上で友達である必要がある（H:135977643706045）。広告の支払いとは系統が違う
- 開発者文書では、月極請求書払いの上限の引き上げや、管理者システムユーザーに付ける財務の役割を「**ファイナンスエディター（Finance Editor）**」と書く（H:2086865811541431、D:Create system user）。画面の「財務」の詳細オプションとの対応は書かれていない ❓

### 3-2. アセットへの権限 ✅〔仕様〕（H:442345745885606、H:1242256693745272）

- アセットにも**フルアクセス許可**と**部分的なアクセス許可**がある。アセットのフルアクセス許可は、そのアセットで使えるすべての許可（**削除を含む**）と、すでに割り当てられた人の許可の管理
- **ページ・Instagram プロフィール・WhatsApp アカウント・コマースアカウント・カタログ**のフルアクセス許可を持つ人は、ポートフォリオのフルアクセス許可が無くても、ほかのメンバーに許可を付けられる（広告アカウントはこの列挙に入っていない）
- 部分的なアクセス許可は、担当するタスクを選んで付ける

**広告アカウントのタスク**（H:1242256693745272 の表の項目）

| タスク | 中身（ページの説明文） |
|---|---|
| キャンペーンの管理 | 広告を作成・編集する |
| パフォーマンスを確認する | レポートを表示する |
| クリエイティブハブのモックアップを管理する | クリエイティブハブでモックアップを表示・作成・編集する |
| 広告アカウントを管理する | 広告アカウントの設定、財務、アクセス許可を管理する |

- 表には「広告を閲覧する」の行もある。どのタスクにどの行が含まれるかの対応（チェックの位置）は、取得した本文の文字だけでは読み切れなかった ❓（ページの表を画面で見て確かめる）
- 支払い方法の編集には、**ポートフォリオに入っている広告アカウントでは広告アカウントのフルアクセス許可**、広告マネージャで権限を管理している広告アカウントでは**管理者権限**が要る ✅（H:132073386867900）

**ほかのアセットのタスク**（同じページ）

| アセット | タスク |

### 3-3. API の名前（タスクの英語名）✅〔仕様〕（D:Ad Account、D:Ad Account Assigned Users）

- 広告アカウントに人を割り当てる API（`/act_{id}/assigned_users`）のタスクは `MANAGE`・`ADVERTISE`・`ANALYZE`・`DRAFT`・`AA_ANALYZE` の 5 つ
- 割り当てた人の読み取りでは `tasks`（その人の役割・タスクを展開したもの）と `permitted_tasks`（付けられるタスク）が返る。`summary` の `total_count` は割り当てられたビジネスユーザーとシステムユーザーの数
- 項目によって要るタスクが違う: `funding_source_details`（支払い方法の詳細）は **`MANAGE`**、`is_prepay_account`・`is_tax_id_required` は `ADVERTISE` か `MANAGE`
- 〔推測〕画面のタスクとの対応は、`MANAGE`＝広告アカウントを管理する、`ADVERTISE`＝キャンペーンの管理、`ANALYZE`＝パフォーマンスを確認する、と読める。公式の対応表は見つけていない ❓

### 3-4. パートナー（代理店）への共有 ✅〔仕様〕

- パートナーを入れる方法は 2 つ: **パートナーに自社のアセットへのアクセスを付ける**／**パートナーにアセットを自社と共有するよう頼む**（H:708679622611131）
- パートナーの業務で共有アセットの部分的なアクセス許可を持つ側は、自社のメンバーに**自社が担当する特定のタスクのアクセス許可だけ**を割り当てられる（H:442345745885606）。つまり代理店は、広告主から渡された範囲より広い権限を自社の社員に配れない
- 広告アカウントには、代理店が広告主の代わりに出している場合の申告（`agency_client_declaration`）の項目がある。読むにはポートフォリオの管理者の権限が要る（D:Ad Account）
- 他の広告主（クライアント）の広告はクライアントごとに別の広告アカウントで管理し、既存の広告アカウントの広告主は変えられない（M-アカウント-025）
- パートナーが持つ広告アカウントは閉じられない（2-2）

### 3-7. 運用の判断への効き方

- **最小の権限で渡す**〔公式の推奨〕。Meta は「業務上必要となるアクセス許可のみをメンバーに付与する」と書く（H:442345745885606）。運用担当にはアセットの部分的なアクセス許可（キャンペーンの管理・パフォーマンスを確認する）、計測担当にはアプリと統合とデータセットの管理、経理には財務、と分ける〔推測〕
- **お金を触れる人を数える**。財務の詳細オプション、広告アカウントのフルアクセス許可（支払い方法の編集）、Instagram の「すべて」（支払い方法を含む）が、お金に触れる入口〔推測。根拠は 3-1・3-2 の公式の記述〕
- **短期の外注には一時的なアクセス**（3〜75 日）。外し忘れが起きない
- Google の「標準」に慣れていると、Meta の「アセットのフルアクセス許可」を「標準」相当と思いがち。**Meta のアセットのフルアクセス許可は、削除と人の管理まで含む**（3-2）

- 広告アカウントの制限の理由の 1 つにもなる（34§6-1 の段 3、M-アカウント-011・022）

## 5. 支払い

### 5-1. 支払いの設定は 2 つ＋月極請求書払い ✅〔仕様〕（H:716180208457684、H:2086865811541431）

| 設定 | 仕組み | 使える支払い方法 | 支払い単位額 |
|---|---|---|---|
| 自動請求 | 支払い単位額に達したときに自動で請求。残りは毎月の請求日に請求 | PayPal、主要なクレジットカード、デビットカード | あり |
| 利用可能残高（前払い） | 事前に残高へ資金を入れ、広告を出すと **1 日 1 回を上限に** Meta が残高から引き落とす。自動チャージも設定できる | クレジットカード、デビットカード、地域の決済方法 | 通常は無い（自動請求と両方に設定している場合を除く）。残高に足せる額や 1 日の消化額に制限が付くことがある |
| 月極請求書払い | 条件を満たす会社がクレジットラインで払う。消化額を毎月 1 通の請求書にまとめる | 銀行引き落とし（米国と SEPA のみ）、銀行振り込み、Boleto（ブラジル） | ― |

- 最初の広告を作るときに支払い方法を足す。その支払い方法で支払いの設定が決まる（H:716180208457684）
- **地域の支払い方法は、利用可能残高に資金を入れる用途だけ**で、アカウントに保存できない（自動チャージに使うと保存できるものもある）（H:132073386867900）
- 複数の支払い方法があるときはデフォルトを決める。**利用可能残高があれば先に使われる**（H:132073386867900）
- 支払い方法を足す前の確認（H:132073386867900）: オンライン取引で使える状態か、**OTP（ワンタイムコード）を受ける電話番号に紐づき、その電話が手元にあるか**、番号・有効期限・CVV などが正しいか

### 5-2. 支払い単位額（自動請求だけ）✅〔仕様〕（H:776240779095515。基本は 02§7-2）

- 支払い単位額は「請求されるまでに使える額」。初めて広告を出すと**自動的に少額**に設定され、支払いが済むたびに引き上げられることがある（最終的な額まで）。例として公式は 25 ドルを挙げる
- 支払い単位額に達する回数は月 0 回のことも、1 回のことも、複数回のこともある。**1 つの広告しか出していなくても月に複数回請求されうる**。広告を止めた後にも請求が来る（止める前の分）
- **支払い単位額に達しても広告は止まらない**（02§7-2、M-アカウント-020）
- 広告の領収書には **[請求理由]** があり、支払い単位額に達したのか毎月の請求日なのかが分かる（H:524424920973484）

### 5-3. [今すぐ支払う] ✅〔仕様〕（H:1814143615511573）

- 支払い単位額や請求日の前に、いつでも前もって払える。**広告アカウントの管理者**で、デフォルトの支払い方法があること
- [支払い設定] → [料金] の横の [今すぐ支払う] → 金額 → 支払い方法 → 確定。**反映まで最大 5 分**。未払いで止まっていた場合、新しい広告の作成と既存の広告の再開ができるようになる
- 未払いが無いと [今すぐ支払う] は出ない。手動決済の場合は残高に資金を入れる

### 5-4. 月極請求書払い ✅〔仕様〕（H:2086865811541431）

| 項目 | 中身 |
|---|---|
| 対象 | 条件を満たす会社と、切り替えを求められた会社だけ。資格があれば Business Suite のポートフォリオにお知らせ、[設定] → [請求と支払い] の上部にバナー |
| クレジット上限 | 月極請求書払いで使える最大額。**広告アカウントだけでなく、WhatsApp Business アカウント、ビジネス用 Meta 認証、Meta Business Agent など、あらゆる Meta 製品のアカウントの合計**。達すると、支払うか上限が上がるまで**すべてのサービスが一時停止されることがある** |
| 上限の引き上げ | ファイナンスエディターの役割の人が [請求と支払い] から依頼。今は広告用のクレジットラインだけ |
| 請求のサイクル | 1 か月の費用を累積し、請求期間の終わりに請求書。**支払い期限は発行日から 30 日後**（または所在国の法定期日） |
| 支払い方法 | 銀行引き落とし（米国・SEPA のみ）、銀行振り込み（請求書の Meta の口座へ手動）、Boleto（ブラジルのみ） |

- 日本で使える支払い方法の一覧は ❓（「銀行引き落としは米国と SEPA のみ」とあるので、日本の会社は銀行振り込みになると読める〔推測〕）
- セキュリティの推奨に「**共有クレジットラインに不審なアクティビティが無いか確かめる**」がある。悪質行為者が共有されたクレジットラインで自分の広告を出すことがあるため（H:608572510632070）

### 5-5. 請求の中身の読み方 ✅〔仕様〕（H:716180208457684）

- 料金は、指定しない限り通常は**インプレッションに基づいて**請求される（課金対象の細目は 02§7-3）
- 請求書には広告配信の料金に加えて**地域別手数料**が出ることがある。特定の法域のオーディエンスに配信したとき、デジタルサービス税（DST）など地域特有の費用を賄うために上乗せされる。どの地域が対象かはリンク先の別記事 ❓（日本が対象かは未確認）
- 最終的な広告料金・手数料・**適用される税金**は [請求と支払い] で確かめる
- **広告マネージャのクリック数・インプレッション数と、領収書の「請求対象」の数は一致しないことがある**
- **最終的な請求額が、ある広告の予算を超えることがある**。請求額には請求期間中のすべての広告の料金と地域別手数料が含まれるため
- 予算どおりに消化されるとは限らず、予算は期間に配分され、実際の消化は増減する（日予算の上振れの細目は 02 §6）

### 5-6. 日本の消費税（地図だけ）❓

- **ヘルプセンターに日本の消費税のページは見つからなかった**。2026-11-22 にヘルプ内検索「消費税」（17 件）と「日本 税」（6 件）を見たが、出たのは米国の売上税・一般消費税、インドネシア・オマーン・ウガンダ・ベナン・タンザニア・南アフリカ・ガーナ・ベトナムの付加価値税、カナダの GST/HST、インド・シンガポール・オーストラリアの GST、ニューカレドニアの GCT、WhatsApp Business サービスへの課税で、日本は無かった ❓
- API の項目（D:Ad Account）: `tax_id`（税 ID）、`tax_id_type`、`is_tax_id_required`（税 ID が要るか）、`tax_id_status`（0 不明／1 VAT 不要〔米国・カナダ〕／2 VAT 情報が必要／3 VAT 情報を提出済み／4 オフラインの VAT 確認に失敗／5 個人のアカウント）✅
- 確かめ方: ①自社の広告アカウントの領収書・請求書の発行元、税の行、登録番号の有無を見る ②[請求と支払い] の [支払い設定] の事業者情報・税の欄を見る ③Meta の広告の規約で契約の相手方を見る ④税の判断（仕入税額控除・リバースチャージの要否など）は税理士に確かめる。**この章は税の助言をしない**

### 5-7. 運用の判断への効き方

- **止めても請求は来る**。広告を止めた後の請求は止める前の分（02§7-2）。「止めたのに請求が来た」を乗っ取りと早合点しない。ただし身に覚えのない請求は 8-4 の手順で確かめる
- **支払い方法は複数登録し、デフォルトを決める**〔推測〕。カードの有効期限切れ・限度額で止まるのが一番もったいない止まり方。カードが切れたら支払いの失敗 → 配信停止 → アカウントの制限まで進みうる（34§6-3、支払いのリスク）
- **月極請求書払いのクレジット上限は Meta 製品の合計**。WhatsApp の利用料などで上限を食い、広告まで止まることがある（5-4）
- 経理と運用で「消化金額」と「請求額」が合わない問い合わせが来たら、5-5 の 3 点（請求対象の数の違い、期間中の全広告の合計、地域別手数料・税）を先に確かめる

## 6. 支出の上限

### 6-1. 上限の種類（基本は 02§7-1）

02§7-1 の 4 つ（Meta が決める 1 日の上限予算、キャンペーンの上限予算、広告アカウントの上限予算、プリペイド残高の上限）に、この章で 2 つ足す。

| 上限 | 誰が決めるか | 中身 | 出典 |
|---|---|---|---|
| 支払い単位額 | Meta（実績で上下） | 請求のきっかけ。**配信は止めない** | 5-2 |
| 月極請求書払いのクレジット上限 | Meta | Meta 製品全体の合計。**達するとすべてのサービスが一時停止されうる** | 5-4 |

### 6-2. 広告アカウントの上限予算（`spend_cap`）の API の細目 ✅〔仕様〕（D:Ad Account）

- `spend_cap`: この広告アカウントで使える最大額。**達するとすべての配信が止まる**。`0` は上限なし。**新しい上限は、置いた時点より後の消化にだけ効く**（M-予算-037）
- `amount_spent`: `spend_cap` に対する現在の消化額（上限が無ければ合計）。上限予算・広告マネージャ・支払い履歴で消化金額が違って見えることについては別の公式記事がある（H:196476577203529、本文は未取得 ❓）
- 更新のパラメーター `spend_cap_action`: `reset` で `amount_spent` を 0 に戻す、`delete` で上限を消す
- △ 単位の書き方が同じページの中で違う。**読み取りの項目**の `spend_cap` は「通貨の基本単位（USD ならセント）」、**更新のパラメーター**の `spend_cap` は「通貨の標準の表記（23.50 なら 23.50 ドル）」と書かれている。API で上限を置く前に、テストの広告アカウントで読み直して確かめる
- `min_daily_budget`（この広告アカウントの最低の 1 日の予算）、`min_campaign_group_spend_cap`（キャンペーンの上限予算の最低額）の項目もある。値は通貨と課金で変わる（最小予算は 02 §8）

### 6-3. Meta が決める 1 日の上限予算とビジネス認証

- 1 日の上限予算は、広告と支払いの履歴に基づいて Meta が設定し、規定を守って上限近くまで使うと通常は自動で引き上げられる（02§7-1）
- ビジネス認証が求められうる機能の例の**先頭に「1 日の上限予算」**が挙がっている ✅（H:1095661473946872）。どういう条件で、上限の引き上げに認証が要るかの細目は書かれていない ❓
- 〔推測〕新しいアカウントで大きな予算を一気に使う計画なら、ビジネス認証を先に済ませておくと、上限の引き上げで止まる場面を減らせる可能性がある

### 6-4. 運用の判断への効き方

- **月の総額を守る線は、広告アカウントの上限予算**（02§7-5）。API で置くなら単位を確かめる（6-2 の △）
- **上限は「置いた後の消化」から数える**。月の途中で置くと、それまでの消化は数えない。月初に [リセット] するか、`spend_cap_action=reset` を運用の手順に入れる〔推測〕
- 「予算はあるのに使われない」は、1 日の上限予算・上限予算・残高・クレジット上限の 4 つを順に見る〔推測〕

## 7. 制限・停止・回復（34§6 を土台に深める）

### 7-2. Meta が守るために勝手に変えること ✅〔仕様〕（H:524424920973484）

身に覚えのない動きの原因が、Meta 自身の保護の措置のことがある。不審なアクティビティを確かめた Meta が、アカウントを再開するために次を行った可能性がある。

- **管理者の削除**
- **広告の一時停止**
- **支払い方法の変更**

〔推測〕乗っ取りの調べで「管理者が消えている」「広告が止まっている」ときは、犯人の仕業か Meta の措置かを、アクティビティ履歴の変更者（10-1。「Meta」と出るか）とビジネスサポートホームのお知らせで分ける。

### 7-3. 回復の順序 ✅（34§6-4 の手順に、本文で読めた順序の根拠を足した）

1. **乗っ取りの疑いがあれば、先に安全を確保する**（34§6-4 の 4）。個人のプロフィール・ページ・Instagram の安全の確保はそれぞれ手順がある（H:583427765324458）
2. ビジネスサポートホーム → [アカウント概要] で対象と [対処方法] を見る（34§6-4）
3. 求められた手順（本人確認／認証の完了／アカウントの安全の確保／審査のリクエスト）をする。**審査のリクエストはそのアカウントの管理者が出す。回数は限られ、結果が最終決定**（M-アカウント-015〜017）
4. 支払いの理由（`RISK_PAYMENT`・`UNSETTLED`）なら、支払いを直し [今すぐ支払う] で精算（5-3）
5. 解除されても**止まっていた広告は自動で再開しない**。自分でオンにする（M-アカウント-018）

**やってはいけないこと**: 止まった後に新しい広告アカウント・資産を作って同じ広告を出す（措置の回避。34§6-5）。ポリシー違反で停止され復元の対象外のまま 6 か月たつと、未使用のプリペイドが失効しうる（M-アカウント-013）。

### 7-4. 運用の判断への効き方

- **最初に `account_status` と `disable_reason` を見る**〔推測〕。3（支払い）なのか 1・11・12（規定・完全性・不実表示）なのか 15（乗っ取り）なのかで、やることがまったく違う
- **審査のリクエストは実質 1 回勝負**（34§5-4、M-アカウント-017）。原因を直し、認証と安全の確保を済ませてから出す
- **個人のプロフィールの制限が広告に波及する**（34§6-3、M-アカウント-012）。広告を出す人の個人のアカウントの安全も、広告アカウントの安全の一部

## 8. 乗っ取りと不正アクセスへの備え

### 8-1. 兆候 ✅

| 兆候 | 出典 |
|---|---|
| メール・パスワード・名前・誕生日の変更、知らない人への友達リクエスト、書いていないメッセージ・投稿 | H:583427765324458 |

| ビジネスサポートホームの [アカウント概要] に、乗っ取りを理由にした制限（API なら `disable_reason`=15） | 34§6-4、D:Ad Account |

### 8-2. 守りの機能: セキュリティセンターの推奨 ✅〔公式の推奨〕（H:608572510632070）

ポートフォリオのフルアクセス許可を持つ人は、[セキュリティセンター] で次の推奨と、その実施状況を見られる。

| 推奨 | Meta が書く理由 |
|---|---|
| **アクティブでないユーザーを外す**（過去 **90 日**ポートフォリオにログインしていない人、とくにフルアクセス許可の人） | 悪質行為者はアクティブでないアカウントを狙う |
| **アクティブでない広告アカウントを閉じる**（過去 **1 年**広告を出していない） | 悪質行為者はこうした広告アカウントを狙う可能性が高い |
| **パスキーか二段階認証を設定していない人を外す**（設定するまで） | セキュリティリスク |
| **パブリックなメールドメインの人を外す** | 悪質行為者は誰でも取れるドメインのメールでポートフォリオに入ろうとする |
| **フルアクセス許可の人数を絞る**（**理想は 10 人以下**） | 多すぎるとリスク |
| **ピア承認で公開前に 2 回目の審査**（8-3） | 悪質行為者は不正な広告を出す |
| **マルウェアの可能性が検出された人を外す** | ― |
| **共有クレジットラインの不審なアクティビティを確かめる** | 悪質行為者が共有クレジットラインで自分の広告を出す |

その他の推奨（同じページ）

- **フルアクセス許可のアクティブな人を 2 人確保**（必須ではない）。「2 人目の管理者の承認」で、クレジットラインの共有やフルアクセス許可の人のアクセスの変更など機密の操作に第二の承認が付く。片方のアカウントが乗っ取られても、もう 1 人がいる
- **ユーザーのアクセス許可の監査**: [設定] → [ユーザー] で、各人のアクセス許可・前回ログイン・二段階認証の有無を書いたファイルを書き出せる。**招待を承認していない人はこのファイルに入らない**
- **ビジネス履歴の確認**: ポートフォリオの詳細・アセット・ユーザーへの変更など重要なイベントのファイル。[設定] の [ユーザー] か [ビジネス情報] からダウンロード（10-2）
- 不審・不正なアクティビティはサポートに報告

### 8-3. ピア承認 ✅〔仕様〕（H:529947753306370）

| 項目 | 中身 |
|---|---|
| 何か | 広告が公開される前に、広告アカウントの**信頼できるユーザー**による 2 回目の審査を必須にする |
| 信頼できるユーザー | ポートフォリオのフルアクセス許可の人は既定で信頼できるユーザー。基本のアクセス許可と、その広告アカウントへのアクセスを持つ人を追加できる。**広告アカウントで 90 日以上アクティブでない人は承認者にできない** |
| 設定できる人 | ポートフォリオのフルアクセス許可の人。対象の広告アカウントはそのポートフォリオが所有するもの |
| 例外 | **フルアクセス許可の人が公開する広告は 2 回目の審査が要らない** |
| 保護の段 | **デフォルト**: 不審な広告だけ承認が必要（Meta が自動で承認者に通知。すべての段に含まれる）／**追加**: すべての広告で掲載前に承認（パートナーや一時的なアクセスの人がいるアカウント向け）／**カスタム**: 選んだ予算を超えて公開される広告で承認（不正やミスに備えて支出を管理したいアカウント向け） |
| ドメインのセキュリティ | 信頼できるドメインのリストを作ると、**リストに一致しない URL を含む広告はすべて承認が必要**。リストを空にすると無効 |
| 国別の制限 | 信頼できる国のリスト外をターゲットにする広告は承認が必要（まだ使えない場合がある） |
| 配慮が必要な広告製品の制限 | [CTX 広告をブロックする] をオンにすると、Messenger・Instagram Direct・WhatsApp への**メッセージ誘導広告がすべて承認制**（まだ使えない場合がある） |
| 承認の流れ | 条件に当たると、信頼できるユーザーに広告マネージャの通知と、Meta for Business（advertise-noreply@support.facebook.com）からのメール。[アカウント概要] の [確認して公開] → 予算・クリエイティブ・URL・地域を確かめ [この広告を承認します] → [公開] |
| 場所 | Business Suite の [設定] → [セキュリティセンター] → [ピア承認] → [広告アカウントのセキュリティ] の [管理] |

### 8-4. 被害に遭ったときの手順 ✅（H:524424920973484、H:583427765324458、34§6-4）

1. **個人のアカウントの安全を確保**（パスワードの変更、二段階認証、ログイン中の端末の確認）。プロフィール・ページ・Instagram ごとの手順は H:583427765324458 の各リンク
2. **支払い履歴を確かめる**: [請求と支払い] → [支払いアクティビティ] → [取引 ID] で領収書（金額・日付・支払い方法・対象の広告・請求理由）
3. **誰がアクセスできるか確かめる**: [アカウント設定] の [広告アカウントの役割]。**支払い方法や広告アカウントを共有している相手**が別の広告を出していないか確かめる
4. **アカウントの履歴を全部見る**: [アカウント概要]、アクティビティ履歴（10-1）
5. それでも身に覚えが無く、不正アクセスが疑われるなら、ヘルプの窓口に連絡。Meta の保護の措置（7-2）が先に入っていることもある
6. 〔推測〕その後: 知らない人・システムユーザー・パートナーの共有を外す、トークンを作り直す、ピア承認を「追加の保護」にする、支払い方法を入れ替える

### 8-5. 運用の判断への効き方

- **乗っ取りの被害の大半は「人」から入る**〔推測〕。Meta の推奨 8 項目のうち 5 つ（アクティブでない人、二段階認証の無い人、パブリックなメールの人、フルアクセス許可の人数、マルウェア）は人の整理
- **月に 1 回の点検**〔推測〕: ユーザーのアクセス許可のファイルを書き出し、90 日ログインの無い人・二段階認証の無い人・フリーメールの人・退職者を外す。セキュリティセンターの推奨の残数を見る
- **代理店に追加の保護**: パートナーが出す広告を全部承認制にすると、乗っ取られたのが代理店側でも被害を止められる。ただし公開が遅れる（承認者が見るまで出ない）〔推測〕
- **ドメインのセキュリティは安い守り**: 自社のドメインだけをリストに入れれば、乗っ取った人が詐欺サイトへ飛ばす広告を出しても承認待ちで止まる〔推測。根拠は 8-3 の仕様〕

## 10. アクティビティ履歴と変更の追跡

### 10-1. 広告マネージャのアクティビティ履歴 ✅〔仕様〕（H:289211751238030）

- キャンペーン・広告セット・広告への変更が記録され、**誰が、いつ、何を**変えたか分かる
- 表示の種類: アカウント（広告の承認・却下、広告アカウントの変更）／広告／広告セット／ターゲット／入札／**予算（広告セットの予算の変更と、アカウントの支払い方法の変更。期限切れのカードの削除など）**／キャンペーン／掲載ステータス（一時停止・再開・削除）／スケジュール／ターゲット設定
- 見方: 広告マネージャ → [キャンペーン]・[広告セット]・[広告] → 対象を選ぶ → 右の [アクティビティ履歴] → アクティビティの種類と変更者で絞る
- **変更者の欄に出るもの**:

| 表示 | 意味 |
|---|---|
| 自分の名前 | 自分の変更 |
| 管理者・広告管理者の名前 | 広告アカウントの管理者・広告管理者の権限を持つ人の変更 |
| 自動ルールの名前 | 自動ルールによる変更（[ルールの管理] で確かめる） |
| ビジネスアイデンティティの名前 | 広告アカウントの権限を持つ（持っていた）認証済みのビジネスアイデンティティの変更 |
| Meta | Meta の広告審査の仕組み、**広告アカウントから自分を外したメンバー、外されたメンバー**の変更。承認待ちなどで広告のステータスが変わった場合も |

- 広告をどこで作ったか: [広告の作成完了] の変更者に [Using: Power Editor] なら広告マネージャ、[Using: Boosted Page] ならページ（投稿の宣伝）から
- 見覚えのない変更があれば、広告アカウントの権限を確かめる、と公式は書く
- △ このページは「管理者」「広告管理者」という**旧い広告アカウントの役割名**を使う。アクセス許可の新しい説明（3 章）は「フルアクセス許可」「タスク」。名前が混在している

### 10-2. ポートフォリオの履歴とユーザーのファイル ✅（H:608572510632070）

- **ビジネス履歴**: ポートフォリオで起きた重要なイベントのファイル。ポートフォリオの詳細・アセット・ユーザーへの変更が分かる。[設定] の [ユーザー] か [ビジネス情報] からダウンロード
- **ユーザーのアクセス許可のファイル**: 各人の許可・前回ログイン・二段階認証の有無（招待を未承認の人は入らない）
- ルールの実行の履歴は別にある（「ルールのアクティビティ履歴」。H:382041259713204、本文は未取得 ❓）

### 10-3. API ✅〔仕様〕（D:Ad Account Activities）

- 広告アカウントの `activities` の端点で `AdActivity` の一覧が読める。**作成・更新・削除はできない**（読むだけ）
- 誤りの番号: 200（権限）、613（呼び出しの上限超え）、80004（その広告アカウントへの呼び出しが多すぎる）、190（トークンが無効）、100（パラメーター）、368（不正と判断された操作）
- **何日さかのぼれるか、どの種類の変更が入るかは、この端点のページに書かれていない** ❓（AdActivity のリファレンスを読む。Google は API の `change_event` が 30 日、G27 0 章の 10）
- 公式の Ads MCP にはアクティビティログの道具がある（65 の S-73 の記述）

### 10-4. 運用の判断への効き方

- **編集の前後は管理画面では分けられない**（00§2-2、S-79）。アクティビティ履歴で「いつ何を変えたか」を拾い、成果の表に日付の線を引く〔推測〕
- **自動ルールの変更も履歴に名前で出る**。「誰も触っていないのに予算が変わった」は、まず自動ルールを疑う
- **変更者が「Meta」のとき**は、審査の判定か、外された人の変更。外された人の変更が後から「Meta」になるので、**退職者・外した代理店の変更を追うには、外す前に履歴を書き出す**〔推測。根拠は 10-1 の仕様〕

## 13. 少額・少量のアカウントでの注意〔推測〕

- 一人で運用していると、フルアクセス許可が 1 人になりがち。**信頼できる 2 人目**（経営者・共同運営者）を入れておく。乗っ取られたときに戻す人がいない（8-2）
- 新しいアカウントは支払い単位額が小さく、請求が頻繁に来る（5-2）。カードの利用明細の件数が多くても異常ではない
- 新しいアカウントは Meta が決める 1 日の上限予算が低い（02§7-1）。セール前の大きな増額は早めに実績を積むか、ビジネス認証を先に済ませる（6-3）
- 個人のプロフィールで広告を出している場合、その個人のプロフィールの制限が広告に波及する（34§6-3）。私用の投稿の規定違反に気をつける

## 15. 既存の章との食い違い・補足

- **34§6-6 との関係**: 34 は二段階認証を「特定の地域をターゲットにする広告にアクセスできる人、作成から 90 日以上のポートフォリオで求められうる」と書く。今回の本文（H:865384580786591）も同じ。食い違いなし。この章では「未設定で支払い方法やショップの権限が削除されうる」「90 日未満なら必須化を選べる」を足した
- **00§2-1 との関係**: 00 は器の階層と数の上限を持つ。食い違いなし。この章で「アセットの種類 14」「広告アカウントは削除できず閉鎖だけ」を足した
- **02§7 との関係**: 02 は支払い単位額・上限予算の基本を持つ。食い違いなし。この章で月極請求書払い・利用可能残高の引き落とし頻度・地域別手数料・`spend_cap` の API の細目を足した
- **65 との関係**: 65 は API の変更履歴の端点・期間を ❓ としている（65 の 282 行目）。この章で `activities` の端点の存在と、期間が書かれていないことを確かめた（引き続き ❓）
- **名前の揺れ**: 「全権限」「フルアクセス許可」「フルアクセス」が公式の日本語の中で混在する（H:442345745885606 自身が「フルアクセス(旧称: 全権限)」と書きつつ、同じページでアセットについて「全権限または部分的なアクセス許可」と書く）。この章は「フルアクセス許可」に寄せた
