## 0. 先に結論（この章で一番効く 7 点）

1. **日次の実績を決まった形で取るなら、Marketing API の Insights API（`GET /act_<ID>/insights`）を、権限 `ads_read` だけのシステムユーザーのトークンで呼ぶのがいちばん小さい道**〔推測。部品はすべて ✅〕。自分の広告アカウントだけなら、`ads_read` は標準のアクセスで足り、アプリの審査は要らない ✅（A-07）
2. **公式の Ads MCP サーバー（`https://mcp.facebook.com/ads`）は日本語の案内があり、追加料金なし。ただしオープンベータで段階的に提供中、「すべての広告アカウントが利用できるわけではない」** ✅（A-03・A-04）。
3. **MCP は「読むだけ」に絞れる**: トークンの権限を `ads_mcp_management`＋`ads_read` にする ✅（A-01）。さらに Business Suite の「広告 MCP サーバー」のルールで、エージェントの操作を全部（`all`）止められる ✅（A-02・A-03）。ただしルールは「限定提供」✅（A-02）
4. **呼び出しの上限は、何もしなければ開発用の段階（Limited access）**: 読み取り 1 回 1 点、最大 60 点、300 秒で回復、超えると 300 秒止まる ✅（A-08）。1 日 1 回の取り込みなら足りる〔推測〕。上の段階（Full access）は「15 日で 500 回以上、誤り 15% 未満」で申請 ✅（A-07）
5. **成果の「日」の付け方が Google と違う**: API は 2025-06-10 から管理画面と同じ `mixed`。Meta の中の操作（リンククリックなど）は**表示の日**、ウェブの購入など Meta の外の成果は**成果が起きた日**に付く ✅（A-12）。Google は成果をクリックの日に付ける（G の 94、抜粋）。日次で並べると、同じ「昨日の成果」でも意味が違う
6. **過去 28 日の数字は毎日変わりうる**: Insights は 15 分ごとに更新され、計上から 28 日たつと変わらなくなる ✅（A-12）。日次のシートは「昨日だけ足す」ではなく「直近 28 日を毎日取り直して上書き」にする〔推測〕
7. **2026 年の 2 つの変更は、日次の列の「成果」側に効く**: ① 2026-01-12 から API の 7 日ビュー・28 日ビューの窓はデータを返さない ✅（A-14・A-15）② 2026-03 後半から順次、クリックスルーは**リンクのクリックだけ**に変わり、いいね・保存などのあとの成果は「エンゲージスルー」へ移る ✅（A-16）。表示・クリック・消化金額の列そのものが変わるとは書かれていない ❓。前年比・月比は切り替わりの日を注記する

### 2-2. 運用の判断への効き方

- **日次のスプレッドシート（決まった列を毎日）には、Marketing API を直接呼ぶ小さなスクリプトが合う**〔推測〕。MCP の `ads_get_ad_entities` は日別の行（`time_increment`）やアトリビューションの窓を指定できるかが文書に無い ❓。決まった列を毎日同じ形で取るには、引数が文書化されている Insights API のほうが確か
- **会話で「先週なにが起きた？」と聞く用途には、公式の MCP が早い**〔推測〕。外れの検出・推移・業界の比較の道具は自前で作らなくてよい。ただし「AI の提案（未承認）」と「媒体の推奨」を混ぜない原則（principles 2）は、Meta の道具の返答には付かないので、使う側で守る
- **書き込みの権限は最初から付けない**。公式の手順（CLI の例、Marketing API のユースケース）は書き込みの権限を前提に書かれているので、手順どおりに進めると `ads_management` が付く。トークンを作るときに `ads_read` だけを選ぶ（§2-3 の 7）


**道 A: Marketing API ＋ システムユーザーのトークン（推奨〔推測〕）**

1. **Meta の開発者として登録する**（developers.facebook.com）。登録の手順は公式の「Register as a Meta Developer」✅（A-07 の前提の節）
2. **アプリを作る**。作成の流れは「アプリの詳細 → ユースケース → ビジネス → 要件 → 概要」✅（A-21）。ユースケースは **「Measure ad performance data with Marketing API」**（広告の成果データを測る）を選ぶ ✅（A-22）。
   - 注意: このユースケースでも、アプリの権限の一覧には `ads_management`・`business_management` などが「必須・外せない」と出る ✅（A-22）。**ここで付くのはアプリが求められる権限の枠で、トークンの権限は 7 で絞れる**〔推測〕
   - ビジネスの確認（Business Verification）は作成時には要らない ✅（A-21）。「機微なデータに触れるアプリ」では要る ✅（A-07）。自分の広告の実績を読むだけで要るかは書かれていない ❓
3. **利用の段階を確かめる**。Marketing API を足すと **Limited access が自動で付く** ✅（A-07・A-08）。自分の広告アカウントだけなら `ads_read` は標準のアクセスで足りる ✅（A-07）。Full access は不要〔推測〕（申請するなら「15 日で 500 回以上、直近 500 回の誤り 15% 未満」✅ A-07）
4. **システムユーザーを作る**。Business Suite → 設定 → ユーザー → システムユーザー → 追加。役割は**従業員（Employee）**にする（公式の MCP は従業員のトークンしか受けない ✅ A-01。CLI はどちらでもよい ✅ A-06）。Limited access では、システムユーザー 1 つと管理者のシステムユーザー 1 つまで ✅（A-07）
5. **システムユーザーにアプリを割り当てる**（設定 → アプリ → ユーザーを割り当て）✅（A-06）。アプリがシステムユーザーに入っていないとトークンを作れない ✅（A-06・A-10）
6. **システムユーザーに広告アカウントを割り当てる**。読んでよいと決めた広告アカウントだけ（principles 5）。権限は「見るだけ」に当たるものを選ぶ〔推測。ラベルの日本語名は今回確かめていない ❓〕。ページ・データセット・カタログは割り当てない（読むだけなら要らない〔推測〕）
7. **トークンを作る**。システムユーザーを選んで［トークンを生成］→ アプリを選ぶ → **権限は `ads_read` だけ**にチェック（`ads_read` はシステムユーザーで使える権限の一覧にある ✅ A-10）
   - 期限: **60 日で切れるトークン**（公式は「有効期限付きのトークンがセキュリティ上のベストプラクティス」と書く）か、**期限なし**（更新が要らない代わりに漏れたときの危険を受け入れる）✅（A-10）。ビジネスによっては 60 日が必須 ✅（A-10）
60 日を選ぶなら、作った日から 50 日目に作り直しの予定を入れる〔推測〕
8. **トークンを手元のファイルに置く**。google-ads.yaml と同じ考えで、リポジトリの外のフォルダに置き、権限を本人だけにする（`chmod 600`）〔推測〕。**チャットに貼らない。Claude にファイルの中身を読ませない**（principles 5）
9. **トークンを確かめる**。アクセストークンデバッガー（developers.facebook.com/tools/debug/accesstoken）で「権限（Scopes）が `ads_read` だけ」「期限」を見る ✅（A-09）
10. **広告アカウント ID を控える**。広告マネージャの設定の「アカウント概要」に出る ✅（A-07 の前提の節）。API では `act_` を前に付ける

- **費用**: Marketing API の利用料は、取得した文書のどこにも書かれていない ❓。公式 MCP は「接続に伴う追加料金はかからない」✅（A-03）
- **お金を使わずに動きを確かめる**: アプリのクイックスタートで**サンドボックスの広告アカウント**を作れる。支払い方法が要らず、広告は配信されず、模擬の実績でレポートを試せる ✅（A-22）。principles 3 の「お金のかからない方法」に当たる〔推測〕。ただし「どの段階でも呼び出しは本番のデータに対して行われる」✅（A-07）

**道 B: 公式の Ads MCP サーバー（自分のアプリなし）**

1. 管理権限のある広告アカウント・対応する AI ツール・Facebook ログインの 3 つを用意 ✅（A-03）
2. AI ツールにサーバーの URL（`https://mcp.facebook.com/ads`）を入れ、Facebook でサインインする ✅（A-03）
3. （ビジネスポートフォリオの全権限があれば）Business Suite → 設定 → 統合 → **広告 MCP サーバー** → 広告アカウントを選び、操作ごとに［許可済み］／［ブロック済み］を切り替える。項目が見えなければ、その機能はまだ使えない ✅（A-04）
- **Claude Code から自分のアプリなしでつなぐ手順は公式に無い** ❓。公式の Claude Code の 1 行は `claude mcp add --transport http --client-id <META_APP_ID> meta-ads https://mcp.facebook.com/ads` で、**自分のアプリの ID が要る** ✅（A-01）
- 自分のアプリなしのとき、ログインで渡す権限を `ads_read` に絞れるかは書かれていない ❓。ルールで `all` を止めるのが守りになる（限定提供）

**道 C: 公式の Ads MCP サーバー（自分のアプリあり、Claude Code から）**

1. 道 A の 1・2 で作ったアプリ（または別のアプリ）に、ユースケース「Create & manage ads with ads MCP server」を足す ✅（A-01・A-05）
2. 自分のビジネスのデータだけなら、`ads_mcp_management` の高度なアクセス（審査）は要らない ✅（A-05: 他のビジネスのデータを扱う場合だけ審査）
3. OAuth を使うなら、アプリの Facebook Login for Business の設定にリダイレクト URL を入れる ✅（A-01）。Claude Code 用の値は公式に書かれていない ❓
4. トークンを使うなら、従業員のシステムユーザーで **`ads_mcp_management`＋`ads_read`** のトークンを作る ✅（A-01）。リクエストの `Authorization: Bearer` ヘッダーに入れる ✅（A-01）
- 〔推測〕Claude Code の設定にトークンそのものを書くことになるなら principles 5 に反する。OAuth の道（Meta のログインでトークンを Claude Code の側が持つ）か、道 A を選ぶ

### 2-4. 運用の判断への効き方

- **最初の 1 本は道 A**〔推測〕。理由: ①手順と引数が文書化されている ②権限を `ads_read` だけにでき、principles 2 を鍵で守れる ③オープンベータの提供待ちに左右されない ④日次のシートに同じ形で入れられる
- **道 B は用途**として並行して試せる。使えるかどうかで「日本のアカウントで公式 MCP が使えるか」の ❓ が解ける（0 円、principles 3 の 3 に当たる）
- **60 日か期限なしか**: 1 人で回す運用で、トークンがリポジトリの外の手元のファイルにだけあり、`ads_read` だけなら、漏れたときの害は「実績を読まれる」まで〔推測〕。それでも公式は期限付きを勧める。

## 3. 日次の実績を取る呼び出し

### 3-1. 端点と主な引数 ✅〔公式〕本文（A-11・A-12・A-13）

| 引数 | 値 | 日次で使うとき |
|---|---|---|
| 端点 | `GET https://graph.facebook.com/v27.0/act_<広告アカウントID>/insights`（ほかに `/<キャンペーンID>/insights`・`/<広告セットID>/insights`・`/<広告ID>/insights`）| アカウントの端点に `level` を付けて 1 回で取る |
| `level` | `account`・`campaign`・`adset`・`ad` | シートの粒度。広告まで取ると行が増える |

| `time_range` | `{'since':'YYYY-MM-DD','until':'YYYY-MM-DD'}`（`since` はその日の 0 時から、`until` は翌日の 0 時まで）| 直近 28 日などを指定。`time_ranges`（複数）を渡すと `time_increment` は無視される |
| `date_preset` | `yesterday`・`last_7d`・`last_28d`・`last_30d`（既定）・`maximum`（最大 37 か月）など | 公式は「できれば `date_preset` を使う。任意の期間は効率が悪い」と書く（A-12）|
| `fields` | 取る項目（§4）。指定しないと表示回数と消化金額 | 必要な項目だけにする（重いと時間切れになる）|
| `action_attribution_windows` | `1d_click`・`7d_click`・`28d_click`・`1d_view`・`1d_ev`・`default` ほか（`7d_view`・`28d_view` は一覧に残るが 2026-01-12 から返らない）| 窓ごとの列が欲しいときに指定（§4-2） |
| `action_report_time` | `impression`・`conversion`・`mixed`・`lifetime` | 2025-06-10 から無視され、`mixed` で返る（A-12） |
| `use_unified_attribution_setting` | `true` で広告セットのアトリビューション設定に従う | 2025-06-10 から無視され、管理画面と同じ扱い（A-12） |
| `breakdowns` | `age`・`gender`・`country`・`publisher_platform`・`platform_position`・`device_platform` など | 内訳は推定値を含む（00 §11-2）。日次のシートには入れない〔推測〕 |
| `filtering` | 例 `[{field:"ad.impressions",operator:"GREATER_THAN",value:0}]` | 表示のあった物だけに絞って行を減らす（A-12） |
| `limit`・ページ送り | 応答の `paging.cursors` | 行が多いときは次のページを取る |

- **バージョン**: 最新は v27.0（2026-11-04）。2026-07-29 から Marketing API のバージョンの自動更新が始まった ✅（00 §11-1、S-05）。アプリの設定に「Marketing API version auto-upgrade」がある ✅（A-22）
- **日付はアカウントのタイムゾーン**で区切られる。公式は「アカウントのタイムゾーンの時刻を考えて、1 日の中で問い合わせを分散させる」と書く ✅（A-12）

### 3-2. 非同期のレポート ✅〔公式〕本文（A-12）

1. `POST /act_<ID>/insights`（同じ引数）→ `report_run_id` が返る。**30 日で無効**になるので長く保存しない
2. `GET /<report_run_id>` で `async_status` が `Job Completed`、`async_percent_completion` が 100 になるまで待つ（ほかに `Job Not Started`・`Job Started`・`Job Running`・`Job Failed`・`Job Skipped`）。v25.0 から、失敗したときは誤りの番号と文が既定で返る
3. `GET /<report_run_id>/insights` で結果を取る
- 公式は「まず同期で試し、時間切れになったら非同期」と書く。非同期は再試行を含めて最大 1 時間かかることがある
- 書き出し用の端点（`https://www.facebook.com/ads/ads_insights/export_report/`、`format=csv|xls`）があるが、**バージョン管理の外で、形式が予告なく変わりうる**。スクリプトから頼らない、と公式が書く
- 〔推測〕非同期は `POST` を使う。運用 MCP で「書き込みの呼び出しを持たない」を守るなら、`POST` を許すのは `/insights` だけ、とテストで確かめる

| 項目 | 内容 | 出典 |
|---|---|---|
| 更新の間隔 | Insights は **15 分ごと**に更新 | A-12 |

| 仕組み | Limited access（既定） | Full access |
|---|---|---|
| 広告アカウントの点数 | 読み取り 1 点・書き込み 3 点。**最大 60 点、300 秒で回復、超えると 300 秒止まる** | 最大 9,000 点、300 秒で回復、超えると 60 秒 |
| `ads_insights` の BUC（1 時間・1 アカウント） | 600 ＋ 400 × 有効な広告の数 − 0.001 × ユーザーの誤り | 190,000 ＋ 400 × 有効な広告の数 − … |

### 3-5. 運用の判断への効き方

- **毎朝の取り込みは「直近 28 日を取り直して上書き」**〔推測〕。キーは（日付・広告 ID・窓）。28 日より前の行は固まったものとして残す
- **広告の単位で取って、キャンペーン・広告セットはシートで足し上げる**〔推測〕。ただし**リーチとフリークエンシーは足し上げられない**（人の重なりがあるため。リーチは推定値 ✅ A-13）。上の単位のリーチが要るなら、その `level` で別に取る
- **時刻**: アカウントのタイムゾーンの 0 時を過ぎてすぐは、前日の数字がまだ動く〔推測。15 分ごとの更新 A-12〕。取り込みは朝のある程度遅い時刻にする

- **「結果」をキャンペーンをまたいで足さない**。目的が違えば数えている物が違う ✅（A-13 の定義）
- **CPC と CTR は「リンククリック」の版をシートの標準にする**〔推測〕。クリック(すべて) にはいいね！やコメントが入るので、Google のクリックと比べられない ✅（A-28）

### 5-1. 運用の判断への効き方

- **API を作る前に、まず定期レポートで同じ列を作ってみる**〔推測〕。0 円で、§4 の列が管理画面で何という見出しになるかが分かる（§7 の ❓ がここで解ける）。
- **メールの定期レポートは、日次のシートの「答え合わせ」に使える**〔推測〕。API で取った値と管理画面の値がずれたら、窓（§4-2）と遅れ（§3-3）を先に疑う
- 定期レポートのメールを Claude が読む流れは作らない〔推測〕（メールの中身を読ませるのは、原則 5 の「データを混ぜない」の点で別の判断が要る）

## 6. 運用 MCP につなぐときの案〔推測〕

今の運用 MCP（`../../ads-mcp/README.md` 版 0.9.0、`principles.md` 版 0.3）の作りに合わせた案。**コードは書いていない**。

### 6-1. 守りの形（Google と同じ考え）

| Google での形（今） | Meta での案 |
|---|---|
| 広告アカウントを変える呼び出しはコードに無い（テストで確かめる）| 同じ。加えて**トークンの権限を `ads_read` だけ**にして、API の側でも書き込めないようにする（二重の守り）。非同期の `POST /insights` だけは許し、ほかの `POST`・`DELETE` は道具の中で断る。テストで確かめる |
| 許可リスト（`ochinana_ads/config.py` の 2 つの ID）。それ以外は API を呼ぶ前に断る | 同じ場所に Meta の許可リストを足す。principles 5 版 0.3 の範囲 |
| 認証ファイルの**場所**を環境変数で指す。中身は google-ads ライブラリが読み、道具のコードは開かない | Meta には同じ形のライブラリの読み方が無い〔推測〕。案 1: 環境変数 `META_ADS_TOKEN_FILE` でファイルの場所を指し、道具は呼び出しの直前にだけ読んでヘッダーに入れ、**記録・出力・例外の文に入れない**（テストで確かめる）。案 2: 公式の MCP を OAuth でつなぎ、トークンを手元に置かない。どちらも「AI が鍵の中身を読んだり出力したりしない」は守れる。案 1 は「道具は中身を読まない」という今の書き方とずれるので、principles の付録の書き直しが要る |
| 返答は円・日本語の列名・上位 20 件、大きい結果は `out/` に CSV | 同じ。金額は `account_currency` を見て円だけ扱い、円以外は断るか注記（Google と同じく円以外は未対応）|
| 「媒体が作った文」「AI の提案（未承認）」を分ける | Meta の「結果」は媒体が決めた数え方。返答に「結果の定義: 目的と設定による」「窓: 広告セットの設定」「計上日: mixed」を注記に入れる |

### 6-2. 道具の案（Google と同じ名前の形にするなら）

### 6-3. 日次のスプレッドシートの案

1. 毎朝 1 回（アカウントのタイムゾーンで朝）、許可リストの各アカウントについて `level=ad`・`time_increment=1`・直近 28 日・§4-1 の項目＋窓 2 種を取る
2. （日付・広告 ID・窓）をキーに上書き。28 日より前の行は触らない
3. シートの列は §4-1 の「管理画面の表示名」に合わせ、成果は「結果（設定どおり）」と「7 日クリックの成果」の 2 列（§4-3）
4. 上限の点数（`X-FB-Ads-Insights-Throttle`）を毎回記録し、80% を超えたら待つ
5. 「新しいクリックの定義の開始日」「アトリビューション設定を変えた日」の注記の列を置く
