## 0. 先に結論（この章で一番効く 10 点）

1. **ウェブの AEM（合算イベント測定）の「8 件の優先順位付け」は、今はやらなくてよい。** イベントマネージャの［合算イベント測定］タブは削除され、イベント設定のためのドメイン認証も、キャンペーン作成時のコンバージョンドメインの選択も不要になった ✅〔公式〕本文（B-07）。開発者文書（S-36）の「8 つまで」は古い記述。初版 00 §9-3 の △ はこれで解ける
2. **CAPI は「入れたか」ではなく「照合できたか」で効く。** 照合（マッチング）されたイベントだけがアトリビューションと配信の最適化に使われる ✅〔公式〕本文（S-17、B-09）。点検は「イベントのマッチングクオリティ（EMQ。ヘルプは 0〜10、開発者文書は 1〜10 △。直近 48 時間で算出。開発者文書は可能なら 6.0 以上を勧める＝24§7-1）」「イベントのカバー率（CAPI がピクセルの 75% を覆うのが目標）」「追加で報告されたコンバージョン」の 3 つで見る ✅〔公式〕本文（B-09、B-17、B-32）
3. **ピクセルと CAPI で同じイベントを送るなら、`event_name` と `event_id` をそろえる。** そろわないと二重に数える。`event_id` が無いときは `external_id` か `fbp` で除くが、これは条件付き ✅〔公式〕本文（B-13、S-15）
4. **CAPI のウェブ・アプリのイベントは、起きてから 7 日を過ぎると送れない（リクエスト全体がエラー）。** 売上・リード目的の最適化に効かせるなら 1 時間以内が推奨 ✅〔公式〕本文（S-16、B-18）
5. **オフライン（店舗・CRM）のイベントは最大 62 日まで遅らせられる** とヘルプは書く。開発者文書は `event_time` を 7 日前までと書きつつ、店舗のイベントは「62 日以内にアップロード」と書く △（B-18、B-28）
6. **アトリビューションには「モデル」の層がある。** 標準・インクリメンタル・カスタムの 3 つ。**公開後にモデルは変えられない**（変えるならキャンペーンを作り直す）。インクリメンタルでは入札コントロール（単価目標・上限・ROAS 目標）を使えない ✅〔公式〕本文（S-57、B-02）
7. **標準モデルの窓は「クリック 1 日か 7 日」「ビュー 1 日」「エンゲージスルー 1 日」。** クリックは**リンクのクリック**だけ。28 日クリック・28 日ビュー・7 日ビューは広告セットの設定から外れた ✅〔公式〕本文（S-57）。既定はヘルプ「成果」（611432918970668）が「クリックから 7 日間、表示から 1 日間、またはエンゲージメントから 1 日間」と書く ✅。API の `default` は「クリック 7 日＋ビュー 1 日」（S-28）でエンゲージスルーの有無の書き方が違う △
8. **Meta の数字は GA4 と合わないのが正常。** Meta はビュー（見ただけ）とエンゲージスルーを含め、人単位でデバイスをまたいで数え、データが欠けるところはモデルで補う。GA4 はクリックと Cookie が中心 ✅〔公式〕本文（B-15、B-27）
9. **イベントマネージャの件数 ＞ 広告マネージャの件数** も正常。イベントマネージャは広告と無関係なイベントも含む ✅〔公式〕本文（B-14）
10. **リード獲得で成約を最適化に戻すなら「CRM 用コンバージョン API」（コンバージョンリード）。** 条件は月 200 件以上のリード、1 日 1 回以上のアップロード、狙う段階がリードから 28 日以内、その段階の転換率 1〜40% ✅〔公式〕本文（B-33）。使えるフォームは日本語のヘルプ（782657799338685、名前は「適格リード」）が「ウェブサイトフォームとインスタントフォームの両方」、開発者文書の概要が「インスタントフォームだけ」と書く △（64§4-2）

## 1. Google との対比（G06・G24 との対比表）

Google 側の記述は G06・G24・`90_核となる理解.md` に合わせた（記憶で書いていない）。

| 観点 | Google 広告（G06・G24） | Meta 広告 | 運用の判断への効き方 |
|---|---|---|---|

| iOS・ブラウザの制限への対応 | 推定コンバージョン（モデル化）を「コンバージョン」列に含める（G06 §8） | AEM（iOS 14.5 以降の端末のウェブ・アプリのイベントを集計とノイズ付けで処理）＋モデル化されたコンバージョン ✅ 本文（B-07、B-27） | どちらも「列の中に推定が入っている」。Meta は**ウェブの AEM の設定作業が無くなった**（2026-11 時点） |

| アトリビューションのモデル | データドリブンかラストクリック（G06 §5） | 標準・インクリメンタル・カスタムの 3 つ ✅ 本文（S-57） | Google のモデルは「手柄の配り方」。Meta のモデルは「**何を成果として数え、何に最適化するか**」まで変える（インクリメンタルは増分のコンバージョンに最適化） |
| 入札への効き方 | コンバージョン アクションの「メイン／サブ」と目標で決める（G06 §4） | 広告セットの「コンバージョンイベント（パフォーマンスの目標）」と、アトリビューション設定（最適化にも使う）✅ 本文（S-13、S-57） | Meta は窓を変えると**最適化も変わる**（S-13「最適化のための成果の割り当て」）。レポートの見え方だけの設定ではない |
| 計測の点検の道具 | タグ診断、Tag Assistant（G24 §10） | イベントマネージャの診断・イベントのテスト、Meta 広告データヘルプツール（旧 Meta Pixel Helper）✅ 本文（B-13、B-35） | Pixel Helper という名前で探しても見つからない。2026 年時点の名前は「Meta Ads Data Advisor／広告データヘルプツール」 |

## 2. 道具の全体と器（データセット）

### 2-1. 何がどこにあるか ✅〔公式〕本文（B-24、B-10、B-22）

| 道具 | 役目 | 置き場所 |
|---|---|---|
| データセット（旧 ピクセルの器） | ウェブ・アプリ・実店舗などのイベントを 1 か所でつなぎ、管理する。ヘルプは「データセットとピクセル: Meta ピクセル、コンバージョン API やその他のツールを使用して、ウェブサイト、アプリ、実店舗など、さまざまなソースからのイベントデータをリンクして管理」と書く | ビジネスポートフォリオのデータソース |
| Meta ピクセル | ウェブサイトに置くコード。サイト上の行動（イベント）を記録する | データセットの一部 |
| コンバージョン API（CAPI） | サーバー・CRM・店舗などから直接イベントを送る。ウェブ・実店舗・メール・ビジネスチャット・電話・アプリ・オフラインに対応 | 同じデータセットに入る |
| オフラインイベントセット | オフラインの行動データのアップロード用（旧来の器）| データソース |
| カスタムコンバージョン | イベントや URL に条件を足して成果を定義 | データソース |

- ✅ CAPI はアプリイベント API やオフラインコンバージョン API の代わりに使える。すでに旧 API を使っていれば続けられるが、「データセットの作成が必要な場合には使用できません」とヘルプは書く（B-10）。開発者文書は旧オフラインコンバージョン API を「レガシー」と呼ぶ（B-28）
- ✅ オフラインのイベントは CAPI で送る場合、データセットに結び付ける必要がある（B-28）

### 2-2. 運用の判断への効き方

- **新しく作るなら、ウェブもオフラインも「1 つのデータセット＋CAPI」に寄せる。** 旧オフラインイベントセットや旧 API で新しく組まない〔推測〕（B-10・B-28 の「レガシー」「代わりに CAPI」から）
- **代理店に渡す権限は、広告アカウントだけでなくデータセットにも要る。** データセットには広告アカウント・メンバー・パートナーを別々に足す（ヘルプの関連ページ名で確認。本文は未読 ❓）
- カスタムコンバージョンは広告アカウント単位で見え方が変わる。ポートフォリオにアクセスできる人は両方から、広告アカウントだけの人はそのアカウントで作ったものだけ見える ✅ 本文（B-20）

### 2-3. Google との違い

Google はコンバージョン アクションが「計測の単位」で、タグはそれを動かす部品。Meta は**データセットが計測の単位**で、その上に標準イベント・カスタムイベント・カスタムコンバージョンが乗る。Google の「メイン／サブ」に当たる区分は Meta に無く、**広告セットで選んだイベントだけが最適化の対象**になる（S-13）。

## 3. Meta ピクセル

### 3-1. 仕組みと置き方 ✅〔公式〕本文（B-22、B-19）

- ベースコードを全ページの `<head>` に、イベントコード（`fbq('track','Purchase',{value:…,currency:…})` など）をページごとに置く
- ピクセルの使い道としてヘルプが挙げるのは、①狙いどおりの人に出ているかの確認と見込み客の発見・リターゲティング、②自動入札で成果を出しやすい人に届ける、③効果の測定

### 3-2. 標準イベント（17 種）✅〔公式〕本文（B-19）

支払い情報の追加（AddPaymentInfo）、カートに追加（AddToCart）、ウィッシュリストへの追加（AddToWishlist）、登録完了（CompleteRegistration）、問い合わせ（Contact）、製品のカスタマイズ（CustomizeProduct）、寄付（Donate）、場所の検索（FindLocation）、チェックアウト開始（InitiateCheckout）、リード（Lead）、購入（Purchase。value と currency）、スケジュール（Schedule）、検索（Search）、トライアル開始（StartTrial。predicted_ltv あり）、応募（SubmitApplication）、サブスクリプション登録（Subscribe。predicted_ltv あり）、コンテンツビュー（ViewContent）。

- ヘルプはコンテンツビューについて「URL に訪問があったことはわかりますが、訪問者がウェブページで何を実行または閲覧したかはわかりません」と書く（B-19）
- ✅ 標準イベント以外の名前で送るのが「カスタムイベント」。最適化に使うにはカスタムコンバージョンを経て標準イベントのカテゴリを選ぶのが勧められる（§7）

### 3-3. Cookie の設定 ✅〔公式〕本文（B-23）

- 既定は「ファーストパーティ Cookie とサードパーティ Cookie の両方を使う」。ファーストパーティ Cookie は使えるブラウザが多く、保存期間も長い
- ファーストパーティ Cookie をオフにすると「測定とレポートの正確性も低下」とヘルプは書く
- ❓ ファーストパーティ Cookie（`_fbp`・`_fbc`）の有効期間はヘルプ本文に書かれていない

### 3-4. 詳細マッチング（ピクセル側の照合の強化）✅〔公式〕本文（B-25）

| 方式 | 中身 |
|---|---|
| 手動 | ピクセルの初期化にメールなどを渡す。ピクセルが自動でハッシュ化する（IMG ピクセルは自分でハッシュ化）。iframe 内や IMG ピクセルでも使える |
| 自動 | イベントマネージャでオン。ピクセルがフォームの氏名・メールなどを探し、ブラウザ内でハッシュ化して送る。照合後すぐ削除 |

- 効き目としてヘルプが挙げるのは、アトリビューションされるコンバージョンの増加、カスタムオーディエンスの拡大、コンバージョン単価の削減

### 3-5. 点検の道具: Meta Ads Data Advisor（旧 Meta Pixel Helper）✅〔公式〕本文（B-35）

- Chrome・Edge の拡張機能。**旧名 Meta Pixel Helper**。既存の利用者は自動で更新され、診断の機能はそのまま
- ピクセル・CAPI（GTM 経由を含む）の設定、Shopify・WooCommerce の接続、Salesforce・HubSpot の CRM データ、カタログ、詳細マッチングの設定まで手伝う。設定の自動化にはログインと広告アカウントの管理者権限が要る（検出と点検はログインなしで動く）
- **2026-08-03 から**、Data Advisor で新しくピクセルを作ると、標準イベントの自動検出が既定でオン（外せる）
- 日本語ヘルプの重複除外のページは「Chrome 拡張機能の Meta 広告データヘルプツール」と書く（B-13）

### 3-6. 運用の判断への効き方

- **ピクセルだけの構成は、今は「最低限」。** ブラウザの読み込み失敗・接続・広告ブロッカーで落ちる分を CAPI で補うのが Meta の推奨（B-10、B-17）。まずピクセル＋詳細マッチング（自動）を入れ、次に CAPI
- **購入には必ず value と currency を付ける。** 値の最適化（ROAS 目標・価値の最大化）とレポートの ROAS の前提（B-19、B-21）
- **自動検出の標準イベント（2026-08-03 以降の既定）は、意図しないイベントを作りうる**〔推測〕。最適化に使うイベントは自分で定義したものだけにし、自動で増えたものはイベントマネージャで確認する

### 3-7. Google との違い

Google タグは GA4・Google 広告の両方の器。Meta ピクセルは Meta 専用で、**オーディエンス（リターゲティング）の材料と、計測と、最適化の信号を 1 本で兼ねる**。Google の「タグを止めてもリマーケティングは GA4 から作れる」に当たる代わりの道は無い。

## 4. コンバージョン API（CAPI）

### 4-1. 何が良くなるか ✅〔公式〕本文（B-10）

ヘルプが挙げる利点（ウェブのイベント）:

1. データの接続性: ピクセルより「ブラウザーの読み込みエラー、接続の問題、広告ブロッカーの影響を受けにくい」。ピクセルと組み合わせると結果の単価の削減に役立つ
2. 後ろの段階のアクションへの最適化: 購入後のアクション（サブスクリプションなど）、店舗でのアクション、顧客スコア
3. 効果測定の改善（オンラインとオフライン）
4. イベントのマッチングを増やす（顧客情報パラメーターを足せる）

- ✅ ヘルプは「コンバージョン API はピクセルと同じく、iOS の App Tracking Transparency のようなデータ共有のポリシーや、e プライバシー規則のようなヨーロッパのプライバシー規制を回避する手段として設計されたものではありません」と明記（B-10）
- ✅ CAPI で送ったイベントも AEM の制限に従って処理される（B-07）
- ✅ Messenger 誘導広告の最適化に使えるメッセージイベントは、今は購入だけ（B-10）。△ 63 章（2026-11-22）は、条件を満たせば「メッセージを通じた購入数」と「メッセージを通じたリードの数」（Instagram は 5 件／30 日、WhatsApp は 1 件）に最適化できると書く（63§0・§8-2）。リードもある

### 4-2. 入れ方の選び方 ✅〔公式〕本文（B-11、B-12）

| 入れ方 | 価格 | 時間 | 必要なもの | 送れるもの | 重複の除外 |
|---|---|---|---|---|---|
| Meta 対応コンバージョン API（イベントマネージャからワンクリック）| 無料 | ワンクリック | Meta ピクセル | ウェブだけ | ピクセルで送るイベントが自動で CAPI でも送られ、自動で重複除外 |
| ダイレクト連携（コード）| 開発費・保守費しだい | 新規 2〜4 週間（ウェブ送信済みでアプリ・オフライン・メッセージを足すなら 1〜2 週間）| 開発者、リアルタイムで送る基盤 | ウェブ・アプリ・オフライン・CRM・ビジネスメッセージ | 自分で設定 |
| パートナー連携 | パートナーしだい | パートナーしだい | — | パートナーしだい | 多くのプラットフォームで自動（B-13）|
| CAPI ゲートウェイ | クラウドの費用だけ（月 30 ドルから）| 30 分未満（ヘルプ）。開発者文書は AWS のスタック作成に約 30〜40 分 | AWS か GCP（アカウントは新規でも可）| ウェブ | 自動 |

- ✅ **モバイルアプリと実店舗（オフライン）のイベントは、今はダイレクト連携が唯一の選択肢**（B-11 冒頭）

- ✅ 開発者文書のゲートウェイ設定ガイドはカスタムドメインを推奨（データの経路の最適化とコスト削減の可能性）。設定できるリージョンは 1 つ（B-30）

### 4-3. 必須・推奨のパラメーター ✅〔公式〕本文（S-16、S-17、B-29、B-34）

| 項目 | ルール |
|---|---|
| `action_source` | 全イベントで必須。値は `email`・`website`・`app`・`phone_call`・`chat`・`physical_store`・`system_generated`・`business_messaging`・`other` |
| `event_time` | 実際に起きた時刻（UNIX 秒）。**送る時点から 7 日前まで**。7 日より古いものが 1 件でもあると**リクエスト全体がエラー** |
| `event_source_url`・`client_user_agent` | ウェブのイベントで必須 |
| `event_id` | 重複除外の鍵。広告主が決める一意の文字列 |
| `external_id` | 全イベントで推奨（S-17） |
| `fbp`・`fbc` | ブラウザ ID・クリック ID。変わりうるので送るたびに新しい値を取る（S-17） |
| `client_ip_address` | ハッシュ化しない（B-34） |
| 顧客情報（メール・電話・氏名など）| ハッシュ化して送る。Business SDK・Parameter Builder Library は自動で正規化・ハッシュ化（S-17、B-34） |
| `data_processing_options` | 今受け付ける値は `LDU`（限定データ使用）（B-29） |
| `original_event_data` | 遅れて送るイベントを過去の獲得イベントに結び付けるメタデータ。遅れがあるときは使用を強く推奨（B-29） |

- ✅ **Parameter Builder Library**（オープンソースの SDK。クライアント側は JavaScript、サーバー側は PHP・Java・Python・Node.js・Ruby）が `fbc`・`fbp`・IP・参照元 URL・正規化とハッシュ化した顧客情報を作る。Meta は EMQ の改善につながるとし、`_fbp`・`_fbc` を顧客の行動の早い段階で取ることを勧める（B-34）

### 4-4. 運用の判断への効き方

| 状況 | 選ぶもの | 理由 |
|---|---|---|
| Shopify などで EC を運営 | そのプラットフォームのパートナー連携 | 追加費用なし、重複除外も自動（B-11、B-13）|
| 自社サイト、開発者がいない、ピクセルは入っている | まず Meta 対応 CAPI（ワンクリック）。月 300 ドル超の支出で精度を詰めたいなら CAPI ゲートウェイ | ワンクリックは無料。ただしピクセルが送るパラメーターしか送れない（B-11）。ゲートウェイはクラウド費だけ（B-12）|
| GTM を使っている | GTM のパートナー連携（サーバーサイド GTM） | Google 側のサーバーサイド GTM と基盤を共用できる〔推測〕（開発者文書に「Conversions API for Google Tag Manager」の項目がある。本文は未読）|
| 店舗・電話・CRM の成約を返したい | ダイレクト連携（オフライン）か CRM 用 CAPI | オフラインは今ダイレクト連携だけ（B-11）|
| リード広告（インスタントフォーム）の商談化・成約で最適化したい | CRM 用 CAPI（コンバージョンリード）| §9-3 |

- **ワンクリック CAPI は「CAPI を入れた」ことにはなるが、照合の質は上がりにくい**〔推測〕。ピクセルで共有するパラメーターを CAPI でも共有するだけ（B-11）なので、メール・電話のハッシュを足す余地が無い。EMQ を見て足りなければダイレクトかゲートウェイに進む

### 4-5. Google との違い

Google のサーバーサイド計測は「Cookie の寿命を延ばす・ブロックを避ける」話が中心で、成果の取りこぼし対策の 1 つ（G24 §6）。Meta の CAPI は**照合の鍵（メール・電話・external_id）を足す主な経路**で、照合できたかどうかがそのまま最適化に入るか入らないかを決める（S-17）。だから Meta では「サーバー側は後回し」が通りにくい。

## 5. ピクセルと CAPI の併用と重複の除外

### 5-1. 2 つの送り方 ✅〔公式〕本文（B-13、B-17）

| 戦略 | 例 | 重複除外 |
|---|---|---|
| 冗長設定（推奨）| 欠落に備えて購入をピクセルと CAPI の両方から送る | 必要 |
| 分担設定 | ブラウザからカート追加、サーバーから購入 | 不要 |

- Meta のベストプラクティスは**冗長設定**（両方で同じイベントを共有）。ネットワークの問題やページの読み込みエラーでピクセルが落としたイベントを CAPI で補える（B-17）

### 5-2. 重複除外の条件 ✅〔公式〕本文（B-13）

- `event_name` が一致し、`event_id`（ピクセルは `eventID`）が一致すること
- サーバーとピクセルのイベントが似ていれば、**先に受け取ったほうが優先**
- 除外の対象: ①同じ名前・同じ eventID のピクセルイベントの重複 ②同じ event_name・event_id のサーバーイベントの重複 ③ピクセルとサーバーの両方から送られ、`event_name`＋`event_id`、または `event_name`＋`external_id`/`fbp` が一致するもの
- `event_id` が無いときは `fbp` と `external_id` で除外する。ただし開発者文書（S-15）は、この方式はブラウザ→サーバーの順で届いた場合に限り、過去 48 時間にブラウザのイベントが無ければサーバーのイベントを捨てない、と条件を付ける。同じ経路から 2 回送ったものは除かない（S-15）
- オフライン（店舗）の重複除外は別のルール: 鍵は `dataset_id`・`event_time`・`event_name`・`item_number` に、`order_id`（既定）か、それが無いときは顧客情報。**重複除外の窓は最大 7 日**（B-28）

### 5-3. 点検の順番 ✅〔公式〕本文（B-13）

1. ブラウザ側とサーバー側で同じ `event_id` を使っているか
2. イベントマネージャの［イベントのテスト］で、受信・重複除外・破棄を確かめる
3. `event_name`・`event_id` の書式がどの経路でも同じか
4. イベント数の急な増減を見る
5. 広告データヘルプツールか SDK のデバッグ道具を使う

よくある原因としてヘルプが挙げるのは、`event_id` の不一致・欠落、ブラウザとサーバーの送信の遅れ、パラメーター名や値の誤り。

### 5-4. 運用の判断への効き方

- **CAPI を入れた直後に成果が急に増えたら、まず二重計上を疑う。** 本当に取りこぼしが戻ったのか、`event_id` の不一致で 2 件になっているのかは、イベントマネージャの重複除外の状況で分かる（B-13）〔推測〕（判断の順番）
- **入札の目標値（単価目標・ROAS 目標）は、CAPI の導入前後で置き直す。** 計測される件数が変わると、同じ目標値でも意味が変わる〔推測〕（G06 §11 の「計測の変更日を記録する」と同じ考え方）
- 計測の変更日は必ず記録する（G26 §13-8 と同じ）

### 5-5. Google との違い

Google は同じ成果を「Google 広告のタグ」と「GA4 の取り込み」の 2 つのアクションで持つとき、片方をサブにして二重計上を防ぐ（G24 §2）。Meta は 1 つのイベントを 2 つの経路から送り、Meta の側で 1 件にまとめる。**Google の発想で「CAPI はサブにしておこう」とはできない**（その仕組みが無い）。

## 6. イベントの品質（EMQ・カバー率・追加で報告されたコンバージョン・鮮度・遅延）

### 6-1. イベントのマッチングクオリティ（EMQ）✅〔公式〕本文（B-09、B-32）

- 日本語ヘルプの名前は「**イベントのマッチングクオリティ**」（英 Event Match Quality）。初版 00 は「イベントの照合の質」と書いたが、管理画面に近い表記はこちら
- 中身: サーバーイベントとともに送った顧客情報パラメーターが、イベントを Meta アカウントに照合するのにどれだけ効いているか。**0〜10 のスコア**。顧客情報の質と、照合できたイベントの割合から計算
- **直近 48 時間のデータで計算**するので、定期的にイベントを送り続けないとスコアが古くなる
- すべての標準ウェブイベントとカスタムウェブイベントで出る。開発者文書（Dataset Quality API）は「今はウェブのイベントだけ」「リアルタイムで計算」と書く（B-32）
- ✅ 照合されたイベントは「コンバージョンを広告にアトリビューションし、コンバージョンの可能性が高い人にその広告を表示するのに役立つ」（B-09）

**パラメーターの優先度**（ヘルプの表。日本語版の表は「中」の一部が「M」と表示されている）✅〔公式〕本文（B-09）

| 優先度 | パラメーター |
|---|---|
| 高 | メール、クリック ID |
| 中 | Facebook ログイン ID、生年月日 |
| 中（表では「M」）| 国、電話番号、外部 ID（広告主の一意の ID）、ブラウザー ID |
| 低 | リード（ID）、名、姓、市、郵便番号 |

- △ EMQ の目安: ヘルプには数値が無いが、開発者文書（Conversions API の Verifying Setup）は「可能なら EMQ 6.0 以上を目指すことを勧める」と書き、範囲を 1〜10 とする（ヘルプは 0〜10）。「合格」という公式の点は無い。もう 1 つの公式の数値は、セルフサービスのコンバージョンリフトの条件「EMQ が 5 を超えるイベントを送信」（`26` §5、B-48）

### 6-2. イベントのカバー率 ✅〔公式〕本文（B-17、B-32）

- 定義: ピクセルのイベントのうち、CAPI でも送られ、重複除外の鍵を共有しているものの割合（7 日平均）（B-32）
- **目標は 75%**。ヘルプは「Meta ピクセルイベントに対するコンバージョン API のイベントカバー率は、75% を目指す必要があります」と書く（B-17）。開発者文書の `goal_percentage` も 75（B-32）

### 6-3. 追加で報告されたコンバージョン ✅〔公式〕本文（B-16、B-32）

- 旧名「追加でアトリビューションされたコンバージョン」。CAPI とピクセルの併用でどれだけ報告が増えたかを示す
- 算出に使うのは過去 7 日のコンバージョン、CAPI かピクセルに接続した広告セットにアトリビューションされたコンバージョン、処理完了後に報告されうるコンバージョン数
- 開発者文書では `acr`。カバー率・照合の鍵ごとに「満たせば増える見込み」も返す（B-32）

### 6-4. データの鮮度と遅延 ✅〔公式〕本文（B-18、B-17）

| 使い道 | イベントの種類 | 推奨 | 最大 |
|---|---|---|---|
| オーディエンス | CAPI のウェブ・アプリ | 24 時間以内 | 7 日以内 |
| オーディエンス | オフライン | 24 時間以内 | 62 日以内 |
| 広告マネージャのアトリビューション | CAPI のウェブ・アプリ | 7 日以内 | 7 日以内 |
| 広告マネージャのアトリビューション | オフライン | 7 日以内 | 62 日以内 |
| 「売上」「リード」「エンゲージメント」が目的の広告 | CAPI のウェブ・アプリ | **1 時間以内** | 7 日以内 |
| コンバージョンリフトテスト | CAPI・アプリイベント API・ピクセルのウェブ・アプリ | 7 日以内 | 90 日以内 |
| 商品メディアを表示する広告（旧 Advantage+ カタログ広告） | CAPI のウェブ・アプリ | 1 時間以内 | **24 時間以内** |

- 最大を過ぎて送ったイベントは「Meta 側で利用しないことがある」（B-18）
- ヘルプのベストプラクティスも「イベントはリアルタイムで、またはできるだけリアルタイムに近い方法で共有」（B-17）

### 6-5. 運用の判断への効き方

- **点検は「EMQ → カバー率 → 鮮度」の順。** EMQ が低ければメール・電話のハッシュと `fbc`・`external_id` を足す。カバー率が 75% 未満なら CAPI で送っていないイベントを足す。鮮度が「1 日 1 回」なら売上・リードの最適化には遅い（1 時間以内が推奨）〔推測〕（順番は書き手の判断、基準値は公式）
- **夜間の一括送信は、最適化には不利。** 売上・リード目的は 1 時間以内が推奨（B-18）。CRM から日次で送るのは「成約」など後ろの段階に限る〔推測〕
- **カタログの広告（商品メディアを表示する広告）は 24 時間を過ぎると最大を超える。** カタログ広告の購入・カート追加は CAPI でも即時に送る（B-18）
- **EMQ は「多く送るほど上がる」ではなく、「照合できる鍵を送るほど上がる」**。名・姓・市・郵便番号は優先度が低い（B-09）。フォームで取るならメールと電話を優先する

### 6-6. Google との違い

Google の拡張コンバージョンには「診断」と「効果の数字」がある（G24 §4-4）が、0〜10（開発者文書は 1〜10）のような 1 つのスコアは無い。Meta は EMQ という**1 本のスコアで照合の質を見せ、セルフサービスのリフトの利用条件（EMQ 5 超）にまで使っている**。Google の感覚で「拡張コンバージョンは入っていれば十分」と考えると、Meta では足りない。

## 7. 標準イベントとカスタムコンバージョン

### 7-1. カスタムコンバージョンでできること ✅〔公式〕本文（B-20、B-21）

- 標準イベント・カスタムイベント・［すべての URL トラフィック］にルールを足して絞る（例: URL に「mens」を含み、値が 50 ドルより大きい購入）
- コードを足さずに URL のルールで標準イベントを記録する
- パフォーマンスの目標（最適化の対象）に使える。「受信が十分な回数に達すると」使えるようになる（B-20。回数は ❓ 記載なし）
- データソース全体ではなく、個々のカスタムコンバージョンだけをパートナーと共有できる

### 7-2. 決まり ✅〔公式〕本文（B-21）

| 項目 | ルール |
|---|---|
| 上限 | **広告アカウントごとに 100 個**。使わないものを消して作り直せる |
| 自動アーカイブ | **2 年間**アクティブでない・使われていないものは自動でアーカイブ。戻すには同じルールで作り直す |
| 最適化のカテゴリ | すべての URL トラフィックかカスタムイベントを元にするなら、最適化のための標準イベントのカテゴリを選ぶ必要がある（推奨）。標準イベントを元にするなら不要 |
| 値 | 整数だけ。元のイベントに値が無いときだけ使う |
| URL のルール | 「URL が次である」は完全一致（UTM・http/https・末尾の / の違いで数えない）。**「URL が次を含む」を推奨** |
| すべての URL トラフィック | 該当ページにページビューを含むベースコードが要る |
| 商品メディアを表示する広告（旧 Advantage+ カタログ広告） | 最適化はカスタムコンバージョンでなく標準イベント。ただし設定と測定には使える |
| 削除 | 広告セットの最適化を変えてから消す。消したものに最適化した広告セットは配信されるが、照合・更新が止まり成果が落ちうる |
| ルールの数 | 必要最低限に（ルールが少ないほど対象が広がり、コンバージョンを多く得られる） |

### 7-3. 運用の判断への効き方

- **最適化の対象は「件数が取れるいちばん後ろのイベント」**。購入が週に少なければ、カスタムコンバージョンで「高単価の購入」に絞るのは逆効果になりうる（件数が減る）〔推測〕（学習フェーズの週 50 件の目安は 00 §6）
- **サンクスページの URL で作るなら「含む」。** 完全一致は UTM 付きで数えない（B-21）
- **LP 改善やフォームの差し替えで URL が変わったら、カスタムコンバージョンのルールも直す。** 直さないと「成果が急にゼロ」になる〔推測〕

### 7-4. Google との違い

Google のコンバージョン アクションは 1 アカウントに多く作れ、メイン／サブで入札への効き方を分ける（G06 §4）。Meta のカスタムコンバージョンは **100 個の上限**があり、最適化に使うものは広告セットで 1 つ選ぶ。Google の「サブのアクションを並べて観察する」使い方は、Meta では広告マネージャの列の追加で代える〔推測〕。

## 8. ドメインの認証・AEM・iOS

### 8-1. ウェブの AEM の今（2026-11-18 時点）✅〔公式〕本文（B-07、B-06）

- AEM は iOS 14 以降の端末の人からのウェブイベントとアプリイベントを測るためのプロトコル。識別子の削除・差分プライバシーの適用・データの集約をしてから、広告のパーソナライズと効果測定に使う

  3. **ウェブサイトのドメイン認証は、イベントの設定に関する目的では不要**（ほかの理由では今も要ることがある）
  4. 広告マネージャでキャンペーンを作るとき、**コンバージョンドメインを選ぶ必要はない**

### 8-2. iOS のアプリと SKAdNetwork ✅〔公式〕本文（B-07、B-06、S-57）

- アプリの AEM は、リンク先をモバイルアプリにした売上（カタログの有無を問わない）・リード・エンゲージメントのキャンペーンで使える。カスタムイベントへの最適化は今は非対応

### 8-4. 運用の判断への効き方

- **iOS の比率が高い商材では、オーディエンス（リターゲティング）の縮小を前提に組む。** 広いターゲットに寄せるのが Meta の推奨（B-06）

### 9-1. 店舗・オフラインのイベント ✅〔公式〕本文（B-28、B-10）

- △ 期限: 開発者文書は `event_time` を「7 日前まで」と書き、同じページで「店舗の取引は 62 日以内にアップロード」と書く。ヘルプの遅延の表はオフラインの最大を 62 日とする（B-18、B-28）。**62 日を上限、7 日以内を推奨として扱う**のが安全〔推測〕

### 9-2. 運用の判断への効き方（店舗）

- **店舗の成果は「アトリビューションの列」と「リフト」で読み方が違う。** 列はアトリビューション設定の窓（ウェブと同じ）で数える。店舗への影響を言うならリフト（`26` §5）〔推測〕

## 11. アトリビューション

00 §9-4を土台に、モデル 3 種の条件と使い分けを足す。

### 11-1. モデルの層と設定の層 ✅〔公式〕本文（S-57）

- 広告セットを作るときに**アトリビューションモデル**を選ぶ。この選択は配信に反映され、どのコンバージョンを広告の成果として数えるかの基準になる
- 標準モデルを選んだときだけ、さらに**アトリビューション設定**（窓）を選ぶ
- ヘルプは「現在、Meta では標準アトリビューションモデルとインクリメンタルアトリビューションモデルを提供しています」と書く（カスタムは「まだご利用いただけない場合があります」B-04）
- **モデルが違う広告セットの結果は、キャンペーンの概要テーブルで比べられない**。比べるなら［アトリビューション設定の比較］機能。外部の分析ツールを使っているなら、そのツールで評価する

### 11-2. 3 つのモデルの条件と使い分け

| モデル | 何を数え、何に最適化するか | 使える条件 | 向く場面 | 出典 |
|---|---|---|---|---|
| 標準 | 選んだ窓（クリック・ビュー・エンゲージスルー）の中で起きたコンバージョンをすべて数え、それに最適化 | 制限なし（キャンペーンの種類による窓の制限は §11-3）| 既定の運用。ほかの媒体と窓をそろえて比べたいとき | ✅ 本文 S-57 |
| インクリメンタル | 「広告がコンバージョンの要因になったか」を予測する機械学習モデルで、**増分のコンバージョンに最適化・報告** | 目的が［売上］［エンゲージメント］［リード］、コンバージョンの場所が［ウェブサイト］か［ウェブサイトとアプリ］、目標が［コンバージョン数の最大化］か［コンバージョン値の最大化］。**入札コントロールは使えない**。**公開後にモデルを変えられない** | 既存顧客・指名に近い人に広告が寄りすぎている疑いがあるとき。報告の数字より「本当に増えた分」を増やしたいとき | ✅ 本文 B-01・B-02 |
| カスタム | 外部の分析ツールのアトリビューション（各購入にどれだけ Meta の貢献を割り当てるか）を共有し、**広告主の基準の成果に最適化** | CAPI か対応パートナー（Adobe・Northbeam・Rockerbox・Triple Whale）。**新しいキャンペーンだけ**。作れるまで通常 1〜2 週間、高品質のシグナルが要る。最適な条件として「独自のアトリビューションで媒体をまたいで予算を決めている」「注文単位のクリックスルーの貢献と値を共有できる」「購入に最適化した売上キャンペーン」「価値の最大化か最大数量の入札戦略」 | MTA（マルチタッチ）の仕組みを持つ EC。Meta の数字と自社の数字の差が大きいとき | ✅ 本文 B-04 |

- ✅ カスタムが向かない場合としてヘルプが挙げるのは、ブランドの認知などファネル上部の目的、Meta の既定のアトリビューションに満足していて自社の測定との差が大きくない場合（B-04）
- ✅ インクリメンタルの結果は、モデルをインクリメンタルにしていない広告セットでも［列: パフォーマンス］→［アトリビューションモデルを比較］→［インクリメンタル］で見られる。**2025-04-01 より前の期間では出ない**。例: 全体 100 件のうち 70 件を Meta が増分とみなせば、［結果］列はインクリメンタルで 70、標準で 100（B-03）
- ✅「増分結果」はヘルプの「推定指標」の一覧に入っている（実測でなくモデルによる値）（B-26）
- ✅ 公式の発表（2025-06-04）: インクリメンタルアトリビューションは世界での提供を終えたばかり。試した広告主は通常のキャンペーンより増分コンバージョンが平均 46% 多かった（Meta の自己申告）。リフトテストを先にする必要はない。カスタムアトリビューションは「来年にかけてテスト」と書いていた（B-37）。2026-01-28 の発表は Q4 のモデル更新で増分コンバージョンが標準より 24% 多いと書く（S-40、00 §9-4）

### 11-3. 標準モデルの窓 ✅〔公式〕本文（S-57）

|---|---|---|
| ふだんの運用、とくに少額 | 標準・クリック 7 日（＋ビュー 1 日は「見る」だけ）| 件数を確保して学習を進める（00 §6）。窓を短くすると件数が減る〔推測〕 |
| GA4・Google 広告と並べて報告したい | 標準のまま、列だけ「クリック 1 日／7 日」に分けて見る（［アトリビューション設定の比較］） | 最適化を変えずに比べられる（S-57）。ビュー・エンゲージスルーを除くと GA4 の考え方に近づく〔推測〕 |
| リターゲティング・既存顧客への配信が多く、手柄の取りすぎが疑わしい | まず［アトリビューションモデルを比較］でインクリメンタルの列を見る。差が大きければ、新しいキャンペーンでインクリメンタルを試す | 列を見るだけなら既存のキャンペーンを壊さない（B-03）。モデルを変えるには作り直しが必要（B-02）|
| 単価目標・入札上限・ROAS 目標を使いたい | 標準 | インクリメンタルでは入札コントロールが使えない（B-02） |
| 自社の MTA で予算を決めている EC | カスタム（使えるなら）| B-04 |
| 認知・ファネル上部 | 標準（窓は結果に関係が薄い）| カスタムは向かないとヘルプ（B-04） |

- **モデルの切り替えは「新しいキャンペーン」＝学習のやり直し**（B-02、00 §6-2）。少額のアカウントで気軽に試すと、学習のやり直しの損のほうが大きい〔推測〕
- **2026-03 前後をまたぐ前年比は注記する**。クリックの定義が変わり、旧版のアカウントもある（S-38、S-57）

### 11-5. Google との違い

- Google のアトリビューション モデル（データドリブン／ラストクリック）は「複数のクリックに手柄をどう配るか」で、**最適化の対象のコンバージョンそのものは変わらない**（G06 §5）。Meta のインクリメンタルは「**増分とみなしたものだけを数え、それに最適化する**」ので、数える対象が変わる
- Google は計測期間をアクション単位で 1〜90 日（G06 §5）。Meta は広告セット単位で、最長クリック 7 日
- Google の「エンゲージ ビュー」（動画を一定時間見た後の成果）と Meta の「エンゲージスルー」は似ているが、Meta は**動画以外のリンク以外のクリック（いいね・保存など）まで含む**（S-57）
- Google のデータドリブンは件数が少ないとラストクリックと同じになりうる（G06 §5）。Meta のインクリメンタルが件数の少ないときにどうなるかは公式に記載なし ❓

## 12. 数字が合わない理由（GA4・Google 広告・イベントマネージャ）

### 12-1. Meta の中での違い ✅〔公式〕本文（B-14）

| 比べるもの | 起きること | 理由 |
|---|---|---|
| イベントマネージャ ＞ 広告マネージャ | 広告マネージャの結果のほうが少ない | イベントマネージャは広告と関係ない行動（オーガニック・ほかの媒体経由・広告を見ていない人）も含めて受信したほぼすべてを出す。広告マネージャはアトリビューションされたものだけ |
| イベントマネージャの［データソース］の合計イベント数 | 重複除外されていない | 1 人が同じ行動を複数回しても数える |
| カスタムコンバージョンの数 ＜ 標準・カスタムイベントの数 | 少ない | 重複・データポリシー・規制で破棄したものを引いている |

### 12-2. 外部のツール（GA4 など）との違い ✅〔公式〕本文（B-15）＋ Google 側（G06 §1）

| 理由 | Meta 側 | GA4・Google 広告側 | 出典 |
|---|---|---|---|
| 数える単位 | 人単位（Meta アカウント）。デバイスをまたぐ | Cookie 単位が中心 | B-15 |
| 表示への帰属 | ビュースルー（見ただけ）・エンゲージスルーを含められる。既定にビュー 1 日（S-28） | GA4 にビュースルーは出ない（G06 §1） | B-15、S-57 |
| 窓 | 最長クリック 7 日 | Google 広告は既定 30 日（1〜90 日）。GA4 は 2026-08-11 からクリックスルー 1〜90 日（G06 §1） | S-57、G06 |
| 広告ブロック | ピクセルが動かないと Meta は少なく数える（CAPI で補える） | GA のタグも止まりうる | B-15、B-10 |
| 参照元 URL | 第三者の多くは参照元 URL で結ぶ。HTTPS→HTTP の移動や、新しいタブで後から買うと参照元が切れ、Meta 経由と数えられない | 同左 | B-15 |
| 指標の定義 | 定義と計算方法が違う | — | B-15 |
| 集計レポート | データ共有が制限されたアプリ・サイトでは集計レポート（届く情報が減る） | — | B-15 |
| ショップ | Facebook・Instagram のショップ内の行動は第三者のツールで見えないことがある | — | B-15 |
| モデル化 | データが欠けるときに一部のコンバージョンを統計モデルで推定（ウェブの測定方法が変わった場合など） | Google 広告は推定コンバージョンを含む（G06 §8） | B-26、B-27 |
| 計上の日 | △ API は 2025-06-10 から `action_report_time=mixed`（Meta の外の成果＝ウェブの購入などは**成果の時刻**、Meta の中の操作は表示の時刻。指定は無視）。広告マネージャのレポートは「コンバージョンの時間ごとか、インプレッションが発生した表示時間ごとかを選べる」とヘルプは書く。両方を書く。管理画面で選ぶ場所と既定の値は ❓（25§3-2、65§4-2。2026-11-24 の統合で ❓ を △ に） | Google 広告はクリック日、GA は発生日（G06 §1） | — |
| クリックの定義 | 2026-03 以降、クリックスルーはリンクのクリックだけ | — | S-38 |

### 12-3. 運用の判断への効き方

- **「どちらが正しいか」ではなく「何を数えているか」をそろえて比べる。** 比べるときは Meta を「標準・クリック 7 日（ビュー・エンゲージスルーを除く）」の列にし、GA4 は Meta 経由の流入（UTM で切り出す）に絞る〔推測〕（手順は書き手。窓の選択肢は S-57）
- **真の値は台帳（申込み・受注の記録）。** Meta・Google・GA4 は同じ申込みをそれぞれ自分の手柄として数え、合計は台帳を超えうる（G26 §2-5 と同じ）
- **UTM は必ず付ける。** 参照元 URL が切れる場面（B-15）でも、UTM があれば GA4 で Meta 経由を切り出せる。ヘルプも「Google アナリティクスを使用している場合、トラッキングするには UTM パラメーターを入力する必要があります」と書く ✅（25§5、2026-11-24 に〔推測〕から格上げ）
- **UTM は入稿前に決める。** 公開後に URL パラメーターを変えることはできるが、**広告セットが再び情報収集期間に入る可能性がある** ✅（ヘルプ 2360940870872492、25§5・07§3-8）。名前のダイナミックパラメーター（`{{campaign.name}}` など）は初回公開時の名前で固定され、後で名前を変えても値は変わらない ✅（25§5-3）
- **Meta の数字が GA4 より大きいこと自体は異常ではない**（ビュー・エンゲージスルー・人単位・モデル化）。異常を疑うのは、①CAPI の導入日や設定の変更日を境に急に増えた（二重計上）②イベントマネージャの数と比べて広告マネージャの数が近すぎる（ほぼすべてを広告の手柄にしている）とき〔推測〕

### 12-4. Google との違い

Google は「アトリビューションの違いで最大 20% の差が出ることがある」と、GA と Google 広告の差の目安を公式に書く（G06 §1）。Meta は差の大きさの目安を公式に書いていない ❓。Meta の差は、Google と GA4 の差より大きくなる要因が多い（ビュー・エンゲージスルー・人単位）〔推測〕。

## 13. 少額・少量のアカウントでの設計

1. **最初の 1 日でやること**: ピクセル（ベースコード＋購入かリードのイベントに値と通貨）＋自動詳細マッチング＋Meta 対応 CAPI（ワンクリック）。EC プラットフォームならパートナー連携（B-11、B-25）
2. **最初の 2 週間で見ること**: イベントマネージャの EMQ・カバー率・追加で報告されたコンバージョン。二重計上が無いか（B-09、B-16、B-17、B-13）
3. **最適化のイベントは件数優先**。週 50 件（00 §6）に遠いなら、購入より手前（カート追加・チェックアウト開始など）も候補〔推測〕
4. **アトリビューションは標準・クリック 7 日のまま触らない**。インクリメンタルの列は「見るだけ」（B-03）。モデルの切り替えは学習のやり直し（B-02）
5. **月 300 ドル以上をウェブの成果に使うなら CAPI ゲートウェイを検討**（Meta が示す目安、B-12）
6. **計測の変更日を台帳に書く**（CAPI の導入・イベントの差し替え・2026-03 の定義変更）（G26 §13-8）
7. **リードの成約は台帳で評価**。コンバージョンリードは月 200 件・28 日以内・転換率 1〜40% の条件（B-33）

## 14. 判断の型

| 症状・問い | 最初に見るところ | 次の手 |
|---|---|---|
