## 0. 先に結論（この章で一番効く 12 点）

1. **実装の依頼は「ピクセル＋CAPI の冗長設定、同じ `event_id`、メールと電話のハッシュ、`fbc`・`fbp`・`external_id`・IP・ユーザーエージェント」までを 1 枚で渡す。** 部分だけ頼むと、06 の EMQ・カバー率・重複除外のどれかで詰まる ✅〔公式の推奨〕本文（F24-04、F24-01、F24-15）
2. **CAPI は 1 回のリクエストで 1,000 件まで。専用のレート制限は無く、Marketing API の呼び出しとして数える。** タイムアウトは 1,500 ミリ秒に置く（多くは 600 ミリ秒未満で返る）。4xx は直してから送り直し、タイムアウトなどクライアント以外の原因のときだけ再送する ✅〔仕様〕〔公式の推奨〕本文（F24-03、F24-14）
3. **`test_event_code` を付けて送ったイベントは「捨てられない」。** イベントマネージャに入り、ターゲティングと効果測定に使われる。本番では外す ✅〔仕様〕本文（F24-03）
4. **ハッシュ化の前に正規化する。** メールは前後の空白を取って小文字、電話は記号・文字・先頭の 0 を取って**国番号から**（日本の 090-1234-5678 は `819012345678`〔推測: 公式の規則を日本の番号に当てた例〕）、国は `jp` を**1 か国のデータでも必ず**送る。IP はハッシュ化しない ✅〔仕様〕本文（F24-01）
5. **`fbc` は大文字・小文字を変えない。** `fb.1.<ミリ秒>.<fbclid>` の形。ピクセルが無くても、URL に `fbclid` があれば CAPI で `fbc` を送れる。自分で `_fbc` を置くなら**HTTP の応答ヘッダーで 90 日** ✅〔仕様〕〔公式の推奨〕本文（F24-02）
6. **v13.0 から「それだけでは無効」な組み合わせがある。** 顧客情報が「市・国・州・郵便番号・性別・ユーザーエージェント」「生年月日＋ユーザーエージェント」「名＋性別」「姓＋性別」のどれか（またはその一部）だけのイベントは無効になる ✅〔仕様〕本文（F24-04）
7. **`external_id` は送れるなら必ず送る。** `fbp` しか無いと Meta は `fbp` を `external_id` の代わりに使うが、両方あれば `external_id` が優先される。ピクセル・CAPI・オフラインで**同じ値**にする ✅〔公式の推奨〕本文（F24-15）
8. **EMQ の目安「6.0 以上」は開発者文書に書いてある。** 「Where possible, we typically recommend that you aim for an Event Match Quality score of 6.0 or higher」（F24-13）。06 §6-1 と rules.csv M-計測-050 の「公式に基準の数値は無い（❓）」と食い違う △。開発者文書は範囲を「1〜10」、ヘルプは「0〜10」と書く点も △
9. **Google アナリティクスを「パートナー連携」としてイベントマネージャにつなげられる。** GA のキーイベントを Meta のコンバージョンイベントに対応づける（ウェブのイベントだけ、ランディングページビューは不可）✅〔仕様〕本文（F24-21）。06 §1・§1 末尾の「Meta には GA4 から取り込む道は無い」と食い違う △。ただし、こうして入ったイベントが**配信の最適化に使われるか**は書かれていない ❓
10. **ピクセル ID は公開情報。** 他人のサイトに貼られると、知らないドメインのイベントが入る。イベントマネージャの［トラフィックの許可］で**許可リスト**を作る（ブロックリストとの併用は不可。上位ドメインを足すとサブドメインも入る）✅〔仕様〕〔公式の推奨〕本文（F24-18）
11. **限定データ使用（LDU）は米国の 14 州だけの仕組み。** 日本向けの運用では設定しない。日本で効くのは電気通信事業法の**外部送信規律**（2023-06-16 施行。通知・公表／同意／オプトアウトのどれか）✅〔仕様〕本文（F24-05、F24-25）。どの事業者が対象かの当てはめは、このメモでは判断しない
12. **イベントマネージャの［診断］は 24 時間以内に検出された問題を［アクティブ］に出し、3 日触らないと［過去に検出された問題］へ移って直し方が消える。** 週 1 の点検では間に合わない ✅〔仕様〕本文（F24-17）

Google 側は G24 の記述に合わせた（記憶で書いていない）。06 §1 の対比表と重なる行は省いた。

| 観点 | Google 広告（G24） | Meta 広告 | 運用の判断への効き方 |
|---|---|---|---|
| ブラウザのタグの部品 | Google タグ（gtag.js）＋イベント スニペット、GTM、コンバージョン リンカー（G24 §1-1） | ベースコード（`<head>`、`fbq('init')`＋`PageView`、`<noscript>` の画像）＋イベントコード（`<body>` の中ならどこでも）✅ 本文（F24-08、F24-09） | Meta にはリンカーに当たる部品は無い。クリック ID（`fbclid`→`_fbc`）の保存はピクセルが行い、サーバーから自分で置くこともできる（F24-02） |

### 2-2. 実装の 4 段 ✅〔公式の推奨〕本文（F24-07）

開発者文書は CAPI の始め方を 4 段で書く: ①連携の方法を選ぶ ②その方法の前提をそろえる ③実装する ④設定を確かめ、成果のためのベストプラクティスに従う。前提は**ピクセル ID**（すでにあるならブラウザとサーバーで**同じ ID**）、**Meta Business Suite**、**アクセストークン**、イベントの種類ごとの必須パラメーター。

### 2-3. アクセストークン ✅〔仕様〕本文（F24-07）

| 作り方 | 手順 | 条件 |
|---|---|---|
| イベントマネージャ（推奨） | ピクセルを選ぶ →［設定］→ コンバージョン API の［手動で設定］の［アクセストークンを生成］。［概要］の［連携を管理］→ コンバージョン API の［管理］で、CAPI 用のアプリとシステムユーザーが自動で作られる | リンクは**開発者の権限がある人にだけ見える** |
| 自社のアプリ | ビジネス設定でシステムユーザーにピクセルを割り当て、［トークンを生成］ | 自社のアプリとシステムユーザーが要る |

- どちらも**アプリの審査も権限の申請も要らない**と開発者文書は書く ✅
- v12.0 以降に作ったトークンは、作った時点の最新版に限らず、使えるすべての Graph API の版で動く ✅
- 開発者文書の注: Marketing API のアクセスの段階名が「Standard → Limited」「Advanced → Full」に変わり、Full の条件は「過去 15 日に 500 回の呼び出し」（旧 1,500）✅（F24-07）
- ファイアウォールの内側の企業は Meta のクローラーの IP 一覧が要り、それは「頻繁に変わる」✅

### 2-4. 運用の判断への効き方

** ピクセルに紐づく鍵は、漏れると他人が購入イベントを送れる〔推測〕。置き場所は `.env` などに限り、共有の文書に書かない
- **ブラウザとサーバーで別のピクセル ID を使わない。** 重複除外も EMQ も同じデータセットの中で働く（F24-07、06 §5-2）
- **代理店に頼むなら「誰のポートフォリオのシステムユーザーで作るか」を先に決める。** 代理店のポートフォリオで作ると、契約が切れたときに CAPI が止まる〔推測〕（06 §2-2 のデータセットの権限と同じ考え）

### 2-5. Google との違い

Google は Google タグの「送信先」を足すだけで GA4 と Google 広告に同時に送れる（G24 §1-1）。Meta はピクセルと CAPI が**同じ ID で 2 本の経路**を持ち、サーバー側は**トークンを持つ別の仕組み**として作る。Google の sGTM は「あると良い」、Meta の CAPI は 06 §4-5 のとおり「標準構成」。

## 3. Meta ピクセルの設置

### 3-1. ベースコード ✅〔仕様〕〔公式の推奨〕本文（F24-08）

| 項目 | 決まり |
|---|---|
| 置き場所 | 「行動を計測するすべてのページ」の `<head>` と `</head>` の間を**強く推奨**。`<head>` に置くと、ブラウザや第三者のコードに実行を止められる可能性が下がる |
| ID | ベースコードの**2 か所**（`fbq('init', ...)` と `<noscript>` の画像の URL）にピクセル ID が入る |
| PageView | ベースコードは読み込むたびに `PageView` を 1 回送る。**この呼び出しは残すことを推奨** |
| `<noscript>` | 1×1 の非表示の画像（`https://www.facebook.com/tr?id=<ID>&ev=PageView&noscript=1`）。画像だけで入れる方法もあるが「推奨しない」 |
| 確かめ方 | ページを開いてイベントマネージャに `PageView` が出れば設置できている。出なければ数分待って再読み込み、それでもだめなら Data Advisor |
| タグマネージャ | ほとんどのタグ管理の仕組みで動く。各ツールの文書に従う |
| スマホ用の別サイト | パソコン用と別のモバイルサイトがあるなら**両方に入れる** |

- ❓ 1 ページに置けるピクセルの数、HTTPS の要否、Content Security Policy、iframe、シングルページアプリの扱いは、この開発者文書のページに書かれていない（F24-08）。確かめ方: 開発者文書の「Advanced」系のページ

### 3-2. 画像（IMG）ピクセルの制約 ✅〔仕様〕本文（F24-10、06 §3-4）

- 画像タグで詳細マッチングを使うなら、**自分で SHA-256 でハッシュ化**し、`ud[em]`・`ud[fn]`・`ud[ln]` などで送る
- 手動の詳細マッチングは**ベースコードの中**（`fbq('init', ...)` の第 3 引数）に置く。そうしないと手動の詳細マッチングとして扱われない ✅
- メールは「小文字のハッシュ前」と「正規化した SHA-256」の両方を受け付ける。ピクセルがメールを SHA-256 でハッシュ化するとコード例に書かれている ✅。他の鍵も自動でハッシュ化するかは、このページに明記が無い ❓（ヘルプ 06 §3-4 は「ピクセルが自動でハッシュ化する」と書く）

### 3-3. イベントコード ✅〔仕様〕本文（F24-09）

| 項目 | 決まり |
|---|---|
| 標準イベント | `fbq('track', '<名前>', {...})`。名前は 06 §3-2 の 17 種 |
| カスタムイベント | `fbq('trackCustom', '<名前>', {...})`。**名前は 50 文字まで**の文字列 |
| 置き場所 | `<body>` の中ならどこでも。ページの読み込み時か、ボタンのクリックなどの操作時 |
| 前提 | 計測するページすべてにベースコードが入っていること |
| パラメーター | 第 3 引数の JSON。カスタムオーディエンスの条件に使うキーは**値に空白を含めない** |
| `value`・`currency` | 購入と、価値の最適化を使うすべてのイベントで `value` が必須。金額であること |
| `contents` | オブジェクトの配列。各オブジェクトに `id` と `quantity` が必須 |
| `content_ids` | 整数か文字列の配列（SKU など） |
| `content_type` | `product` か `product_group`（`content_ids`／`contents` が商品 ID か商品グループ ID かに合わせる） |
| その他 | `num_items`（InitiateCheckout）、`search_string`（Search）、`status`（CompleteRegistration）、`predicted_ltv`、`delivery_category`（`in_store`・`curbside`・`home_delivery`）、`content_category`、`content_name`。標準・カスタムどちらにも独自のプロパティを足せる |

- カタログ（商品メディアを表示する広告）に要るイベントと `content_ids` の決まりは `21` §8 に書いた
- ✅ **2025-09-02 から**、健康状態（例: 関節炎、糖尿病）や財務状況（例: 信用スコア、高収入）を示唆するカスタムコンバージョンはフラグが付き、API で `is_unavailable: true` が返る。フラグの付いたものは新しいキャンペーンに使えない（F24-09。異議・編集・別のものを選ぶよう求められる）

### 3-4. GTM で入れる ✅〔公式の推奨〕本文（F24-20）

ヘルプの手順の要点:

1. GTM で新規タグ →［カスタム HTML］→ イベントマネージャ（［データソース］→ データセット →［イベントを追加］→［新しい連携を追加］→［Meta ピクセル］→［ウェブサイトに手動でコードを追加］）でコピーしたベースコードを貼る
2. ［詳細設定］の［タグ呼び出しオプション］を**［1 ページにつき一度］**、トリガーは**［すべてのページ］**
3. イベントごとに別のカスタム HTML タグ（`fbq('track','AddToCart',{currency:...,value:...})` など）と、条件付きのページビューのトリガー（例: URL が `/product/` を含む）
4. GTM の［プレビュー］と Data Advisor で確かめ、［送信］で公開。イベントマネージャでピクセルが「アクティブ」かを確かめる

- 準備として挙げられているもの: GTM の管理者権限、イベントマネージャへのアクセス、ウェブのコンテナ、（任意）GA4 へのアクセス、ビジネスポートフォリオ、ベースコード
- 同じ記事は「サーバーサイドタグ設定とコンバージョン API（GTM）」として、イベントマネージャで CAPI をサーバーサイド GTM とつなぐ別記事を案内する（題名だけ確認。本文は未読 ❓）

### 3-6. ピクセルトラフィックの許可 ✅〔仕様〕〔公式の推奨〕本文（F24-18）

| 項目 | 決まり |
|---|---|
| なぜ要るか | ピクセルはベースコードと ID だけなので、サイトに置いた時点で ID は公開情報。他人がその ID を自分のサイトに置ける。パートナー連携・第三者の広告技術・iframe 経由のリダイレクトでも知らないドメインが参照元に出る |
| リストの種類 | 許可リストかブロックリストの**どちらか一方**（併用不可）。**許可リストを推奨** |
| 許可リスト | 足したドメイン以外は自動でブロック |
| ブロックリスト | 足したドメインだけブロック、ほかは自動で許可 |
| サブドメイン | 上位ドメイン（`domain.com`）を足すとサブドメイン（`m.domain.com`）も入る |
| 知らせ | 新しいドメインからのイベントを検知すると、ピクセルを持つポートフォリオか広告アカウントの完全な管理権限を持つ人の**1 人だけ**にメール。［診断］にも出る |
| 誰が変えられるか | ピクセルを作った広告アカウントのキャンペーン管理権限か完全な管理権限、ピクセルを作ったビジネスの完全な管理権限、ピクセルの完全な管理権限を持つ人 |
| 別物 | 広告が出る先を決める「パブリッシャーの許可リスト・ブロックリスト」とは別 |

### 3-7. 運用の判断への効き方

- **ベースコードは GTM でも直書きでもよいが、2 重に入れない。** 直書きと GTM の両方で `init` すると `PageView` が 2 回飛ぶ〔推測〕。Data Advisor で 1 ページ 1 回かを見る（ショップ広告のヘルプにも「ピクセルの重複を修正する方法」の記事がある＝F21 側の出典）
- **購入イベントは「サンクスページの表示」か「注文確定の操作」のどちらかに決め、両方に付けない**〔推測〕。両方に付けると `event_id` が別になり、重複除外が効かない
- **新しいサイトでは最初に許可リストを作る。** 自社のドメイン（LP 用の別ドメイン、決済の外部ドメインを含む）を全部入れる。決済が外部ドメインで完了する構成は、許可リストから漏れると購入が消える〔推測〕
- **カスタムコンバージョンの名前と URL に病名・収入などを入れない。** 2025-09-02 以降はフラグで使えなくなる（F24-09）。健康・金融の商材は、名前を「申込完了」など中立にする〔推測〕
- **GTM の［1 ページにつき一度］を外さない。** シングルページアプリでは画面遷移で `PageView` が出ないことがある〔推測〕。その場合はトリガーを履歴の変更にするなど、GTM 側で設計する（公式の Meta 側の記載は ❓）

### 3-8. Google との違い

Google の GTM には Google 広告用の公式のタグの型があり、コンバージョン リンカーもタグとして入れる（G24 §1-2）。Meta のヘルプの手順は**カスタム HTML にコードを貼る**形で、リンカーは無い。Google には「タグを他人に貼られる」前提の設定（トラフィックの許可）が G24 に無い。

### 4-2. ダイレクト連携の決まり ✅〔仕様〕本文（F24-03、F24-14）

### 4-5. CAPI for App Events ✅〔仕様〕本文（F24-06）

| 項目 | 決まり |
|---|---|
| 送り先 | `POST /{DATASET_ID}/events`。アプリのイベントは**データセットに紐づける必要がある** |
| アプリとデータセット | 送る前にアプリをデータセットにリンク。**1 つのデータセットにリンクできるアプリは 1 つだけ** |
| 統合の確認 | `GET /{ads-pixel-id}/is_consolidated_container` で統合済み・対象かを見る |
| `action_source` | `app` |
| `event_id` | 重複除外のために必須。不正確な ID は誤って重複扱いになりうる |
| `app_data.advertiser_tracking_enabled` | **必須**。0 か 1。iOS 14.5 以降の端末の ATT の許可を示す |
| `app_data.application_tracking_enabled` | 任意。0 か 1 |

### 4-6. 運用の判断への効き方

| 状況 | 選ぶもの | 理由 |
|---|---|---|
| 小さな自社サイト、開発者なし、月の広告費が少ない | Meta 対応 CAPI（ワンクリック）→ EMQ を見て判断 | 無料・保守なし（F24-11）。06 §4-4 の「照合の鍵が増えない」弱点は残る |
| GA4 と GTM で計測を組んでいる | ピクセルは GTM、CAPI は sGTM か Meta 対応 CAPI。GA 連携は**補助** | GA 連携の最適化への効き方が ❓（§4-4） |
| 複数ドメイン（本体・LP・キャンペーンサイト）をまたぐ | CAPI ゲートウェイ（1 インスタンスで複数ドメイン） | F24-11 |
| 店舗・電話・CRM の成約を返す | ダイレクト連携か、CRM・POS のパートナー連携 | §4-1 の △ を確かめてから |
| アプリがある | CAPI for App Events か MMP のパートナー | `advertiser_tracking_enabled` と `extinfo` を正しく（F24-06） |

- **ダイレクト連携の発注書に「1,000 件ずつ」「1,500 ミリ秒」「4xx は再送しない」「`event_time` 7 日超は送る前に外す」を書く。** 夜間の一括送信で 8 日前の 1 件が混ざると、その夜の全件が落ちる（F24-03）
- **ゲートウェイの費用は「月 30 ドルから」だが、上限は書かれていない。** クラウドの請求は別に見張る〔推測〕

### 4-7. Google との違い

Google の sGTM・タグ ゲートウェイは、Google タグを自社ドメインから配信して Cookie と遮断を改善する仕組み（G24 §6）。Meta の CAPI ゲートウェイも自社のクラウドに置くが、目的は**ピクセルと CAPI の冗長設定と `event_id` の自動付与**。Google の「Data Manager」に当たる、Meta の GA 連携は**最適化への効き方が公式に書かれていない**点が違う。

06 §4-3 の表（`action_source`・`event_time`・`event_id`・`fbp`・`fbc`・`data_processing_options`・`original_event_data`）を土台に、**正規化とハッシュ化の決まり**を足す。

### 5-1. 顧客情報パラメーターの一覧と正規化 ✅〔仕様〕本文（F24-01、F24-10）

全体の決まり: リクエストには**正しい形の `user_data` を 1 つ以上**。連絡先（名前・メール・電話）は**送る前にハッシュ化**（照合だけに使う。Business SDK は自動でハッシュ化）。ページの例は SHA-256 の出力（F24-01）。ブラウザから送る値とサーバーから送る値は**一致させる**。

| キー | 中身 | ハッシュ化 | 正規化の決まり（公式） | 日本のデータに当てると〔推測〕 |
|---|---|---|---|---|
| `em` | メール | 必須 | 前後の空白を取り、小文字 | 全角の英数字が混ざるなら半角にしてから小文字〔推測〕 |
| `ph` | 電話 | 必須 | 記号・文字・**先頭の 0** を取る。**国番号を必ず付ける**（1 か国のデータでも） | `090-1234-5678` → `819012345678`、`03-1234-5678` → `81312345678` |
| `fn`・`ln` | 名・姓 | 必須 | ローマ字（a-z）を推奨。小文字、句読点なし。特殊文字は **UTF-8** で（例: 韓国語の文字、`valéry`） | 漢字・かなのまま UTF-8 で送れるが、推奨はローマ字。どちらが照合しやすいかは ❓ |
| `db` | 生年月日 | 必須 | `YYYYMMDD`。年 1900〜今年、月 01〜12、日 01〜31 | 和暦は西暦に直す |

| `ct` | 市 | 必須 | ローマ字推奨、小文字、句読点・特殊文字・**空白なし**。特殊文字は UTF-8 | `shibuya` など。漢字の扱いは `fn` と同じく ❓ |
| `st` | 州・県 | 必須 | 米国は 2 文字の ANSI 略号の小文字。米国以外は小文字、句読点・特殊文字・空白なし | `tokyo` など〔推測〕 |
| `zp` | 郵便番号 | 必須 | 小文字、空白とダッシュなし。米国は先頭 5 桁、英国は「地域・地区・セクター」 | `150-0002` → `1500002` |
| `country` | 国 | 必須 | 小文字の ISO 3166-1 alpha-2。**照合は世界全体なので 1 か国でも必ず** | `jp` |
| `external_id` | 広告主の ID | **推奨**（必須ではない） | 他の経路でも同じ形に（§5-4） | 会員 ID をハッシュ化して |
| `client_ip_address` | IP | **しない** | 正しい IPv4 か IPv6。**IPv6 があれば IPv6**。空白なし。実際の IP。ブラウザのイベントは自動、サーバーのイベントは手で入れる | ロードバランサーの IP を送らない〔推測〕 |
| `client_user_agent` | ユーザーエージェント | しない | **CAPI のウェブのイベントで必須**。IP と一緒に全イベントで送ると照合と配信が良くなりうる | — |
| `fbc` | クリック ID | しない | §5-2 | — |
| `fbp` | ブラウザ ID | しない | §5-3 | — |
| `subscription_id` | 定期購入の ID | しない〔記載から〕 | 1 商品の注文 ID のように働く | — |
| `fb_login_id` | アプリスコープの ID（整数） | しない | Facebook ログインで初回に発行 | — |
| `lead_id` | リード広告のリード ID（整数） | しない | — | 06 §9-3 |
| `anon_id` | アプリのインストール ID | しない | アプリのイベントだけ | — |
| `madid` | 広告 ID（AAID・IDFA） | しない（App Events の文書）／一覧の表には記載なし ❓ | — | — |
| `page_id`・`page_scoped_user_id` | ページ ID、Messenger のページスコープ ID | しない | — | — |
| `ctwa_clid` | クリック・トゥ・WhatsApp 広告のクリック ID | しない | — | — |
| `ig_account_id`・`ig_sid` | Instagram のアカウント ID、IGSID | しない | — | — |

- ✅ 配列で送れるのは `em`・`ph`・`fn`・`ln`・`db`・`ge`・`ct`・`st`・`zp`・`country`・`external_id`。他は 1 つの文字列か整数（F24-01）
- ✅ 一部のパラメーターはピクセルからも送れ、`client_user_agent` のようにブラウザで自動で集まるものもある（F24-01）
- ✅ Parameter Builder Library を使うと、各パラメーターに付加の文字列（appendix）が付く。中身はライブラリのページを見る（F24-01、F24-02）

### 5-2. `fbc`（クリック ID）✅〔仕様〕〔公式の推奨〕本文（F24-02）

| 項目 | 決まり |
|---|---|
| 元 | 広告のクリックで Meta が URL に付ける `fbclid` |
| 大文字・小文字 | 「ClickID の値は大文字と小文字を区別する。使う前に**一切変更しない**」 |
| 形 | `fb.{subdomainIndex}.{creationTime}.{fbclid}` |
| `subdomainIndex` | Cookie を置いたドメインの段数。`com`=0、`example.com`=1、`www.example.com`=2。サーバーで作って `_fbc` を置かないなら **1** |
| `creationTime` | `_fbc` を保存した時刻の **UNIX ミリ秒**。保存しないなら、`fbclid` を初めて見た時刻 |
| 取り方 | サーバーでリクエストの URL のクエリから `fbclid` を読む。無ければ Cookie ヘッダーの `_fbc` |
| ピクセルが無いとき | 今の URL に `fbclid` があれば、CAPI で `fbc` を送れる |
| 自分で `_fbc` を置く | **HTTP の応答ヘッダーで、有効期間 90 日**。置くのは「`_fbc` が無く URL から `fbclid` が取れたとき」か「URL の `fbclid` が Cookie の値（最後の `.` の後ろ）と違うとき」だけ |
| 代わりの方法 | 形を整えた値を自社のデータベースに持つ。URL に新しい値があれば最新のものに |
| 送る頻度 | 「すべてのイベントで `fbc` を送ることを推奨」 |
| ハッシュ化 | ページに明記は無いが、例ではハッシュ化していない（メール・電話はハッシュ済みで並ぶ）|

### 5-3. `fbp`（ブラウザ ID）✅〔仕様〕本文（F24-02）

- ピクセルがファーストパーティ Cookie を使うとき、`_fbp` が無ければ「サイトのドメインに一意の識別子を保存する」
- 形は `fb.{subdomainIndex}.{creationTime}.{randomnumber}`。乱数はピクセルの SDK が作る。**サーバーで乱数を作る方法は書かれていない** ❓
- `fbc`・`fbp` はセッションをまたいで変わりうるので、保存したプロフィールを最新の値で更新する（F24-02、F24-04）
- ❓ `_fbp` の寿命は記載なし（06 §3-3 と同じ）

### 5-4. `external_id` ✅〔仕様〕〔公式の推奨〕本文（F24-15）

| 項目 | 決まり |
|---|---|
| 型 | 文字列か文字列の配列。1 イベントに 1 つ以上 |
| ハッシュ化 | 推奨 |
| 一貫性 | 「チャネルをまたいで一貫させなければならない」。ピクセル・CAPI・オフライン・アプリイベントで同じ人に同じ値（例: ピクセルで `123` なら CAPI でも `123`） |
| 照合の仕組み | ①`external_id` と他の顧客情報を一緒に送る ②Meta が全部の情報で照合し、見つかれば `external_id` をその人に結びつける ③その後は `external_id` だけのイベントでもその結びつきを使う |
| 結びつきの寿命 | 定期的に切れる。「できるだけ頻繁に更新」 |
| 使えるオーディエンス | ウェブサイト・アプリ・オフラインのカスタムオーディエンス、それを元にした類似。**顧客リストのカスタムオーディエンスは `external_id` だけでは作れない** |
| `fbp` との関係 | `fbp` があって `external_id` が無いと、Meta は `fbp` を `external_id` として使う。両方あれば**常に `external_id` が優先**（性能が良いため） |

### 5-5. 照合の最低線（v13.0 以降）✅〔仕様〕本文（F24-04）

顧客情報が次の組み合わせ（またはその一部）だけのイベントは**無効**:

| 無効になる組み合わせ |
|---|
| `ct` ＋ `country` ＋ `st` ＋ `zp` ＋ `ge` ＋ `client_user_agent` |
| `db` ＋ `client_user_agent` |
| `fn` ＋ `ge` |
| `ln` ＋ `ge` |

- 読み方〔推測〕: 地域・性別・生年月日・名前の片方だけでは人を絞れないので、**メール・電話・`external_id`・`fbc`・`fbp`・IP のどれか**を必ず添える

### 5-6. `custom_data`（標準のパラメーター）✅〔仕様〕本文（F24-28）

- `value`（金額）と `currency`（3 文字の ISO 4217）は購入で必須。価値の最適化を使うイベントでも `value` が必須
- `contents` は `id`・`quantity`・`item_price`・`delivery_category` を持つ JSON の配列
- `content_type` は `product` か `product_group`。`num_items` は InitiateCheckout だけ、`search_string` は Search だけ
- `order_id` は文字列。`predicted_ltv`（予測の生涯価値）、`net_revenue`（利益の値）もある
- 注意: カタログの `price` は「数値＋空白＋通貨コード」だが、`value` は数値だけ。**同じ形にしない**（F24-28、`21` §4）

### 5-7. 運用の判断への効き方

- **正規化の仕様書を 1 枚作り、ピクセル・CAPI・オフライン・顧客リストで共有する。** `external_id` と電話の形が経路で違うと、照合が割れる（F24-15）。日本のデータでは、電話の国番号と先頭の 0、郵便番号のハイフン、全角の混入が主な落とし穴〔推測〕
- **名前・住所は「足せるなら足す」程度。** 優先度が低く（06 §6-1）、名＋性別などは単独で無効（§5-5）。フォームで聞く項目を増やすより、メールと電話を確実に取る
- **`fbc` は LP の最初のリクエストで拾う。** 遷移の途中で `fbclid` が落ちると取り戻せない。外部の決済ドメインへ移る前に自社のサーバーで保存する〔推測〕（F24-02 の「サーバーで URL から読む」から）
- **`value` は「税込か税抜か」「送料を含むか」を決めて、Google・GA4 と同じ定義にする**〔推測〕。公式は「金額であること」以上を決めていない（F24-09、F24-28）

### 5-8. Google との違い

Google の拡張コンバージョンは「メール・電話・氏名＋住所」をハッシュ化して送り、gclid は別の仕組み（G24 §4）。Meta は**同じ `user_data` の中に、ハッシュ化するもの（em・ph など）としないもの（IP・UA・fbc・fbp）が並ぶ**。Google は v13 の「無効な組み合わせ」に当たる線を G24 に書いていない。

## 6. データセット

### 6-1. 決まり ✅〔仕様〕本文（F24-06、F24-07、06 §2）

- ピクセル ID ＝ データセット ID。CAPI はその ID に送る（F24-07）。アプリのイベントもデータセットに紐づける（F24-06）
- 1 つのデータセットにリンクできるアプリは 1 つ（F24-06）
- 統合済み（consolidated）のデータセットかどうかを API で確かめられる（F24-06）
- データセットの共有は、メンバー・広告アカウント・パートナーを別々に足す（ヘルプの記事の題名: 「ビジネスポートフォリオでデータセットにメンバーを追加する方法」「…広告アカウントを追加する方法」「…パートナーを追加する方法」。本文は未読 ❓）

### 6-2. 運用の判断への効き方

- **1 つの事業（1 つのサイト）＝ 1 つのデータセット。** 事業ごとに分けるかはオーディエンスと最適化の単位で決める〔推測〕。カタログの売上キャンペーンでは広告セットごとにデータセットを選ぶようになった（`21` §10）
- **アプリが 2 つあるならデータセットも 2 つ。** 1 データセット 1 アプリの決まり（F24-06）

### 6-3. Google との違い

Google はコンバージョン アクションが単位（G24・G06）。Meta はデータセットが単位で、その中のイベント名で最適化を選ぶ（06 §2-3）。

## 7. イベントのマッチングクオリティ（EMQ）の上げ方

定義・優先度・48 時間の計算は 06 §6-1。ここでは**上げるための実装**だけを書く。

### 7-1. 公式に書かれた目安 ✅〔公式の推奨〕本文（F24-13）

- 開発者文書（Verifying Setup）: 「Event Match Quality is scored from 1 to 10」「Where possible, we typically recommend that you aim for an Event Match Quality score of 6.0 or higher」。スコアを押すと推奨が出る。Overview か Setup Quality API で見る
- △ 06 §6-1 と rules.csv M-計測-050 は「EMQ の『良い』の基準の数値は公式に示されていない ❓」と書き、範囲を 0〜10（ヘルプ B-09）とする。開発者文書の「1〜10」「6.0 以上」と食い違う。**6.0 はヘルプではなく開発者文書の推奨**として扱う
- セルフサービスのコンバージョンリフトの条件「EMQ 5 超」（06 §6-1、`26` §5）とは別の数字

### 7-2. 上げ方の順番（公式の要素を、効く順に並べ直した）

| 順 | やること | 根拠 |
|---|---|---|
| 1 | メール（`em`）を取れる場面すべてで送る（ログイン・会員登録・購入・リード） | 優先度「高」（06 §6-1） |
| 2 | `fbc` を全イベントで送る（URL の `fbclid` から作るか `_fbc` を読む） | 優先度「高」（06 §6-1）。「すべてのイベントで送ることを推奨」（F24-02） |
| 3 | `client_ip_address`（IPv6 優先）と `client_user_agent` を全イベントで | IP は「質の高い顧客情報パラメーター」（F24-04）。UA はウェブで必須（F24-01） |
| 4 | `external_id` を全イベントで、全経路で同じ値に | F24-04、F24-15 |
| 5 | 電話（国番号つき）、`fbp`、国（`jp`） | 優先度「中」（06 §6-1）、F24-01 |
| 6 | 名・姓・市・郵便番号は余力があれば | 優先度「低」（06 §6-1）。単独では無効の組み合わせあり（§5-5） |
| 7 | 鍵を「顧客の行動の早い段階」で取る（`_fbp`・`_fbc`） | Parameter Builder の推奨（06 §4-3） |
| 8 | 送り続ける（48 時間で計算） | 06 §6-1 |

### 7-3. 運用の判断への効き方

- **EMQ が低いとき、最初に見るのは「ハッシュ化の前の正規化」と「`fbc` の欠け」。** 正規化を間違えると、送っていても照合されない〔推測〕。Payload Helper で 1 件の形を確かめる（F24-04）
- **テストで自分のデータを使う。** 開発者文書は「テストイベントは Meta のアカウントに照合されないと捨てられることがある」と書く（F24-04）。架空のメールでテストすると「届かない」と誤解する
- **EMQ 6.0 は「入札・予算を変える前の上流の確認」の目安にする**〔推測〕。成果が出ないときに入札を触る前に、計測の上流（EMQ・カバー率 75%・鮮度）を片づける（`28` の運用の型の順序と同じ）

### 7-4. Google との違い

Google の拡張コンバージョンの診断は「一致率」などを出す（G24 §4-4）が、0〜10 の 1 本のスコアと「6.0 以上」の目安は Meta 特有。

## 8. ドメインの認証

使う場面は 06 §8-3（リンク編集の権限、ショップでの販売、ビジネス認証など）。ここでは**やり方**を書く。

### 8-1. やり方 ✅〔仕様〕本文（F24-16、F24-22）

| 項目 | 決まり |
|---|---|
| 費用 | 無料（F24-22） |
| 場所 | ビジネス設定 →［ブランドセーフティ］→［ドメイン］→［追加］（F24-16） |
| 方法 | **1 つだけでよい**: ①DNS の TXT レコード（ホストの欄に `@` が要る業者もある）②HTML ファイルをサイトの**ルート**に置く ③メタタグをドメインの**ホームページ**の `<head>` に |
| 時間 | DNS は「通常は数分、最大 72 時間」。HTML とメタタグの待ち時間は記載なし |
| 残すか | TXT・ファイル・タグは**残す**。「認証のために定期的に確かめられることがある」 |
| 誰が | HTML の方法はサイトのルートへの管理者アクセスが要る。**代理店はドメインの所有者のビジネスマネージャで認証**し、後で共有してもらう |
| 認証でできること | ドメインにページを割り当て、リンクの編集権限を管理（オーガニック・有料の両方）。Open Graph のタグを手で直さずに所有権を示せる |

- ❓ サブドメインと eTLD+1 の扱い、ドメインの数の上限は、このページに無い。第三者のフォーラムは「サブドメインではなく主ドメイン」「タグは静的な HTML に（クローラーは JavaScript を実行しない）」と書く〔実務家・仮説〕抜粋
- ✅ ヘルプは同じページで、有料の「ビジネス向け Meta 認証」（認証バッジ・なりすまし対策など）を案内する。ドメイン認証とは別物（F24-22）

### 8-2. 運用の判断への効き方

- **メタタグは GTM で入れない。** Meta のクローラーが JavaScript を実行しないなら読めない〔実務家・仮説〕。HTML に直書きか DNS にする
- **DNS の TXT は「72 時間」を見込んで、公開の 3 日前に入れる**（F24-16）
- **代理店のポートフォリオで認証しない。** 所有者のポートフォリオで認証し、代理店にはパートナーとして共有（F24-16）

### 8-3. Google との違い

Google 広告の運用で「ドメインの所有権を広告の仕組みに示す」作業は G24 に無い。Meta ではリンク編集の乗っ取り防止とショップの前提になる。

## 10. iOS・ブラウザの制限

06 §8 は AEM（8 件の優先順位は不要になった）と SKAdNetwork まで。ここでは**クリック ID と Cookie が落ちる場面**を書く。

### 10-1. 何が落ちるか

| 制限 | 中身 | 印 |
|---|---|---|
| iOS の ATT | アプリのイベントで `advertiser_tracking_enabled`（0／1）を必ず送る | ✅ 本文（F24-06） |
| Safari のリンク追跡保護（Link Tracking Protection） | Safari 17 から、**プライベートブラウズ**で、サイト間の追跡に使われる既知のクエリ引数を、遷移の前に URL から取り除く。キャンペーンの集計だけに使う引数（例: `campaign`）は通す | ✅ 本文（F24-26） |
| 同上の対象の引数 | **`fbclid` が対象かは、WebKit の本文に引数の一覧が無く確かめられない** ❓。第三者は `fbclid` が除かれると書き、メール・メッセージのアプリでも働くと書く | 〔実務家・仮説〕抜粋 |
| ITP の Cookie の短縮 | `document.cookie` で置く永続 Cookie の上限など（G24 §1-4 と同じ WebKit の仕組み） | G24 §1-4 を参照 |
| CAPI は回避の手段ではない | 「ATT や e プライバシー規則を回避する手段として設計されたものではない」 | ✅ 06 §4-1（B-10） |

### 10-2. 運用の判断への効き方

- **`fbc` が取れない人は一定数いる前提で、メール・電話・`external_id` を厚くする。** `fbclid` が落ちても、ログインや購入で取れる鍵で照合できる（§7-2）〔推測〕
- **`_fbc` はサーバーから HTTP の応答ヘッダーで置く**のが公式の推奨（F24-02）。WebKit の ITP が短くするのは `document.cookie` で置く Cookie（G24 §1-4）なので、サーバーで置く方が残りやすい〔推測: 2 つの公式文書の組み合わせ。Meta はこの理由を書いていない〕
- **`fbclid` を自前の別名の引数に置き換える小技は使わない。** 第三者が勧める例がある〔実務家・仮説〕が、Meta の `fbc` は「`fbclid` の生の値」を求める（F24-02）。広告側の URL を変える方法は公式に無い ❓

### 10-3. Google との違い

Google は iOS で gclid が付かない場面に gbraid・wbraid を用意した（G24 §1-1）。Meta には `fbclid` の代わりの識別子は公式文書に無く、**AEM（06 §8）と、メールなどの照合の鍵**で補う形。

## 11. イベントマネージャの診断と確かめ方

### 11-1. ［診断］タブ ✅〔仕様〕本文（F24-17）

| 項目 | 決まり |
|---|---|
| 対象 | ウェブ・アプリ・オフラインのイベントの問題と、設定を良くする推奨 |
| ［アクティブ］ | **24 時間以内に検出**され、解決済みでも無視でもない問題 |
| ［過去に検出された問題］ | 最初の検出から **3 日間**操作しないとここへ移り、**解決方法が表示されなくなる** |
| ［無視］ | ［無視する］を押したもの。戻すまで残る |
| 重要（赤） | できるだけ早く直す。プラットフォームの更新、プライバシーの規制の改定、Meta のプライバシーポリシーへの違反などに伴う、優先度の高い変更 |
| 警告（黄） | 優先度が低い。例: 値のパラメーターの設定の誤り、ピクセルが新しいドメインからイベントを送り始めた |
| 解決 | 手順に従って直す。翌日に検出されなければ自動で［過去に検出された問題］へ。3 日後に再び検出されれば［アクティブ］に戻る |
| 共有 | ウェブ・アプリの問題の［無視］［解決済み］は**ポートフォリオの全員に効く**。オフラインの［無視］は自分だけ。オフラインに［解決済みにする］は今は無い |

### 11-2. ［イベントのテスト］✅〔仕様〕本文（F24-23、F24-03）

- 場所: イベントマネージャ →［データソース］→ データセット →［テストイベント］
- ウェブ: サイトの URL を入れて［ウェブサイトを開く］。**［テストイベント］のページを開いている間だけ**記録される
- できること: 受信の確認、異常の検知、**ウェブのイベントの重複除外**（どれが処理され、どれが重複として除かれたか）
- 絞り込み: 標準・カスタム・自動で記録されたピクセルのイベント（HTML のメタデータ、ボタンのクリックなど）・自動で記録されたアプリのイベント、URL・パラメーター・問題
- テストの情報は **24 時間**か削除するまで残る。［アクティビティをクリア］しても、イベントマネージャ・広告レポート・オーディエンスには残る
- 分析に出るまで **30 分以上**かかることがある
- CAPI のテストは `test_event_code` を付ける（F24-03）。**付けたイベントも捨てられず、ターゲティングと効果測定に使われる**

### 11-3. Overview の各タブ ✅〔仕様〕本文（F24-13）

| 見るもの | 場所 | 読み方 |
|---|---|---|
| 受信・破棄・処理 | Overview | 重複除外の前の件数、同意の管理などで破棄された件数、処理された件数 |
| 経路 | ［接続方法］ | どの経路（ブラウザ・サーバーなど）で来たか |
| 鮮度 | イベントの詳細 →［イベントの鮮度］ | 平均の遅れを「リアルタイム」〜「毎週」で |

| EMQ | Overview か Setup Quality API | §7-1 |

### 11-4. 点検の順番（この章の型。各手順の中身は公式）

| 順 | 見るもの | 止まったら |
|---|---|---|
| 1 | ［診断］の［アクティブ］の「重要」 | 3 日以内に直す（F24-17） |
| 2 | Overview の受信・破棄・処理 | 破棄が多い → 同意・ポリシー。処理が少ない → 形式 |
| 3 | ［接続方法］ | サーバーの経路が無い → CAPI が止まっている |

### 11-5. 運用の判断への効き方

- **［診断］は毎日見るか、少なくとも 2 日に 1 回。** 3 日で直し方が消える（F24-17）。週次の点検にしか入れていないなら、日次の軽い点検に移す
- **［無視］は全員に効くので、代理店と共有のポートフォリオでは押す前に知らせる**（F24-17）
- **CAPI のテストを本番のデータセットでやるなら、テストの購入を実在の金額で送らない。** `test_event_code` 付きでも効果測定に入る（F24-03）。金額 0 か、テスト用のデータセットを使う〔推測〕

### 11-6. Google との違い

Google のタグ診断は Google 広告の管理画面にあり、メッセージごとに直し方が出る（G24 §10）。Meta は［診断］の 24 時間・3 日のルールと、［無視］の全員共有が独特。重複除外の「重なり」のような指標は G24 に無い。

## 14. よくある思い込みと実際

| 思い込み | 実際 | 出典 |
|---|---|---|
| テストで送ったイベントは本番に混ざらない | `test_event_code` 付きでも捨てられず、ターゲティングと効果測定に使われる | F24-03 |
| CAPI は大量に送るとレート制限に当たる | 専用の制限は無い。1 回 1,000 件まで、Marketing API の呼び出しとして数える | F24-03 |
| 顧客情報は全部ハッシュ化する | IP・UA・`fbc`・`fbp`・`madid`・`anon_id` はハッシュ化しない | F24-01、F24-06 |
| 日本のデータなら国は送らなくてよい | 照合は世界全体なので 1 か国でも必ず `jp` | F24-01 |
| 電話は 090 から始まる 11 桁のままでよい | 先頭の 0 を取り、国番号から（81…） | F24-01 |
| 名前と性別だけでも照合に効く | 名＋性別、姓＋性別だけのイベントは無効 | F24-04 |
| `fbclid` は小文字にそろえて保存してよい | 大文字・小文字を区別する。一切変えない | F24-02 |
| ピクセルが無ければ CAPI で `fbc` は送れない | URL に `fbclid` があれば送れる | F24-02 |
| `external_id` は CAPI だけで送ればよい | ピクセル・オフライン・アプリで同じ値にする | F24-15 |
| ピクセル ID は秘密 | 公開情報。他人が貼れる。許可リストで防ぐ | F24-18 |
| 許可リストとブロックリストを両方使える | どちらか一方だけ | F24-18 |
| LDU は日本の同意にも使える | 米国 14 州だけの仕組み | F24-05 |
| 日本の法令はピクセルに関係ない | 外部送信規律（2023-06-16）がある。当てはめは法務で | F24-25 |
| 診断は週 1 で見れば足りる | 3 日放置で直し方が消える | F24-17 |
| ドメイン認証は計測のために必須 | ウェブのイベント設定のためには不要（06 §8-1）。リンク編集・ショップなどのため | 06、F24-22 |
| EMQ の目安は公式に無い | 開発者文書に「6.0 以上を目指すことを勧める」（ヘルプには無い）△ | F24-13 |
| Meta は GA と一切つながらない | イベントマネージャのパートナー連携で GA のキーイベントを対応づけられる（最適化への効き方は ❓）△ | F24-21 |

## 15. 少額・少量のアカウントでの注意

- **ワンクリックの Meta 対応 CAPI で始め、EMQ と鮮度を 2 週間見る。** ゲートウェイやダイレクト連携の費用と手間に見合うかは、その後で決める〔推測〕
- **イベントが少ないと EMQ・重複除外の率が安定しない**〔推測〕（48 時間で計算＝06 §6-1）。数日分を並べて読む
- **小さな EC は Shopify などのパートナー連携が最短。** 重複除外も多くは自動（06 §5、F24-19）
- **代理店に「CAPI を入れて」とだけ頼まない。** §0-1 の 1 枚を渡す

## 16. 判断の型

| 状況 | まずやること | 次に | 根拠 |
|---|---|---|---|
| 成果の件数が急に増えた | 重複除外のタブの「重なり」と率 | `event_id` の不一致を直す | F24-13、06 §5-4 |
| 成果の件数が急に減った | ［診断］の重要、［接続方法］、トラフィックの許可 | 同意のバナーの導入日、サイトの改修日を確かめる | F24-17、F24-18、F24-13 |
| EMQ が低い | 正規化（電話・国・メール）、`fbc` の欠け | IP・UA・`external_id` を全イベントに | F24-01、F24-02、§7 |
| 知らないドメインのイベント | 許可リスト | 決済・LP のドメインを漏らさない | F24-18 |
| CAPI の夜間バッチが全部落ちた | 7 日より古い `event_time` の混入 | 送る前に外す処理 | F24-03 |
| 健康・金融の商材でカスタムコンバージョンが使えない | 名前と URL のルールに病名・収入の語が無いか | 中立の名前で作り直し、異議 | F24-09 |
| 米国に売る越境 EC | LDU を州の判定（`0,0`）で | 影響（リターゲティング・効果測定の制限）を見込む | F24-05 |
